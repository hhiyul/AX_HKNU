# 백엔드 v0.3 재구성 — 설계 결정

기준 문서: `AX_STUDIO_Project_UX_Flow_Atlas_v03` (F00–F11),
조원 파이프라인 명세 `origin/feature/ai-agent-pipeline` 의 `docs/ai-agent-pipeline/`.

질문 없이 진행하라는 요청이라 아래 결정은 모두 백엔드 담당이 임의로 내린 것이다.
파이프라인 코드가 오면 다시 맞춘다.

## 목표

- 프로젝트 작업실(개요, 상품기획, 경제성, 기획 산출물, 추가 기록, AI 채팅)의 저장 구조와 API를 만든다.
- 여러 탭·기기에서 같은 자료를 고칠 때 조용히 덮어쓰지 않는다.
- 응답을 못 받은 저장 요청이 두 번 반영되지 않는다.

## 하지 않는 것

- AI 답변 생성, 문서 자동 작성, 웹 검색. 파이프라인이 붙을 자리(서비스 함수)만 둔다.
- 프론트 화면.
- 휴지통·복구. 삭제는 바로 지운다.
- 대용량 파일 업로드 (나중에).

## 공통 규칙

| 규칙 | 내용 |
|---|---|
| 소유권 | 모든 문서에 `user_id`. 남의 자료와 잘못된 ID는 404 |
| 버전 | 고칠 수 있는 문서는 정수 `revision`. 요청의 revision이 다르면 409 `REVISION_CONFLICT` |
| 프로젝트당 하나인 문서 | 기획 항목, 추가 기록, 비용표. 아직 없으면 revision 0으로 보내야 만들어진다 |
| 중복 요청 | `Idempotency-Key` 헤더. 같은 키는 한 번만 처리, `GET /requests/{key}` 로 결과 조회, 7일 보관 |
| 프로젝트 삭제 | 딸린 자료를 모두 지운다. 진행 중인 AI 작업이 있으면 409 `PROJECT_IN_USE` |

## 영역별 결정

**프로젝트** — 이름만 있으면 만든다. 브랜드는 선택이고 나중에 연결·해제할 수 있다.
`target_customer`, `features`, `expected_price`, `status` 는 없앴다. 그 내용은 기획 항목이 맡는다.

**상품기획** — 항목은 `ck_01`–`ck_06` 고정. 항목마다 초안(`draft`)과 확정본(`decided`)을 따로 갖는다.
상태는 저장하지 않고 계산한다: 초안이 있으면 DRAFT, 확정본만 있으면 DECIDED, 둘 다 없으면 UNSET.
확정된 항목을 다시 고치는 동안에도 기존 확정본은 남는다. 확정할 때마다 이력(`plan_versions`)이 쌓인다.
내용은 다듬지 않고 그대로 저장한다. 금액은 `ck_05` 에만 넣는다.
일괄 저장은 항목별로 결과를 돌려주고 통과한 것만 반영한다. 내보내기는 MD와 TXT가 같은 글이다.

**추가 기록** — 프로젝트당 문서 하나에 항목을 모은다(최대 200개). 항목마다 DRAFT/DECIDED.
비슷한 기록 찾기는 글자 2개 단위 겹침 비율 0.5 이상 또는 같은 제목. 알려주기만 하고 저장을 막지 않는다.

**경제성** — 비용표는 통째로 바꿔 저장한다. 금액 `null` 은 "모름"이고 0과 구분한다.
가정(`ASSUMPTION`)은 `approved` 가 true일 때만 계산에 쓴다.
시나리오는 만들 때 계산해 저장한다. 빠진 비용은 `excluded` 에 이유와 함께 남기고 `complete: false`.
채택하면 `ck_05` 의 초안으로 넘어간다. 확정은 상품기획에서 따로 한다.

> 계산식은 임시다: 이익 = 판매가 − 원 단위 비용 합 − (판매가 × 비율 비용 합), 수수료는 원 단위 반올림.
> 세금·배송 배부 기준은 팀에서 정해지지 않았다(파이프라인 명세 C-02). `economics.compute()` 만 고치면 된다.

**기획 산출물** — 문서는 기획 항목과 따로 저장하고 기획이 바뀌어도 자동으로 고치지 않는다.
문서를 만들 때 항목별 확정 버전을 적어 두고, 지금과 다르면 `stale_items` 로 알려준다.
`sync` 는 "바뀐 기획을 확인했다"는 표시만 한다. 최종본을 고치면 다시 DRAFT가 되고 이전 최종본은 이력에 남는다.

**AI 채팅** — 프로젝트당 하나. 처음 조회할 때 만들어진다.
HTTP로는 사용자 메시지만 받는다. AI 답변은 파이프라인이 `chat.add_message(role="ASSISTANT")` 로 남긴다.
메시지 순번은 채팅 문서의 `message_count` 를 원자적으로 올려 받는다. 설정 revision과는 별개다.

**AI 제안** — 제안은 기획과 따로 보관한다. 대상은 `ck_01`–`ck_06` 또는 `record`.
만들 때 대상의 revision을 적어 두고, 조회할 때 그 사이 대상이 바뀌었는지(`target_changed`) 알려준다.
반영은 사용자가 고친 최종 내용과 대상의 현재 revision을 보내야 한다. 닫힌 제안은 409 `PROPOSAL_CLOSED`.

**개요·맥락** — `overview` 는 화면용 요약, `projection` 은 AI에 넘길 맥락이다.
`projection` 의 섹션 이름과 `bundle_revision` 은 파이프라인 명세를 따랐다.

## UX v0.3과 파이프라인 명세가 어긋나는 곳

| 주제 | UX v0.3 | 파이프라인 명세 | 지금 구현 |
|---|---|---|---|
| 채팅 범위 | 프로젝트 밖 전체 채팅(F09) | 프로젝트와 채팅 1:1 | 1:1. 다른 프로젝트는 읽기 전용 참고(`chip_refs`) |
| 추가 기록 | 항목별 초안·확정 | 프로젝트당 문서 하나 | 문서 하나, 항목마다 상태 |
| 삭제 | 버전 보관 | 휴지통 없음 | 바로 삭제, 확정 이력만 보관 |
| 채팅 요약(캡슐) | — | 저장 구조 있음 | 만들지 않음 |

## 파이프라인이 붙을 때 손볼 곳

- `ai_jobs.job_type` 값 목록 (보류 중)
- 제안을 만드는 주체: 지금은 HTTP로 누구나 만들 수 있다. 파이프라인이 직접 `proposals.create_proposal` 을 부르게 되면 HTTP 생성은 닫아도 된다.
- 경제성 계산식
- 문서 자동 작성과 `basis` 채우기
- 브랜드에는 revision이 없다. `projection` 은 브랜드 수정 시각으로 대신한다.

## 기존 DB

`init_db.py` 가 규칙을 바꾸기 전에 예전 문서를 보정한다:
`projects`·`assets` 에 브랜드 주인의 `user_id` 를 채우고, 프로젝트에 `revision: 1` 과 빈 이름을 채운다.
