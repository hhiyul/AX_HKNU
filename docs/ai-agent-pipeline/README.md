# AI 에이전트 파이프라인 명세

AI 에이전트 파이프라인의 명세를 상위 요구사항부터 모듈 설계까지 순서대로 정리하는 디렉터리입니다.

현재는 [프로토타입·Figma 분석](00-prototype-analysis/README.md)과 [AI 파이프라인 사용자 기능명세 v0.1 초안](02-user-feature-spec/ai-pipeline-user-feature-spec-v0.1.md)을 준비한 단계입니다. 팀원이 작성할 시스템 기능명세는 아직 없으며, 사용자 기능명세의 상위 추적 관계는 연결 대기입니다. 모듈 기능명세는 작성 전입니다. 분석 자료와 사용자 기능 초안은 상위 시스템 기능명세를 대체하지 않습니다.

## 현재 확인된 제품 기준

- 전체 백엔드, 프로젝트 구성, 브랜드 생성은 팀원이 담당합니다. 이 세션에서는 AI 채팅 파이프라인, 에이전트 루프, 도구 호출과 하네스 구성을 분석하고 명세화합니다.
- 이 세션의 파일 변경 범위는 `docs/ai-agent-pipeline/` 안입니다.
- PLAN-01·PLAN-02는 폐기되었습니다. 첨부 HTML에 남은 PLAN 화면·확정본 선택·데이터 구조는 현행 요구사항으로 채택하지 않습니다.
- 주 작업 방식은 Chat입니다. 상품 기획의 6개 항목은 각각 내용과 상태를 가지며, 고정된 작성 순서를 강제하지 않습니다.
- AI는 내부 평가와 편집 가능한 제안을 만듭니다. 저장된 체크리스트의 내용·상태는 사용자의 저장/확정 선택과 서버 검증을 거쳐 갱신합니다.
- 프로젝트에 연결된 Chat의 체크리스트 저장 대상은 해당 프로젝트 하나로 고정합니다. 다른 프로젝트 작업은 새 Chat에서 시작합니다(D-UF-001).
- 독립 Chat에서 프로젝트를 최초 한 번 첨부하듯 연결해 해당 프로젝트의 Projection 정보를 불러오고 같은 대화를 이어갈 수 있습니다. 구체적인 UX와 Projection의 조회·갱신·모델 입력 범위, 연결 전 이력·내부 평가의 모델 입력 취급 및 다른 프로젝트의 읽기 전용 참조는 미정입니다(D-UF-002).
- 연결 전 제안은 프로젝트의 Projection 정보를 바탕으로 재검토한 뒤 사용자가 내용·항목을 확인하고 저장·확정을 선택합니다. 재검토만으로 저장되지 않습니다(D-UF-003).
- 프로젝트 연결 시 Projection은 불러오되 재검토는 자동 실행하지 않고 사용자가 명시적으로 요청할 때 실행합니다. 기존 제안의 저장 시도만으로도 재검토를 자동 실행하지 않습니다(D-UF-004).
- 명시적인 재검토 요청에서 대상이 요청·문맥상 명확하면 바로 실행하고, 모호할 때만 확인합니다. 최신 제안이나 전체 제안을 임의 선택하지 않습니다. 구체적인 UX·의도 및 대상 식별의 세부 기준은 미정입니다(D-UF-005).
- 명시적인 재검토 요청의 대상이 정해지면, 재검토 시작 직전에 Projection을 다시 조회해 그 결과를 재검토 자료로 사용합니다(D-UF-006).
- 재검토는 시작 자료로 완료하고 완료 시 변경 여부를 확인합니다. 변경이 확인된 해당 제안은 이전 정보 기반으로 표시해 저장을 보류하고 명시적인 재요청을 받습니다. 기존 저장 상태는 유지하며 변경만으로 자동 중단·재실행하지 않습니다(D-UF-007).
- 변경 판정은 제안별 실제 입력·조회한 참조 자료 묶음의 버전을 기준으로 하고 저장 대상 항목 버전도 별도로 검증합니다. Projection 전체를 AI에 전달하면 전체 자료 묶음을 참조 범위에 포함합니다. 정확한 묶음 경계·버전 형식과 완료 후 저장까지의 근거 재검증·충돌 처리는 미정입니다(D-UF-008).
- 체크리스트별 내용·상태를 하나의 버전 묶음으로 관리하되, 각 항목 내부에는 실제 사용자 문제를 해결할 하위 필드·질문·평가 기준을 둡니다. 결정한 범위와 아직 미합의인 필드·평가 기준을 [검토안](02-user-feature-spec/checklist-problem-criteria-draft.md)에서 구분합니다(D-UF-009).
- 고객 접점·판매 경로 가설은 고객 선정의 하위 필드로 포함해 저장·평가 대상으로 관리합니다(D-UF-010).
- 고객 선정은 구매 상황별 고객 가설 안에서 구매자·사용자, 목적·상황, 접점·판매 경로와 접근 근거를 연결하는 방향으로 설계합니다. 버전·저장 상태는 고객 선정 항목 단위를 유지하며 가설 개수·실제 저장 구조·필수 입력·세부 충족 및 완료 판정은 미정입니다(D-UF-011).
- 주 사용자는 펀딩을 준비하는 창작자입니다. 고객 가설의 구체화 평가와 실제 검증을 분리하며 아직 없는 실측값·실제 고객 반응을 가설 구체화 완료의 필수 조건으로 요구하지 않습니다. 가설·추정·미정과 실제 근거를 구분하며 세부 필수 정보·충족 조건은 미정입니다(D-UF-012).
- 고객 가설 구체화 완료에는 접점 후보와 해당 고객을 만날 수 있다고 보는 이유가 필수이며, 실제 접근 실적·반응은 비필수입니다. 이 기준을 Chat 진행·초안 저장 조건으로 자동 적용하거나 전체 완료의 충분조건으로 취급하지 않습니다. 나머지 필수 정보·전체 완료 판정은 미정입니다(D-UF-013).
- 참여·구매 목적은 가설 구체화 완료에 필수이며, 구체적인 계기·시점은 제안에 영향을 줄 때만 추가 확인합니다. 모든 가설에 행사·날짜를 요구하거나 필요한 상황 정보를 임의로 채우지 않습니다. 나머지 정보의 필수 수준·전체 완료 판정은 미정입니다(D-UF-014).
- 사용 관계는 제안에 영향을 줄 때만 추가 확인하고 그렇지 않으면 미정으로 남길 수 있습니다. 응원 목적만으로 사용자가 없다고 추정하지 않으며, 미정과 사용자 없음을 구분합니다. 나머지 필수 정보·전체 완료 판정은 미정입니다(D-UF-015).
- 대상을 구별할 특성·관계는 가설 구체화 완료에 필수입니다. 관심·행동·역할·창작자와의 관계 등으로 대상을 설명할 수 있으면 되며, 예시를 모두 채울 필요는 없습니다. 연령·성별·직업 등은 제안에 영향을 줄 때만 추가 확인하고 이미 파악한 내용을 반복 질문하지 않습니다. 필수 기준을 사용자 직접 입력 목록으로 만들지 않으며, 나머지 세부 평가·전체 완료 판정은 미정입니다(D-UF-016).
- 중요한 정보가 미정이면 조건별 제안을 제공하고 해당 고객 가설 전체의 구체화 완료는 보류합니다. Chat과 부분 제안은 계속하며 같은 미정 질문을 반복하지 않습니다. 이는 내부 평가의 보류로 저장 상태 변경이나 다른 체크리스트의 보류로 자동 확대하지 않습니다. 중요성 판단은 D-UF-018을 따르며 보류 해제·재평가·상황 변화 후 재질문·기록의 세부 기준은 미정입니다(D-UF-017).
- 조건부 확인 정보는 추천 대상·접점·구성·핵심 메시지·실행 조건 등 핵심 선택이 달라질 때만 중요하게 봅니다. AI는 어떤 선택이 어떻게 달라지는지 설명해야 하며 단순한 말투·표현·개인화 차이만으로 추가 확인이나 완료 보류를 요구하지 않습니다. 기존 필수 요건과 반복 질문 방지 기준은 유지하며 설명의 세부 품질·경계 사례 등은 미정입니다(D-UF-018).
- 같은 미정 사항의 재질문은 사용자 요청이 있거나 관련 상황의 실질적인 변화로 질문의 필요성·영향이 달라졌을 때만 이유를 설명하고 수행합니다. 시간 경과·대화 진행만으로 반복하지 않고 이미 답을 확인할 수 있으면 활용합니다. 여전히 모르면 조건별 제안·Chat을 계속하며 재질문 자체는 평가 보류 해제·저장·확정을 뜻하지 않습니다. 상황 변화·요청의 세부 식별·설명 품질과 재평가·기록·복구 등은 미정입니다(D-UF-019).
- 진행 중인 Chat에서 새 정보가 들어오면 영향을 받는 기준과 남은 보류 사유를 별도의 평가 요청 없이 같은 응답에서 갱신합니다. 해소된 사유와 남은 사유를 구분하며 평가만으로 저장된 내용·상태를 바꾸지 않습니다. 연결 전 제안의 프로젝트 기반 재검토는 기존 명시적 요청 원칙을 유지하고, 전체 완료·보류 해제의 세부 충족 조건과 다른 재평가·실패 처리·표시·기록·복구는 미정입니다(D-UF-020).
- 평가 갱신의 기본 안내는 변경된 평가와 남은 보류 사유를 짧게 전달하고 상세 기준별 결과는 사용자 요청 시 제공합니다. 기본 안내에도 보류 사실·사유가 드러나야 하며 전체 기준별 평가표를 매번 나열하지 않습니다. 요약·상세 제공만으로 저장·확정하지 않고 정확한 형식·위치·상세 요청 UX·최신성 안내·기록·복구는 미정입니다(D-UF-021, OPEN-UF-14).
- 고객 선정의 전체 구체화 완료 판정에는 실제 진행 대상으로 정한 가설만 포함합니다. 여러 진행 대상은 모두 평가하며 미선택 비교 후보의 미정 자체는 전체 완료를 막지 않습니다. 진행 대상의 중요한 미정·공통 영향 정보는 계속 평가하고, 대상 지정은 D-UF-023을 따릅니다. 변경의 세부 규칙과 실제 저장 구조·세부 충분조건은 미정이며 범위 결정만으로 후보를 삭제하거나 저장 내용·상태를 바꾸지 않습니다(D-UF-022).
- 진행 의사와 대상·범위가 명확하면 추가 확인 없이 평가 범위에 반영하고 모호할 때만 확인합니다. 단순한 긍정·AI 추천·최근 언급만으로 선택을 대신하지 않으며 진행 대상 지정과 저장·확정은 구분합니다. 의도·대상 식별의 세부 기준·UX와 변경의 세부 규칙·기록·복구는 미정입니다(D-UF-023).
- 진행 대상에서 빠진 이전 가설은 현재 작업의 비교 후보로 남겨 다시 검토·선택할 수 있게 합니다. 비교 후보의 미정 자체는 전체 완료를 막지 않으며 변경·후보 유지·재선택만으로 저장된 내용·상태를 바꾸지 않습니다. 재선택 시 전체 재평가는 D-UF-025를 따르며 참조 자료의 갱신·조회와 실제 후보 표시·정리·별도 삭제·보관 기간·기록·복구는 미정입니다(D-UF-024).
- 이전 가설을 재선택하면 현재 대화·참조 자료로 해당 가설의 전체 기준과 남은 보류 사유를 같은 응답에서 다시 평가합니다. 별도 평가 요청을 필수로 요구하지 않고 과거 판정의 자동 승계나 변경 부분만의 평가로 대체하지 않습니다. 저장된 내용·상태는 자동으로 바꾸지 않으며 프로젝트 연결 Chat의 재조회 시점은 D-UF-026을 따릅니다. 정확한 필드·조회 범위·모델 입력과 실패·미완료·자료 변경 처리는 미정입니다(D-UF-025).
- 프로젝트 연결 Chat의 재선택 평가는 대상·범위가 명확해진 뒤 실제 평가 시작 직전에 같은 프로젝트의 Projection을 다시 조회하고 그 자료로 전체 기준·남은 보류 사유를 평가합니다. 연결 당시나 확인 질문 전 조회로 대신하지 않으며 저장된 내용·상태는 자동으로 바꾸지 않습니다. 실패의 기본 처리는 D-UF-027을 따르며 재시도·평가 재개와 정확한 필드·모델 입력·자료 변경의 세부 처리는 미정입니다(D-UF-026, OPEN-UF-03).
- 재선택 평가의 Projection 재조회가 실패하면 해당 평가를 보류하고 재시도를 안내하되 Chat과 부분 제안은 계속할 수 있습니다. 이전 자료로 평가 완료를 대신하지 않고 실패·보류·부분 제안만으로 저장된 내용·상태를 바꾸지 않습니다. 보류 후 재시도 실행은 D-UF-028을 따르며 요청의 세부 식별·UX와 성공 후 평가 재개·동시 요청·기록·복구는 미정입니다(D-UF-027, OPEN-UF-10).
- 보류 안내 후에는 사용자가 명시적으로 재시도를 요청할 때만 실패한 Projection 조회를 다시 시도합니다. 재시도 안내·연결 회복·시간 경과·다른 대화만으로 자동 실행하지 않고 요청·재조회만으로 저장된 내용·상태를 바꾸지 않습니다. 성공 후 동일하고 명확한 대상의 재개는 D-UF-029를 따르며 대상 변경과 세부 요청 식별·UX·기록·복구는 미정입니다(D-UF-028).
- 재시도 조회가 성공하고 보류했던 평가 대상이 그대로이며 명확하면 추가 확인 없이 같은 응답에서 새 자료로 전체 기준·남은 보류 사유를 재평가합니다. 재개·평가만으로 저장된 내용·상태를 바꾸지 않습니다. 진행 대상에서 빠진 가설의 보류 평가는 D-UF-030을 따르며 그 밖의 변경·불명확 시 처리와 세부 식별·동시 요청·실패·자료 변경·기록·복구는 미정입니다(D-UF-029).
- 진행 대상에서 빠진 가설의 보류 평가는 종료하고 이전 가설은 비교 후보로 유지합니다. 재선택하면 현재 자료로 새로 평가하며 종료·재선택·새 평가만으로 저장된 내용·상태를 변경하지 않습니다(D-UF-030).

위 기준은 2026-10-30 사용자 설명·추가 확인 및 공유 Figma를 근거로 합니다. 상세 항목과 아직 결정되지 않은 계약은 분석 문서와 [사용자 기능명세의 미정 계약 목록](02-user-feature-spec/open-contracts.md)에서 구분합니다.

## 작성 및 읽기 순서

1. 시스템 기능명세를 먼저 확인하여 기능의 목적과 범위를 맞춥니다.
2. 해당 시스템 기능을 근거로 사용자 기능명세를 작성합니다.
3. 사용자 기능을 충족하도록 모듈 기능명세를 작성합니다.

이번 사용자 기능 초안은 사용자의 명시적인 요청으로 상위 시스템 기능명세보다 먼저 작성했습니다. 현재는 확인된 제품 기준과 분석을 근거로 하며, 시스템 기능명세가 준비되면 범위·권한·공통 데이터의 정합성과 추적 관계를 대조합니다. [미정 계약](02-user-feature-spec/open-contracts.md)은 별도로 유지합니다.

하위 명세에는 근거가 되는 상위 문서의 상대 경로와 해당 기능명 또는 기능 ID를 연결합니다. 상위 요구사항이 없거나 모호한 부분은 미정으로 남겨 두고, 하위 설계만으로 확정하지 않습니다.

## 문서 관리 기준

- 각 폴더의 `README.md`는 해당 계층의 안내와 문서 목록을 제공합니다.
- 실제 명세 문서는 해당 계층의 폴더에 추가하고 안내 문서에서 연결합니다.
- 문서를 분리할 때는 기능이나 모듈 단위로 나누고, 파일명으로 내용을 식별할 수 있게 합니다.
- 작성 예정 항목, 검토 중인 제안, 확정된 내용을 구분합니다. 안내 문서의 항목 목록은 확정된 기능 요구사항을 뜻하지 않습니다.
- 한글 문서는 UTF-8로 저장합니다.
- 이 경로에는 명세를 관리합니다. 실행 코드의 배치 위치는 모듈 설계 시 별도로 정합니다.
