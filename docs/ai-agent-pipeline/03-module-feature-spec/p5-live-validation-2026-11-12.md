# P5 실제 OpenAI 합성 데이터 검증 — 2026-11-12

## 범위와 결과

사용자가 실제 유료 호출을 승인한 범위에서 `feature/ai-agent-pipeline`의 P5 합성 프로토타입을 별도 localhost 서버와 합성 SQLite로 검증했다. 프로젝트·브랜드·대화·문서는 모두 테스트용이며 공통 MongoDB에는 연결하지 않았다. 모델은 `gpt-6-luna`이고 서버의 실제 OpenAI 모드 표시와 완료 응답을 확인했다. 키와 압축된 요약 내용은 이 기록에 포함하지 않는다.

실제 요청 세 건은 모두 완료됐다. 두 번째와 세 번째 요청에서 모델이 프로젝트 정보 읽기 도구를 각 1회 호출했고 그 진행·결과가 표시됐다. 웹 검색은 허용하지 않았고 실행하지 않았다. 모델 생성의 숨은 재시도 여부까지 포함한 정확한 Provider 호출 횟수, 실제 사용량 및 청구 금액은 현재 P5 로그에 기록되지 않아 확정할 수 없다. 계수 검증 요청도 실제 API를 사용했다.

## 합성 입력과 결과 검증

압축 전용 사용자 이력은 합성 색상 결정을 포함하는 텍스트와 반복 단어로 구성했고 UTF-8 약 325KB였다. 이 데이터는 테스트 DB의 기존 짧은 대화 앞에 삽입했다. 이후 일반 채팅은 압축 캡슐을 만들었으며, 04 생성 요청은 **현재 대화 포함**을 명시했다. 문서의 출처 확인은 메시지 ID와 revision/상태 메타데이터만 검사했고 압축 본문은 사용자 화면이나 이 문서에 공개하지 않았다.

정상 응답은 서버의 `response.completed`·모델 확인을 통과했다. 브라우저에서 첫 채팅의 3개, 압축 후 채팅의 20개, 문서 생성의 92개 텍스트 증분을 확인했다. 문서 생성은 프로젝트 자료 읽기 결과가 비어 있어도, 명시 포함한 과거 대화의 내용과 현재 저장된 CK를 구별했다.

## 남은 범위

- 첫 일반 채팅의 회상 실패를 해결하거나 동일 입력에 대한 안정성을 입증한 것은 아니다. 더 명확한 요청에서 문서 생성이 성공한 사실과 별개로 후속 원인 분석·회귀 검증이 필요하다.
- 실제 압축은 1단계만 관찰했다. 단계별 실패 재시도, 최대 3단계·최대 6회, 실제 모델 한도 초과·연결 단절·동시성은 기존 가짜 Provider/합성 단위 테스트의 범위이며 이번 실호출 결과가 아니다.
- P5 프로토타입의 실제 팀 인증·프로젝트/브랜드/CK owner·공통 파일 저장소·운영 DB 통합과 다중 프로세스 안전성은 검증하지 않았다. 현재 코드에는 비용과 실제 호출별 사용량을 사용자에게 확인할 수 있는 운영 기록이 없다.
- AI의 기존 문서 수정·삭제 경로는 사용자의 최신 요청에 따라 이번 구현과 검증 범위에서 제외했다. 생성 문서는 사용자가 직접 저장했다.

## 후속 원인 분석과 대조 — 2026-11-12

### 확인된 사실

- 합성 원문에는 두 색상이 있었고, 내부 캡슐에도 두 색상을 뜻하는 단어와 선택·제외 관련 단어가 있었다. 단어 검사만으로 요약 의미가 완전히 보존됐다고 단정하지 않는다. 캡슐 전문은 공개하지 않는다.
- 실패한 실행의 순서는 압축 시작 → 압축 완료 → 프로젝트 정보 읽기 → 답변이었다. 도구 결과에는 여섯 CK가 모두 `UNSET`으로 표시됐다. 원래 Provider 요청 전문은 저장되지 않아 해당 실행의 실제 wire를 직접 대조할 수 없다.
- 해당 코드 경로를 격리된 가짜 Provider로 재현하자, 압축 직후 첫 입력에는 요약이 과거 대화로 표시됐지만 프로젝트 읽기 도구 결과를 전달하는 두 번째 입력에서는 그 표지가 빠졌다. 회귀 시험은 수정 전 실패했다. 이는 **입력 표지의 실제 결함**이나, 이번 실패를 일으킨 유일한 원인이라는 증거는 아니다.
- 사용자의 기존 실호출 허용 범위에서 합성 캡슐·질문·미작성 CK 도구 결과를 이용해 입력을 가능한 범위에서 재구성하고, 과거 대화 표지만 다르게 한 생성 요청을 각 1회 실행했다. 표지가 없는 경우 799 입력 토큰, 있는 경우 807 입력 토큰이었고 두 답변 모두 채택·제외 색상을 정확히 구분했다. 각 경우 하나의 표본이며, 원래 `call_id`와 도구 인자 전문이 보존되지 않았으므로 원본 wire의 완전 재현은 아니다. 이 결과는 표지 누락이 실패를 반드시 일으킨다는 가설을 뒷받침하지 않는다.

### 해석 및 수정

현재 확인된 것은 **요약 표지가 도구 호출 뒤 사라지는 결함**과 **모델이 한 번은 실패하고 재구성된 대조 입력에서는 성공한 관찰**이다. CK가 미작성인 것과 미등록 대화의 결정은 서로 다른 사실인데, 모델이 이를 혼동했거나 질문의 참조 범위를 다르게 해석했을 가능성이 있다. 모델 내부 판단은 관측할 수 없으며 입력 재구성 차이·생성 변동 등도 배제할 수 없다. 따라서 답변 실패의 단일 원인은 미확정이다.

서버는 압축 직후, 도구 호출 후, 같은 대화 재방문에 동일한 과거 대화 표지를 유지하도록 수정했다. 문서 자동 라우팅 뒤에도 이미 압축한 이력을 유지해 같은 원문을 불필요하게 다시 압축하지 않는다. 이 동작은 합성 회귀 시험으로 확인했으며, 수정 후 전체 P5 경로의 실제 OpenAI 재검증은 별도로 수행하지 않았다. 사용자가 볼 수 있는 요약 내용·CK 승인·문서 변경 권한은 추가하지 않았다.

채팅 UI는 모델의 텍스트 조각마다 새 블록을 만들던 문제를 수정했다. 같은 연속 답변의 조각은 한 블록에 이어 붙이고, 실제 모델 텍스트의 줄바꿈과 별도 도구 상태 경계는 유지한다. 실시간 표시와 재방문 이력 양쪽에 같은 처리를 적용했다.

첫 모델 호출과 도구 결과 뒤 두 번째 모델 호출에서 각각 **실제 계수한 입력과 발송 직전 입력의 지문이 일치**함을 확인했다. 별도의 검증 래퍼는 요청 내용·요약·키를 기록하지 않고 모델명, 토큰 수, 입력 지문, 요약 표지 수, 도구·스트리밍 이벤트와 시간만 기록했다. [비민감 계측 기록](p5-live-revalidation-trace-2026-11-12.jsonl)은 이번 단일 실행의 12개 기록이다.

이번 재검증에서는 OpenAI **생성 요청 3회**(요약 1회, 도구 선택을 포함한 스트리밍 2회)와 입력 계수 요청 5회를 보냈다. 호출별 청구 금액은 확인하지 못했다. 실호출은 한 번의 성공 사례이며, 이전 실패 원인을 단정하거나 반복 실행의 안정성을 보장하지 않는다. 이번 압축 대상은 오래된 사용자 발화였으므로 오래된 AI 발화까지 함께 압축하는 실모델 사례, 다단계 압축·재시도·실서비스 통합은 이번에 검증하지 않았다. 모델 답변은 과거 대화의 색상을 맞혔지만 해당 결정이 CK에 저장되지 않았다는 점을 별도로 설명하지는 않았다.

## 대화 결정과 CK 저장 상태 구분 개선·실제 검증 — 2026-11-12

사용자 요청에 따라 P5 고정 지침에 대화에서 명시된 사용자 결정과 현재 CK의 저장·상태를 구분하는 규칙을 추가했다. 대화에서의 결정만으로 CK 저장·확정을 추정하지 않고, `UNSET`은 해당 CK에 저장된 값이 없다는 의미이며 과거 대화의 결정을 지우지 않는다. `DRAFT`와 `DECIDED`도 구분한다. 실제로 자료가 없거나 접근 불가하면 `UNSET`으로 추정하지 않고 확인 불가로 다루며, 대화와 CK가 다르면 양쪽 출처와 상태를 설명한다. 이 지침이 CK 쓰기 권한을 부여하지는 않는다.

독립된 두 합성 프로젝트의 장문 대화를 `gpt-6-luna` 실제 API로 검증했다. 실제 사용자 데이터는 사용하지 않았고, 각 사례는 서로 독립된 Chat에서 시작했다.

| 사례 | 합성 조건 | 실제 응답·검증 |
| --- | --- | --- |
| CK 미작성 | 대화에서는 청록색 채택·빨간색 제외. 여섯 CK는 `UNSET`, revision 0 | 같은 과거 실패 질문에 대해 대화의 선택과 제외 색상을 말하고, 현재 CK에는 관련 내용이 저장되지 않았다고 구분했다. CK 여섯 개는 그대로 유지됐다. 브라우저에서 응답 스트리밍과 UI를 확인했다. |

각 사례에서 64k 초과 입력을 실제 압축하고 프로젝트 정보 읽기 도구를 거쳐 최종 답변했다. 첫 사례의 전체 입력은 **65,722 → 744 → 도구 결과 후 985토큰**, 두 번째는 **65,714 → 728 → 도구 결과 후 977토큰**이었다. 두 사례 모두 첫 모델 호출과 도구 호출 뒤 모델 호출에 압축 이력 표지가 유지됐고, 각각 계수한 입력 구성과 발송 직전 입력 구성의 지문이 일치했다. 합성 원문과 캡슐도 보존됐다. 첫 사례의 텍스트 증분은 41개, 두 번째는 118개였다.
