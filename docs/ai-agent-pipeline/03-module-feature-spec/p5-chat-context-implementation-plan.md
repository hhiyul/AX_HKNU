## 1. 이번에 제시된 방향과 기존 계약

| 구분 | 현재 해석 |
| --- | --- |
| 대화 맥락 | 같은 Chat의 대화 전문을 기본 대화 맥락으로 사용하자는 요청. 원문 보관과 모델 호출마다 실제 전송되는 입력은 구별하며, 압축 후 모델이 원문 전체를 동시에 읽는다고 보장하지 않음 |
| **64k 압축 시작** | 사용자가 제시한 기준을 **64,000토큰**으로 추적. 전체 구성된 컨텍스트가 길어지면 OpenAI를 이용한 문자열 압축/요약을 실행. 전체 입력 기준이며 출력 예약·안전 여유 및 모델 하드 한도는 별도 검증(Q-P5-01~03) |
| **압축을 사용자에게 표시** | 채팅 UI에서 실제 압축 시작·진행 및 완료/실패를 구분해 알려 줌. 표시 방식은 디자인 후속, 사실 확인 전 완료 표시 금지. 압축이 저장된 원문 대화 삭제라는 오해를 주지 않음 |
| **스트리밍·중간 작업** | 답변을 증분 표시하고 컨텍스트 준비·압축·실제 도구/작업의 진행과 확인된 결과를 사용자에게 전달. 진행 이벤트는 실제 작업 근거를 갖고 정해진 메시지로 성과를 꾸미지 않음 |
| 프로젝트 맥락 | 접근 허용된 브랜드, 프로젝트 정보, CK·기타 관련 메타데이터를 요청 맥락에 주입. 소유 프로젝트·실제 읽기/사용 범위·상태/출처/revision을 구분 |
| 초기 첨부 | 우선 `.txt`·`.md` **두 형식**의 업로드·파싱·주입을 P5에서 구현. 두 형식이라는 뜻이며 개수는 미정. UTF-8·CP949 지원, 기존 여섯 형식 중 나머지는 현재 Chat 미지원(Q-P5-05·06) |

**기존 압축 결정과의 관계:** Q-P5-01~04로 오래된 사용자·AI 발화와 전체 입력 64,000 기준, 최대 3단계 및 단계당 실패 보완 1회를 채택했습니다. 기존 4k 캡슐·최근 AI 원문 16k와 출력·여유 각 8k는 유지합니다. 세 단계 후 또는 압축할 이력이 없어도 64k 이상이면 경고하고 실제 모델 예산이 허용하면 진행합니다. [현행 모듈 계약](p5-context-module-contract.md)을 따릅니다.

**기술적 구분:** [OpenAI 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-luna)상 `gpt-6-luna`의 컨텍스트 윈도는 1,050,000토큰, 최대 출력은 128,000토큰입니다. 64k는 이 모델의 하드 한도가 아니라 서비스의 조기 압축 기준입니다. 실제 모델 접근·계정 한도와 변경 가능성은 별도 확인합니다. [입력 토큰 계수 API](https://developers.openai.com/api/docs/guides/token-counting)는 메시지 역할·도구 정의 등 최종 요청 형식을 포함해 계수할 수 있습니다. 계수 요청도 OpenAI로 자료를 전송하는 외부 요청이며, 로컬 가짜 계수로는 실제 계정·사용량을 검증하지 못합니다.

## 2. 공통 불변식과 현재 코드 차이

1. 프로젝트 1:N Chat과 각 Chat의 고정 소유 프로젝트를 유지합니다(GD-027). 미등록 가정·대화·캡슐·첨부는 세션 범위이며 다른 세션에 자동 전파하지 않습니다(GD-028·033).
2. 저장된 브랜드/프로젝트/기획 데이터는 해당 owner의 공통 자료입니다. 조회·대화·압축·제안은 CK의 저장 승인이나 확정이 아닙니다. AI의 Field별 제안은 대상·기준 revision과 사용자 선택/최종 승인을 거쳐 같은 CK 정본에 반영합니다(Q1·Q6).
3. 사용자가 파일/Chip을 제거하면 원본 삭제나 과거 대화 삭제와 구분합니다. 진행 중 run은 시작 범위를 유지하고 다음 run부터 제거를 반영합니다(D-UF-103·105). 제거한 자료만의 정보를 과거 응답·요약 등으로 자동 재주입하지 않습니다(D-UF-084 등). 실제 사용/읽기 실패·누락과 접근 권한을 구분합니다.
4. 같은 Chat은 단일 활성 응답, 서로 다른 Chat은 병렬 실행을 지원하는 제품 방향입니다(GD-018·024·027). 입력 작성은 가능해도 응답 중 다음 질문의 자동 큐·전송은 하지 않습니다(D-UF-104). 재접속은 원 실행의 상태/결과 조회이며 새 호출이 아닙니다(GD-019). 사용자가 중단하면 중단 시점의 표시를 고정하고 실제 AX 종료와 Provider 원격 취소를 구분합니다(GD-008·010·012).
5. 개별 Chat 생성 중 삭제는 AX 종료/출력 차단 확인까지 불가(GD-034). 프로젝트 전체 삭제는 진행 중에도 허용하고 삭제 후 늦은 결과 반영을 막아야 합니다(GD-020·026). 삭제·쓰기 경합의 실제 owner 보장은 여전히 확인이 필요합니다.
6. 현재 `backend/app/services/chat.py`는 프로젝트당 단일 메시지 목록, `overview.py`의 projection은 순차 조회와 revision 해시를 사용합니다. `items.py`는 `UNSET/SKIPPED/WRITTEN`과 복수 `record`를 사용합니다. 이들은 각각 1:N 세션, CK의 `UNSET/DRAFT/DECIDED`, UF-AI-16 프로젝트당 추가 기록 1개의 승인된 의미와 동일하지 않습니다. 현재 `responses.py`는 비스트리밍 단일 호출만 구현됐습니다. 기존 제품 동작을 이미 제공한다고 표시하지 않습니다.
7. 04 문서는 프로젝트 1:N, Markdown 본문, 저장본 4형식 export, 사용된 자료의 출처/revision을 유지합니다. 전체 재생성은 검토 후 **새 Document**입니다(Q10·13). AI 문서 수정·삭제는 UI 최종 승인(GD-035), 출처에 원본 사본을 보관하지 않음(GD-039). 03 `.md/.txt` CK·추가 기록 원본 export와 분리합니다.

### 3.1 스트리밍·중간 작업의 구체 경계

- UI에는 최소한 `요청 접수`, 실제 `자료 확인`, 실제 `컨텍스트 압축 중`, `압축 완료/실패`, 실제 `도구 작업 시작/결과`, `답변 생성 중`, `완료/중단/실패`를 구분할 수 있는 정보를 제공합니다. 작업이 발생하지 않았다면 그 단계를 수행한 것처럼 표시하지 않습니다. 압축이 필요 없는 요청에 압축 알림을 띄우지 않습니다. 압축의 구체 문구·배치는 디자인 후속입니다.
- 모델 답변의 증분 텍스트와 백엔드가 관측한 작업 이벤트는 별개입니다. 진행 상황에는 실제 참고/미사용·부분 결과의 범위를 표시하며, 내부 추론 원문을 표시하거나 확인되지 않은 정보를 도구 성공으로 꾸미지 않습니다.
- [OpenAI Responses 스트리밍 문서](https://developers.openai.com/api/docs/guides/streaming-responses)의 `stream=true`와 텍스트 delta·완료·오류 이벤트를 기반으로 별도 어댑터를 설계합니다. delta는 텍스트 조각이며 UI 갱신 단위가 반드시 모델 토큰 하나와 같다는 뜻이 아닙니다. 기존 비스트리밍 단일 호출을 제거하거나 같은 파서를 임의 재사용하지 않습니다.
- 백엔드→브라우저는 SSE 등 지속 연결을 권장하되, POST 입력·재연결·순서/중복·종료를 실제 실행과 결박합니다. 전송 방식·정확한 이벤트 이름/API는 설계안이며 아직 공개 물리 계약이 아닙니다. 새로고침·연결 끊김은 사용자 중단이 아닙니다(GD-019). 원 실행을 조회하고 같은 응답을 다시 생성하지 않습니다.
- 압축 알림에는 시작과 최종 결과를 구별하고 진행 중에는 대화 원문이 사라진 것처럼 보이지 않게 합니다. 상세 토큰/비용 UI는 기존 D-UF-094의 제외를 유지하며 이번 ‘압축 중’ 알림만으로 사용량 대시보드를 추가하지 않습니다.

### 3.2 64k 및 자료 처리 파이프라인

1. 접근 가능한 프로젝트·브랜드·CK와 세션 대화·활성 자료·현재 요청을 구성하고 출처·상태·revision·누락을 식별합니다.
2. 동일 wire의 전체 입력을 계수합니다. 64,000 이상이면 과거 사용자·AI 발화를 함께 요약합니다. 출력 8,000 및 안전 여유 8,000과 실제 모델 한도는 별도로 검사합니다.
3. 정상 압축을 최대 3단계 실행하고 각 단계 실패에는 추가 호출을 1회 허용합니다. 유효 후보는 검증·조건부 저장·재계수하며 총 압축 호출 최대 6회입니다. UI는 압축의 실제 시작·진행·완료/실패를 보여주지만 요약 본문을 공개하지 않습니다.
4. 세 단계 후에도 64k 이상이거나 오래된 대화가 없으면 사용자에게 초과를 알리고 실제 한도·출력 여유 내에서 진행합니다. 실패 보완 소진·실제 한도 초과·계수/권한 실패는 중단합니다. 원문·프로젝트·첨부를 자동 절삭하지 않습니다.
5. txt/md와 UTF-8/CP949를 지원합니다. 첨부 원문과 04 산출물은 같은 프로젝트 파일 저장소를 쓰되 GD-033 세션 격리와 GD-039 출처 원본 사본 없음은 유지합니다. 재방문 시 표시된 작업 단계·결과를 확인할 수 있습니다.

## 5. Q-P5-01~12 채택 결과

사용자 답변과 두 후속 확인은 [Grill 결정 추적](grill-feature-decisions.md) 및 [P5 모듈 계약](p5-context-module-contract.md)에 반영했습니다. 64k는 전체 입력의 압축 시작점, 압축은 오래된 사용자·AI 대화 최대 3단계, 각 실패 단계는 추가 1회입니다. 세 단계 후 또는 대상이 없더라도 64k 초과를 알리고 실제 모델 예산 내에서 진행합니다.

첨부는 txt/md 두 형식·UTF-8/CP949이며 산출물과 프로젝트 파일 저장소를 공유합니다. 압축 내용은 사용자에게 열지 않고 진행·도구 결과는 재방문에도 제공합니다. 필요한 프로젝트 읽기·허용된 웹 검색을 에이전트가 선택하고 자료 충돌은 출처·상태·시점과 함께 설명합니다. 검증은 격리된 합성 DB에서 수행합니다.
