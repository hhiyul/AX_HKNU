## 1. 구현 목표와 기준선

목표는 사용자가 허용한 자료로 대화하고, 필요한 원문·일정을 더 조회하며, 확인한 후보만 저장하고, 같은 문서·항목에서 작업을 이어가는 실제 제품 경로를 완성하는 것이다. 순서는 **참고 범위·출처 → 자료·일정 조회 → 확인 등록 → 문서 작업 → 검토·이어서 생성 → 통합 인수**로 잡는다. 각 Phase에서 API·저장·모델 도구·화면·실패 상태를 함께 연결한다.

2026-11-26 계획 작성 시 `feature/ai-agent-pipeline`의 HEAD는 `4382eb4`이며 작업 트리는 clean이었다. 직전 기능 조사 `c97b411` 이후 보완 명세가 커밋된 상태다. 기존 `backend/main.py` 앱과 `front`를 구현 대상으로 삼는다. 독립 P5 프로토타입이나 새로운 에이전트 프레임워크로 대체하지 않는다. 과거 P5 단계와 혼동하지 않도록 이번 Phase ID는 `AG-P0~6`을 사용한다.

재사용 후보는 일정 CRUD·제안 ID 중복 방지, 문서 항목 revision·후보 반영, 기록 후보/저장, 대화별 이력, run/SSE/중지, 파일 파서·이미지 입력이다. 각 후보는 현재 테스트와 실제 경로를 먼저 확인한 뒤 확장한다. 제품·옵션·거래처 정본과 범용 출처·제외는 존재한다고 가정하지 않는다.

이번 문서는 구현 계획이다. 코드·DB·환경 설정은 변경하지 않았고, 기준선 테스트도 아직 실행하지 않았다.

P0→P1→P2→P3을 먼저 진행한다. P4는 P1·P2와 제품 정본 계약을 필요로 한다. P5의 continuation은 P1과 현재 run 수명 계약, 문서 검토는 P4와 규칙 데이터 계약을 필요로 한다. P6는 적용 범위의 모든 선행 Phase를 인수한다. 이 의존 관계가 개별 변경의 조기 회귀 시험을 뒤로 미루는 이유가 되어서는 안 된다.

기능 추적 대응은 P1: CAP-01, P2: CAP-02·CAP-03·CAP-09·CAP-12, P3: CAP-04·CAP-05·CAP-06, P4: CAP-07·CAP-08·CAP-09·CAP-12, P5: CAP-10·CAP-11이다. 같은 CAP가 여러 Phase에 걸치면 앞 단계의 공통 경로와 뒤 단계의 화면/owner 연결을 모두 확인해야 기능 인수를 닫는다.

## 3. Phase별 작업 분할

### AG-P0 — 착수 기준선과 공동 계약

1. 격리 테스트 DB에서 기존 백엔드 시험을 실행하고 실패/skip의 원인을 기록한다. 프런트 lint/build와 현재 대화·항목 도움·일정 직접 등록 경로를 확인한다. 기존 실패는 새 결함과 구분하며 관련 경로를 막으면 먼저 해결한다.
2. `runs → ai_chat → ai_context/ai_tools`, `docs → doc_assist/task_proposals`, `tasks`, `Chat/DocAssist/TaskProposals`의 실제 호출·저장 경계를 표시한다. 같은 저장소의 서비스는 기존 경계를 재사용하며 HTTP 계층을 임의로 추가하지 않는다.
3. scope/source manifest, task proposal의 대화 출처, 건별 등록 요청/결과, purpose 연결, continuation 연결의 저장 위치·revision·인덱스·기존 데이터 이행 방식을 정한다. 실제 공개 DTO는 이 단계의 구체 설계물이다.
4. 제품·옵션·거래처 정본, 목적 후보, 파일 지원표의 제공 위치를 확인한다. 이 저장소의 책임인지 다른 팀 API인지 근거와 함께 기록한다. 미제공은 해당 경로 의존성으로 남기고 기존 자료·일정 작업은 진행한다.

산출물은 기준선 결과, Phase별 작업 목록, 입력/출력·오류 계약, 데이터 이행 계획이다. P0에서 전체 제품을 재설계하거나 모든 J 계약의 실제 제공 완료를 기다리지 않는다. 소요 기간 추정은 이 결과와 실제 첫 변경 단위의 규모를 보고 갱신한다.

### AG-P1 — 모든 AI 입력에 같은 참고 규칙 적용

- **P1-a 서버:** 인증 주체·프로젝트·대화/항목을 소유 키로 scope와 출처를 저장한다. 프로젝트의 참고 설정과 요청별 적용 범위를 구분한다. 모델 도구 dispatch에도 같은 검사 규칙을 적용한다.
- **P1-b 입력:** 기본 prefix·이력·요약·도구 결과에 실제 사용 출처를 남기고 제외 정책을 적용한다. 기존 압축·계수 계약은 유지한다. 선택하지 않은 다른 대화를 자동 검색하지 않는다.
- **P1-c 화면:** 참고 범위 적용/취소·0개·사용 불가와 답변의 실제 출처를 연결한다. 재방문 후 선택을 복원하고 이미 생성한 답변은 다시 쓰지 않는다.

대표 확인: ‘포장 메모를 참고한 대화 → 메모 제외 → 후속 질문’에서 제외된 내용이 요약을 통해 재유입하지 않아야 한다. 기존 이력의 출처를 검증할 수 없으면 입력 사용을 제한하되 원문 기록을 삭제하지 않는다. 항목 화면의 전체 연결은 P4에서 완료한다.

### AG-P2 — 검색과 원문 읽기를 끝까지 연결

- **P2-a 기존 자료:** 현재 기록·문서·메모의 범위 제한 검색, 결과 페이지, 문서/항목 원문 구간 조회를 연결한다. 최근 20개·5개와 잘린 1,500자를 전체 검색 범위로 취급하지 않는다.
- **P2-b 일정:** 기존 일정 owner를 통해 날짜 구간·완료 상태·ID를 조회하고 task_id/revision·읽은 시점·남은 결과를 반환한다. 30개 입력 밖의 일정을 찾는다. 예정 날짜와 완료 처리 날짜를 구분한다.
- **P2-c 파일/화면:** 지정 파일의 실제 읽음·부분·미지원·실패를 노출하고 원본 이동을 연결한다. 업로드/출력 지원과 AI 읽기 지원은 별도다. 현재 지원 파서를 재사용하며 지원 형식을 무조건 추가하지 않는다.
- **P2-d 공동 자료:** 브랜드 공통 자료·제품·거래처는 확인된 owner와 adapter를 연결한다. 미제공 자료는 ‘자료 없음’ 대신 제공 상태를 구분한다. 실제 연결 없이 CAP-12나 관련 인수 사례를 완료로 표시하지 않는다.

대표 확인: ‘다음 주 미완료 일정과 준비할 자료를 찾아줘’에서 허용된 일정과 문서를 추가 호출로 읽고 출처와 함께 답한다. 읽기 예산·진전 없음·중단은 기존 run 한도에 합산한다. 새 검색마다 예산을 초기화하지 않는다.

### AG-P3 — 일반 채팅의 할 일 등록과 기록 저장

- **P3-a 후보:** 문서 전용 task proposal을 공통 후보 생성 로직으로 분리하고 일반 대화의 출처를 추가한다. 후보 생성은 업무 저장이 아니다.
- **P3-b 확인:** 여러 후보의 선택·제목/메모·날짜·목적 0개/복수 선택을 UI에서 확인한다. 날짜 미정 후보는 대화에 남기되 실제 등록은 날짜 확인 뒤 수행한다.
- **P3-c 저장:** 기존 제안 ID 중복 방지를 확장하고, 확인한 payload·요청 식별자·건별 결과와 조회 경로를 구현한다. 성공 건 유지·확정 실패만 재시도·미확인은 결과 조회 우선이다.
- **P3-d 재방문:** 원 대화와 같은 task_id를 연결하고 일정 화면에서 바뀐 현재 상태를 읽는다. 기록 후보도 실제 저장 결과·record ID·출처와 연결한다.

대표 확인: 후보 3개 중 2개를 수정해서 등록하고 한 건의 응답을 유실시킨 뒤 다시 열어도 일정이 중복되지 않아야 한다. 문서 완료와 할 일 실행 완료는 등록 성공으로 바뀌지 않는다. 이미 등록한 후보의 재전송은 일정 수정·복구 권한이 아니다.

### AG-P4 — 문서 작업의 맥락과 반영 대상

- **P4-a 항목 맥락:** 같은 항목의 이전 요청·필요한 답변과 관련 저장 항목을 읽는다. 항목별 참고 복원, 다른 항목의 미저장 글/도움 이력 격리, 파일 참고를 연결한다.
- **P4-b 답변 이동:** 답변 한 건·원 대화·제외 승계·제품 선택을 전용 문서 첫 요청으로 연결한다. 참고를 제거/교체할 수 있어야 한다. 자유형 문서의 `include_session` 기본값을 그대로 사용하지 않는다.
- **P4-c 반영:** 기존 doc/section·저장 revision·초안 revision 검사를 재사용하고 후보 비교→확인 반영→사용자 저장을 연결한다. 스크롤·대상 변경·늦은 응답에도 요청 당시 항목을 유지한다.

대표 확인: 채팅 답변에서 펀딩 문서를 열고 제품을 고른 뒤 참고를 수정하여 항목을 작성한다. 같은 항목에서 이어 묻고 다른 항목으로 이동해도 미저장 내용과 대화가 섞이지 않아야 한다. 실제 제품 정본이 미제공이면 P4-a는 진행할 수 있으나 P4-b의 제품 선택 인수를 닫지 않는다.

### AG-P5 — 검토와 실행 수명 마무리

- **P5-a 검토:** 저장 버전의 규칙 결과와 사용자의 직접 확인, 명시 AI 점검을 분리한다. 제공되지 않은 계산 규칙·가격 의미를 모델이 만들어 검사하지 않는다. AI 의견/실패만으로 완료 상태를 바꾸지 않는다.
- **P5-b continuation:** 원 run/부분 답변과 새 run을 연결한다. 기존 부분 답변을 보존하고 남은 내용만 생성하며 최신 권한·제외를 재검사한다.
- **P5-c 실행:** SSE 재연결·늦은 출력·중지와 원격 미확인의 구분·도구 이후 계수/사용량을 확인한다. 이 계약의 기존 회귀는 P1부터 유지하며 여기서 신규 경로를 통합한다.

DOC-POL-01은 핵심 원가의 최종 완료 분기에만 남긴다. 해당 정책이 미결이면 그 분기를 구현·인수 완료로 선언하지 않는다. 대화·작성·저장·검토 전 다운로드를 이 이유로 막지 않는다.

### AG-P6 — 실제 제품 인수

완전한 한 사용자 여정은 ‘참고 범위 설정 → 기록/일정 찾기 → 후보 확인 등록 → 답변으로 문서 시작 → 항목 대화/비교/저장 → 규칙 검사/AI 점검 → 중단·재접속·이어서 생성 → 재방문’이다. 같은 사용자 여러 탭·다른 프로젝트 격리·원본 변경/접근 불가·저장 응답 유실을 포함한다.

실제 모델은 모의 provider에서 확인할 수 없는 도구 선택·한국어 날짜 해석·근거 사용·지원 파일 입력을 검증한다. 테스트 데이터·호출 범위·사용량을 기록하고 실호출 결과와 모의 결과를 구분한다. 기본 규칙 검사 모델 0회는 실행 기록으로 확인한다.

기존 현재 저장본 Word/PDF 경로도 영향 여부를 회귀 확인한다. 변환기·폰트·저장소 등 실제 제공이 없는 인수는 skip 이유와 함께 남긴다. 데이터 이행·기존 대화/일정/문서 보존·복구 절차를 점검한 뒤 배포 준비 상태를 판단하며, 이 계획 자체가 배포 완료를 뜻하지 않는다.

## 4. 공동 계약을 닫는 시점

| 제공물 | 필요한 Phase | 제공 전 진행 가능한 일 | 완료를 주장할 수 없는 범위 |
| --- | --- | --- | --- |
| 범위 저장·자료 ID/권한/revision·출처 필터 | P1 | 논리/DTO 설계와 기존 서비스 조사 | 실제 입력 격리·출처 제외 |
| 기존 자료·일정 검색/원문·부분 결과 | P2 | owner 단위 구현과 계약 시험 | 모델 도구→실제 owner 조회 |
| 브랜드 공통/제품/옵션/거래처 정본 | P2-d·P4-b | 기존 자료 조회, 항목 자체 맥락 | 해당 자료 검색·제품 선택·등록 상태 판단 |
| 목적 후보·후보/확인 payload·중복/결과 조회 | P3 | 후보 생성과 확인 UI 준비 | 목적 유효성·건별 실제 등록/응답 유실 복구 |
| 파일 지원표·실제 모델·계수 | P2-c·P4·P6 | 기존 지원 파서·상태 처리·모의 provider 시험 | 실모델 원문/이미지 활용·실제 사용량 |
| 계산 규칙·문서 버전·완료 정책 | P5-a | 기존 결정으로 닫힌 검사와 명시 AI 점검 | 미제공 규칙·DOC-POL-01 최종 완료 분기 |

계약 시험용 대역은 테스트에서만 실제 제공과 구분해 사용한다. 제공되지 않은 owner를 임시 DB로 대체하고 제품 통합이 끝났다고 기록하지 않는다. 외부 계약이 사용자 동작을 바꾸면 그 한 가지 결정만 다시 다루며 기존 Grill을 반복하지 않는다.

## 5. 변경·검증 운영

작업 단위는 ‘한 사용자 동작 + 저장/API + 도구 + 화면 + 의미 있는 반례’로 나눈다. 각 단위에 CAP·ACAP·관련 AX-AC와 실제 검증 결과를 연결한다. Phase마다 큰 한 번의 커밋보다 독립 검토·복구 가능한 변경 단위를 권장한다. 필요 시 작업 브랜치는 `codex/` 접두사를 사용하되 지금은 브랜치를 생성하지 않는다.

저장 필드/인덱스는 기존 데이터를 읽을 수 있는 확장부터 적용한다. 새 필드가 없는 옛 대화·후보·일정의 의미와 이행을 시험한다. 기존 데이터의 자동 삭제·출처 추정·완료 상태 변경으로 이행을 대신하지 않는다. 새 도구·UI 진입의 활성화는 필요한 owner 계약과 실제 검증 상태에 맞춘다.

검증 순서는 변경에 맞는 단위/계약 시험 → 격리 MongoDB 통합 → 프런트 lint/build와 실제 UI 확인 → 대표 실모델 인수다. 초기 전체 기준선과 최종 통합 회귀 사이에는 영향받은 시험을 우선 실행한다. 기본 확인을 반복하는 테스트나 같은 검사를 이유 없이 반복하는 비용은 늘리지 않는다.

현재 저장소의 확인된 명령은 다음과 같다. **아래 명령은 계획이며 이번 작성에서 실행하지 않았다.**

```powershell
# 저장소 루트: 격리 test-mongo를 사용하는 백엔드 기준선
docker compose -f docker-compose.test.yml run --rm test-runner sh -c "pip install -q -r requirements-dev.txt && pytest -q"

# front 디렉터리: 현재 제공되는 프런트 검사
npm run lint
npm run build
```

`backend/tests/conftest.py`는 Mongo 호스트가 `test-mongo`가 아니면 시험을 중단하며 fixture는 테스트 데이터를 정리한다. 이 경계를 우회하지 않는다. 현재 프런트 package scripts에는 별도 자동 UI test 명령이 없으므로 lint/build를 UI 인수로 기록하지 않는다. 반복 가치가 큰 핵심 흐름만 자동화 대상으로 선정하고 실제 화면 검증을 남긴다.

각 Phase 종료 기록에는 변경 범위·실제 실행한 시험·실모델/UI 증거·미확인 제공물·데이터 영향·남은 결함을 남긴다. 상태는 설계 완료, 코드 연결 완료, 통합 검증 완료, 사용자 흐름 인수 완료를 구분한다. 인수가 미실행이거나 필수 owner가 미제공이면 그 Phase 전체를 완료로 표시하지 않는다.

## 6. 범위와 첫 실행 단위

AG-OPEN-01 기존 일정 변경을 채팅에서 승인하는 기능, AG-OPEN-02 반복 운영, 브랜드 전체 사업계획서·SNS·판매/재고/정산 쓰기는 이번 구현 범위에 자동 추가하지 않는다. 확정된 신규 후보·확인 등록과 기존 사용자 직접 관리 경로를 먼저 완성한다. 미결 정책은 해당 경로에만 영향을 준다.

첫 실행 단위는 **AG-P0의 현재 회귀 기준선 확보 → AG-P1-a/b의 scope·출처·후속 입력 제외 → P1-c의 최소 확인 UI**다. 첫 사용자 확인 시나리오는 ‘자료 한 개를 제외한 뒤 이어 물으면, 이전 답변/요약에서도 제외 정보가 다시 유입하지 않는다’로 고정한다. 이후 일정 조회(P2-b)를 첫 추가 도구의 대표 사례로 연결하고, 일반 채팅 등록(P3)으로 확장한다.

계획 작성 정적 검증만 수행한다. 한국어 문서는 UTF-8, 상대 링크와 Phase/CAP/ACAP 대응, 변경 범위를 확인한다. 지금 단계에서 구현 Phase나 실행 시험의 완료를 주장하지 않는다.
