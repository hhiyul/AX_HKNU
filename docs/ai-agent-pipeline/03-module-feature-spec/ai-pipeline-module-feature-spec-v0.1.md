# AI 파이프라인 모듈 기능명세 v0.1

작성일: 2026-11-06 · 상태: **책임·논리 계약·단위검증 기준 초안 / 물리 계약 검토 전 / 구현 없음**

## 1. 적용 기준과 이번 산출물

사용자 기능의 정본은 [사용자 기능명세 v0.2](../02-user-feature-spec/ai-pipeline-user-feature-spec-v0.2.md)입니다. UF-AI-01~16과 D-UF-001~108을 구현 관점으로 연결합니다. 이 문서는 제품 동작을 추가하거나 기존 보류를 승인하지 않습니다. 사용자 기능 전체는 v0.2 하나에서 읽을 수 있으며, 과거 Grill 문서를 기능 해석의 필수 입력으로 삼지 않습니다.

이번에는 M-01~08의 책임, 논리 입출력, 실패 처리, 검증 기준을 작성합니다. 아래 분해는 **검토할 책임 구분안**입니다. 여덟 패키지·서비스·에이전트를 만들거나 여섯 체크리스트에 여섯 에이전트를 배치한다는 결정이 아닙니다. 우선 단일 Python 백엔드에서 표현할 수 있는 경계를 검토하며, 프레임워크·멀티에이전트·작업 큐를 선행 요구로 추가하지 않습니다.

`합의`는 v0.2의 제품 제약, `설계안`은 이번 책임·포트 분해, `OPEN`은 다음 세션에서 정할 물리 계약입니다. 입력·출력 이름은 의미를 설명하는 용어이며 Python 타입명·JSON 키·DB 필드·HTTP 경로·상태 enum은 아직 아닙니다. 기존 [이관 대장](deferred-design-contracts.md)은 과거 설계 입력의 이력이고 현행 미정의 판정은 v0.2와 이 문서를 따릅니다.

## 2. 공통 실행·쓰기 경계

### 2.1 두 경로를 구분하는 설계안

**답변 경로:** 명시 전송 → M-05의 실행 접수 → M-01의 허용 자료 조회·입력 구성 → M-03의 모델/도구 루프(M-06 호출) → M-02의 평가·제안 검증 → M-08 전달 및 M-07 기본 대화 기록. 한 run은 한 답변 요청과 그 안의 도구 호출 전체입니다. 단순 질문·그 외 작업에도 여섯 CK 평가를 강제하지 않습니다.

**업무 저장 경로:** 사용자의 내용·범위 검토와 최종 UI 승인 → M-04의 권한·대상·참조/대상 버전·보류 검증 → M-07의 실제 저장 포트 → 항목별 실제 결과 → M-08 안내. 모델의 도구 호출·Chat 저장 문구만으로 이 경로를 승인하지 않습니다. CK는 항목별 `DRAFT`/`DECIDED` 의도가 필요하고, 추가 기록은 종류 없이 `[기록 저장]` 한 번입니다.

대화·캡슐·첨부·내부 실행 기록의 기본 저장과 사용자의 업무 콘텐츠 반영은 다른 권한입니다. 기본 대화 저장을 이유로 CK나 추가 기록에 자동 쓰기하지 않습니다. 반대로 모든 내부 기록에 업무 저장 UI 승인을 요구하지도 않습니다. 실제 저장 대상과 기본 보존 범위는 C-01·03에서 확인합니다.

| 정보 | 필요한 의미 | 현재 미정인 물리 표현 |
| --- | --- | --- |

서버가 판단할 권한·소유·버전·실제 반영 결과를 모델 출력으로 대신하지 않습니다. 전체 Projection이 실제 입력이면 전체 묶음을 참조로 추적하며 모델의 사후 설명이나 Chip 제거로 기존 제안의 검증 범위를 줄이지 않습니다.

## 3. M-01 컨텍스트·Projection·입력 예산

### 1. 목적·근거

접근 가능한 현재 프로젝트 자료와 실제 참조를 요청에 맞게 구성합니다. UF-AI-02·03·04·14, D-UF-006~009·026·065~073·097·099~101·103·105가 근거입니다. 프로젝트 섹션별 컨텍스트 관리를 이 책임에서 다룹니다.

### 2. 책임·경계

소유 프로젝트, 참조 프로젝트, 저장 기획, 사용자 발화, AI 이력/캡슐, 도구 자료, 미채택 제안을 구분합니다. 섹션별 조회·선택·조합·갱신과 출처/버전을 연결합니다. 실제 조회는 M-06/07 포트를 이용하고 입력 구성을 맡으며, 평가·업무 쓰기를 수행하지 않습니다. 추가 기록의 기본 자동 주입 범위는 OPEN-UF-16이므로 임의로 prefix에 편입하지 않습니다.

### 3. 입력·출력

입력은 요청과 소유 관계, 활성 자료·제외 규칙, 현재 저장 상태, 대화/캡슐, 실제 모델 한도·토큰 계산 수단입니다. 출력은 허용된 모델 입력, 실제 참조 묶음·누락/출처 정보, 전체 입력량 판정 또는 진행 불가 사유입니다. 일반 자료 선택과 명시 재검토 직전 Projection 재조회를 구분합니다.

### 4. 처리·상태·제약

- 파일/Chip은 run 시작 참고 범위를 고정합니다. 도중 제거는 활성 목록에 반영하되 이번 run의 후속 도구 호출에도 시작 범위를 유지하고 다음 run부터 제외합니다. 권한 상실·원문 삭제를 무시할 권한은 아닙니다.
- 제거/제외 자료 고유 정보는 이력·도구 결과·추출·캡슐·미채택 제안에서도 이후 자동 재사용하지 않습니다. A에 저장하거나 명시 채택한 가정은 A의 결정으로 유지합니다. 원문 보관과 실제 입력 허용 범위를 구분하며, 출처 필터링을 대화 압축과 혼동하지 않습니다.
- 지시문/도구 정의, 접근 가능한 프로젝트 상태·활성 파일/Chip의 비압축 prefix, 사용자 발화와 AI 이력, 현재 요청/도구 결과를 연결합니다. prefix와 첨부 내용은 자료이며 상위 실행 지시로 승격하지 않습니다.
- 입력 예산 = 실제 모델 한도 − 출력 8,000 − 여유 8,000토큰. AI 이력 100,000 초과 또는 전체 입력 초과 예상 시 **과거 AI 응답만** 압축합니다. 목표는 캡슐 4,000 + 최근 AI 원문 16,000토큰입니다. 사용자 발화·도구 자료 등 비AI 영역을 압축/임의 삭제하지 않습니다.
- 최초 압축 실패/부족 시 현재 요청에서 OpenAI 추가 압축을 **1회** 수행하고 검증·전체 재계산합니다. 수용 가능할 때 원래 요청을 계속합니다. 무한 재귀·자동 반복은 없습니다. 캐시는 원본 맥락/권한의 유일한 저장소가 아닙니다.

### 5. 예외·실패

비압축 영역만으로 예산을 넘거나 추가 압축 뒤에도 초과하면 모델 입력을 몰래 잘라 보내지 않고 이번 진행을 멈춰 원인·가능한 다음 행동을 전달합니다. 실패한 새 캡슐을 유효한 상태처럼 확정하지 않습니다. Projection 재조회 실패는 해당 평가 보류이며 일반 Chat/가능한 부분 도움까지 일괄 중단하는 사유는 아닙니다. 정확한 일반 Chip 재시도/최신성 결과는 제품 잔여입니다.

### 6. 인터페이스·데이터 계약

필요 포트는 허용 Projection/섹션 읽기, 자료 출처·제외 조회, 토큰 계산, 압축 요청, 현재 맥락 읽기/저장입니다. AI·사용자·도구 이력의 순서와 원문/캡슐 관계, 혼합 출처 응답의 필터링 단위는 MC-03·04·05에서 정합니다. 섹션별 선택을 이유로 필드별 업무 상태·버전을 만들지 않습니다.

### 7. 단위검증 수용 기준

UT-01: 제거된 B만의 근거가 캡슐/검색 입력으로 재유입되지 않고 A 채택 가정은 남음. UT-02: run 중 제거 전후 도구 입력은 시작 범위, 다음 run 입력은 제외 범위. UT-03: 압축 요청에 AI 과거 응답만 전달. UT-04: 정상·최초 실패·부족·추가 실패·비AI 초과를 가짜 토큰 계산기/압축기로 재현하고 추가 호출 최대 1회·전체 재계산·원본 상태 보존 확인. 숫자 경계는 초과 전/동일/초과를 구분합니다.

### 8. OPEN·다음 결정

MC-03~05: Projection 필드/섹션·실제 참조 버전, 출처 혼합 자료의 제외 구현, 각 Provider의 토큰 계산/이미지 예산, 압축 모델·요청 입력 한도·캡슐 검증. 추가 기록 자동 참조는 제품 결정 선행입니다.

## 4. M-02 기획·가설·평가·편집 후보

### 1. 목적·근거

여섯 CK의 기획 가설·평가와 사용자 편집/최신 결정을 구분합니다. UF-AI-06·08·09·16, D-UF-010~025·034~040·046~054·060·061·076~080·108이 근거입니다. 세부 완료 기준은 v0.2의 UF-AI-06을 그대로 입력으로 삼습니다.

### 2. 책임·경계

후보/진행 가설, 기준별 결과·근거·남은 미정, 저장 기획과 별도인 변경 후보를 표현·검증합니다. 선택 부분 가져오기와 기존 편집 보호에 필요한 정보를 제공합니다. 모델 호출은 M-03, 저장 검증은 M-04, UI 편집은 M-08입니다. 도메인 평가 완료를 저장 권한으로 사용하지 않습니다.

### 3. 입력·출력

입력은 CK별 논리 기준, 대화에서 확인한 정보·가정, 현재 진행 대상/후보, 저장 내용/상태, 사용자 편집·선택 범위입니다. 출력은 평가 결과·근거·보류 사유, 편집과 분리된 후보, 사용자 선택을 반영한 작업안입니다. 추가 기록은 제목·본문·추가/지정 수정 범위이며 CK 평가 구조에 강제로 넣지 않습니다.

### 4. 처리·상태·제약

- 완료 기준은 실제 검증이 아닌 설명 가능한 기획 가설입니다. CK-01 판매 대상/범위, CK-02 고객·목적·접점/이유 연결, CK-03 고객 목적과 연결된 선택 이유, CK-04 판매 단위 핵심 구성/수량, CK-05 기획 가격/중요 비용과 가정, CK-06 제작 규모/일정/제작·조달 방식 및 명백한 충돌을 다룹니다. 이것은 필수 정보의 요약이며 각 CK의 전체 완료 조건을 대체하지 않습니다.
- 실제 진행 대상으로 정한 가설만 전체 완료 판정에 포함합니다. 미선택 비교 후보의 미정은 단독 차단 사유가 아닙니다. 진행 대상이 없다는 이유로 빈 평가를 전체 완료로 만들지 않습니다.
- 새 정보가 영향을 주는 기준과 남은 보류를 같은 응답에서 갱신합니다. 이미 답한 내용을 반복 질문하지 않으며 중요한 변화/사용자 요청으로 필요성이 달라질 때 이유를 설명합니다.
- 새 제안은 별도 후보이고 기존 미저장 편집과 최신 사용자 결정을 덮어쓰지 않습니다. 가져오기는 명시 선택 범위만 적용하며 다른 값 자동 수정·자동 저장을 하지 않습니다.
- 추가 기록은 프로젝트당 한 문서의 제목·본문입니다. 별도 메모 엔티티 관리·태그·우선순위·완료 상태, `UNSET/DRAFT/DECIDED`를 추가하지 않습니다.

### 5. 예외·실패

미정 비용을 0/임의 값으로 채우거나 실제 시장 반응·견적·계약을 기획 완료의 필수로 요구하지 않습니다. 설명된 중요 비용 미정·명백한 제작 충돌 등 해당 기준에 맞게 완료를 보류하고 가능한 부분 도움을 남깁니다. P-01의 전제 불일치 부분 가져오기는 양쪽 대안 모두 보류이며 적용/차단 정책을 코드 기본값으로 선택하지 않습니다.

### 6. 인터페이스·데이터 계약

기준 식별·결과·근거·가정·불확실성, 가설과 진행 대상, 저장 내용/상태, 후보와 편집 선택 범위의 논리 구조가 필요합니다. 점수제·필드별 업무 상태를 새로 도입하지 않습니다. 추가 기록의 지정 위치 식별 방식은 한 문서 조건을 유지하며 MC-06·09에서 정합니다.

## 5. M-03 모델·평가·제안 에이전트 루프

### 1. 목적·근거

### 2. 책임·경계

M-05가 접수한 실행에서 M-01의 입력을 사용해 M-06 모델/도구를 호출하고 결과를 검증·연결합니다. M-02의 기획 규칙과 M-08의 전달 계약을 따릅니다. 모델에 프로젝트 쓰기 권한을 부여하지 않으며 대화 기록 저장은 M-07과 구분합니다.

### 3. 입력·출력

입력은 요청 목적·명확한 검토 대상, 허용된 입력/도구 목록, 현재 평가/편집 기준, 호출·시간/반복 제한입니다. 출력은 실제 답변, 관련 평가·후보, 사용/누락 근거, 실행 종료/부분 결과·보류 사유입니다. 모든 응답에 제안 또는 전체 CK 평가를 강제하지 않습니다.

### 4. 처리·상태·제약

입력 준비 → 모델 요청 → 응답/허용 도구 요청 구분 → 도구 인자·권한 검증 → 실제 도구 결과 반영 → 필요 시 다음 모델 호출 → 출력 검증 → 결과 전달의 설계안입니다. 실제 상태명은 미정입니다. 재검토 대상이 명확하면 실행하고 모호한 부분만 확인합니다. 평가 직전 Projection 재조회, 시작 자료로 완료·완료 시 변경 확인을 연결합니다.

지시문은 D-UF-100의 여섯 행동을 구현합니다: 목적/범위·작은 다음 행동, 사실/가정/미정 구분, 관련 CK 기준, 최소 변경/UI 반영, 허용 자료/도구와 자료의 비지시성, 간결한 실제 결과/완료 안내. 정확한 프롬프트 문구는 MC-06에서 작성하고 대표 사례로 검토합니다.

보완 검색은 이미 허용된 범위에서만 진행하며 진전 없음 또는 한도에 도달하면 종료합니다. 일반 도구 실패 보완을 Projection의 명시 재시도 요구나 쓰기의 자동 재전송 금지와 혼동하지 않습니다.

### 5. 예외·실패

미등록 도구·형식 불량·허용 범위 밖 인자는 실행하지 않습니다. 모델의 “저장했다”는 문장을 실제 성공으로 신뢰하지 않습니다. 제한/실패 시 확인한 부분과 필요한 보류를 전달하고 무한 루프·허위 도구 성공을 만들지 않습니다. 오류 후 모델 재호출 횟수·진전 판정 방식은 미정이며 새로운 무제한 재시도를 추가하지 않습니다.

### 6. 인터페이스·데이터 계약

모델 요청/응답, 도구 요청과 실제 결과의 연결, 출력 검증·사용 근거, 종료 사유가 필요합니다. 모델 네이티브 tool calling 또는 별도 파싱 중 무엇을 쓸지, 동시 도구 실행 여부·호출 한도·timeout은 MC-02·06·07에서 정합니다. 기본 루프를 위한 프레임워크 설치는 아직 결정하지 않습니다.

### 7. 단위검증 수용 기준

## 6. M-04 최종 반영·버전·충돌

### 1. 목적·근거

사용자가 승인한 변경만 올바른 프로젝트·범위에 반영합니다. UF-AI-09~13·16, D-UF-007~009·034·040~045·055~061·074~075·106~108이 근거입니다.

### 2. 책임·경계

### 3. 입력·출력

입력은 승인한 내용/범위, CK별 저장 종류 또는 추가 기록 승인, 대상·참조 기준과 현재 서버 값입니다. 출력은 항목별 검증 결과와 실제 반영 결과/보류·충돌·미확인입니다. 문서 추가/부분 수정과 CK의 저장/비우기를 구분합니다.

### 4. 처리·상태·제약

- 승인 전 쓰기 없음. 편집 후 내용이 달라지면 갱신 내용을 대상으로 최종 UI 승인이 필요합니다. 승인 결합 방식은 MC-08이며 별도 다단계 승인 UX를 만들지 않습니다.
- 선택 범위 밖 내용 유지. CK의 내용+상태는 항목 단위 한 버전 묶음입니다. DRAFT 재저장은 DRAFT 유지, 명시적 재확정은 중간 초안 저장 없이 가능합니다. 전체 비우기는 사전 영향 안내 후 검증·실제 반영 확인 시 UNSET입니다.
- 내부 평가 미완료만으로 사용자 확정을 거절하지 않습니다. 권한/버전/참조 변경에 따른 저장 보류 등 기존 검증은 유지합니다.
- 여러 CK는 종류를 항목별 선택해 함께 요청할 수 있으며 검증 통과·보류 없는 항목만 반영합니다. 실패 때문에 이미 확인된 다른 성공을 다시 저장하지 않습니다.
- 참조 묶음과 쓰기 대상 버전을 따로 검증합니다. 완료 후 저장까지의 참조 유효성 확인·조건부 쓰기의 경합 처리는 MC-08·09에서 닫습니다.
- 추가 기록은 프로젝트 한 문서의 승인 범위만 누적/수정합니다. CK 내용·상태 불변이며 초안 종류로 대체하지 않습니다.

### 5. 예외·실패

충돌이 확인되면 해당 변경의 미반영·사유·다음 행동을 M-08로 전달하고 사용자 선택을 기다립니다. 자동 병합·덮어쓰기·재저장·재검토는 없습니다. 참조 변경이 확인된 제안은 저장 보류 후 명시적 재요청을 기다립니다. 결과 유실은 실패/미반영으로 단정하지 않고 M-07의 요청 결과 확인으로 넘깁니다.

### 6. 인터페이스·데이터 계약

필요 포트는 현재 권한/소유 검증, 실제 참조/대상 버전 조회, 조건부 변경, 요청별 결과 확인입니다. MongoDB 컬렉션·트랜잭션·수정 연산·버전 토큰을 아직 선택하지 않았습니다. 서버가 결과 확인 수단을 제공하지 않으면 미반영 종료나 안전한 재전송 가능성을 만들어낼 수 없습니다.

### 8. OPEN·다음 결정

## 7. M-05 답변 실행·동시 요청·종료

### 1. 목적·근거

명시 요청과 실제 실행 수명을 연결합니다. UF-AI-01·05·13, D-UF-027~030·098·103~107이 근거입니다.

### 2. 책임·경계

한 Chat의 답변 실행 접수·종료, 명시적 평가 재시도, 중단 요청/실제 결과를 연결합니다. 업무 쓰기 결과는 답변 run과 별도 식별하여 M-04·07이 확인합니다. 답변 동시성 규칙을 이유로 모든 조회·독립 저장 작업까지 일괄 금지하지 않습니다.

### 3. 입력·출력

입력은 사용자 전송, Chat 관계, 현재 답변 진행 여부, 중단·명시 재시도 요청과 실제 하위 결과입니다. 출력은 접수/전송 불가·진행·종료/부분 결과, 보류 대상·재시도 가능 행동입니다. 미전송 텍스트는 실행 요청이 아닙니다.

### 4. 처리·상태·제약

한 Chat은 진행 중 답변 하나만 허용합니다. 사용자는 다음 질문을 작성할 수 있지만 실제 전송은 현재 답변 종료 뒤 직접 합니다. 큐·예약·종료 후 자동 전송은 없습니다. 동시 접수의 서버 방어 방식과 프로세스 간 보장은 MC-07·10에서 정합니다.

재선택 평가 직전 Projection 실패 시 그 평가를 보류합니다. 사용자 명시 재시도 때만 다시 조회하고 성공·동일/명확 대상이면 같은 응답에서 전체 기준/남은 보류를 재평가합니다. 진행 대상에서 빠진 가설의 보류 평가는 종료하고, 재선택 시 현재 자료로 새로 평가합니다.

중단 요청과 Provider/도구의 실제 종료를 구분합니다. 파일/Chip 제거가 run 중단 또는 새 답변 생성 요청이 되지 않습니다. 서비스 재시작 후 중단 작업 자동 재개/복구를 추가하지 않습니다.

### 5. 예외·실패

## 8. M-06 LLM·MCP·파일·계산 어댑터

## 10. M-08 UI 경계·결과 전달·내보내기

짧은 평가 변화·남은 보류를 기본 안내하고 상세 기준은 요청 시 제공합니다. 확인된 다른 CK 영향은 결과와 함께 짧게 알리며 후속 검토는 명시 요청 후입니다. 충돌은 항목·미반영·사유·다음 행동을 명확히 보여 사용자 선택을 기다립니다. 일반 저장 이력은 편집 문서로 열며 별도 전후 비교 화면을 강제하지 않습니다.

CK의 항목별 초안/확정 의도와 추가 기록의 단일 `[기록 저장]` 승인을 구분합니다. 미전송/미저장 편집의 자동 임시 보관은 브라우저 인메모리이며 새로고침·탭 종료 이후 복원 보장은 없습니다. 복귀만으로 전송/AI 실행/저장하지 않습니다.

## 12. 이후 구현·단위검증의 진행 기준

1. 현재 사용자 정본과 작업 트리, 백엔드·Figma를 확인하고 이번에 다룰 M/MC 범위를 정합니다. 필요한 제품/공동 계약을 먼저 닫습니다.
2. 해당 모듈의 정확한 Python 입출력·예외·포트·상태·fixture·UT 기대 결과를 이 문서에 구체화합니다. 의존 시스템이 미정이면 가짜 포트와 실제 미정의 경계를 밝힙니다.
3. **별도의 구현 승인 후에만** Python 코드와 단위시험을 작성합니다. 기본 단위시험은 가짜 Provider/저장소/시계/토큰 계산기·고정 작은 자료로 결정론적으로 수행하며 외부 네트워크·Atlas·키가 필요하지 않게 합니다.
4. 실제 어댑터 코드까지 시험하되 전송 경계만 가짜로 두어 payload·결과/오류 파싱을 검사합니다. 포트 인터페이스만 검사하고 실제 호출 경로를 생략한 것을 어댑터 검증으로 부르지 않습니다.
5. 루프/파이프라인은 가짜 포트 조합으로 정책·순서·상태·실패 전파를 검증합니다. 이는 실제 DB/LLM/게이트웨이 통합 또는 자연어 품질 보장이 아닙니다.
6. 실제 LLM 연결 확인은 모델/키·호출 범위/비용을 확인한 별도 실호출입니다. Docker/Atlas·게이트웨이·브라우저·통합/E2E 검증과도 별도로 기록합니다.

현 시점 증거는 문서·소스·Figma 읽기뿐입니다. Python 구현, 단위시험, LLM 실호출, MongoDB 연결, 통합/E2E 검증은 모두 **NOT_RUN**입니다. 다음 세션 명세가 닫혔다고 인정하려면 선택한 모듈의 입출력·소유·정상/예외·쓰기 경계·구현 전제·UT 기대 결과가 모순 없이 읽혀야 하며 OPEN인 물리 계약은 명시적으로 남아 있어야 합니다.
