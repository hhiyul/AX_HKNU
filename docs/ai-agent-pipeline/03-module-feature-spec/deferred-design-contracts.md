# 모듈 설계 이관 대장

상태: **기존 구현 제약·후속 미정 목록 / 모듈 명세 작성 전 / 구현 착수 아님** · 기준일: 2026-10-30

연결: [사용자 기능 정리·완료 계획](../02-user-feature-spec/user-feature-closure-plan.md) · [사용자 기능명세](../02-user-feature-spec/ai-pipeline-user-feature-spec-v0.1.md) · [기존 결정 기록](../02-user-feature-spec/open-contracts.md) · [세부 참조본](../02-user-feature-spec/agreement-details-v0.1.md)

## 1. 이관의 의미

사용자에게 보일 동작·결과를 먼저 완성하고, 그 동작을 구현할 미정 계약은 여기서 추적합니다. 이 문서는 에이전트 수·프레임워크·저장 구조·실행 상태를 새로 정하지 않습니다. 여섯 체크리스트를 여섯 에이전트로 대응시키지도 않습니다.

D-UF-001~061은 모두 유지합니다. 조회 시점·버전 경계·재시도·사용자 최종 반영 등 이미 구체적으로 정한 내용은 이관 후에도 구현 제약이며, 설계자가 임의로 다시 선택할 수 있는 대안이 아닙니다. 기능 초안·미정 후보는 기존 결정과 구분합니다. 정확한 이유·대안·수용 반례는 결정 기록을 우선 참조합니다.

## 2. 먼저 필요한 사용자·공통 계약

- 정리·완료 계획의 U-01~05: 대표 흐름, 여섯 항목의 사용자 기준, 제안·수정·선택·저장·확정·재편집과 항목 간 영향.
- U-06~09: 실패·충돌·미확인 결과, 자료 사용, 복구·삭제·내보내기, 모델 설정·이용 제한의 사용자 의미.
- C-01~03: 팀원 담당 시스템의 권한·공통 데이터·삭제, 금액의 사업 기준, 제공할 모델·도구·첨부·보존 범위.

이 선행 항목의 빈칸을 모듈의 기본값·API 설계·데모 상수로 대신 채우지 않습니다. 사용자에게 보장할 결과가 달라지면 사용자 기능·공통 계약으로 되돌려 확인해야 합니다.

### 3.1 프로젝트 섹션별 컨텍스트 관리

2026-11-02 사용자가 프로젝트 섹션별 컨텍스트 관리는 모듈 기능명세에서 다룰 항목으로 추가 기록하도록 요청했습니다. 아래는 후속 명세에서 다룰 범위이며 현재 자료 구조·알고리즘·실행 계약을 확정하거나 구현하는 작업이 아닙니다.

- **섹션의 경계와 정보 구분:** 실제 프로젝트 섹션의 분류·식별과 각 섹션의 저장 정보·상태·내부 평가·미저장 제안·최신 사용자 결정·참조 근거를 어떻게 구분해 조립할지. 시스템 명세를 확인하기 전에 섹션을 여섯 체크리스트나 여섯 에이전트에 일대일 대응시키지 않습니다.
- **요청별 선택·조합:** 사용자에게 허용받은 프로젝트/Chip 참조 범위 안에서 어떤 섹션을 조회·요약·연결해 모델 입력에 넣을지, 섹션 간 관련 정보·중요한 가정·누락 정보를 어떻게 함께 다룰지. 실제 정보 선택·입력 예산·전달 형식은 후속 설계입니다.
- **출처·최신성·버전:** 전달한 정보의 출처·기준 시점·실제 참조 묶음과 대상 버전을 연결하고 섹션 변경 시 어떤 자료를 다시 구성·검증할지. 기존 체크리스트 단위 버전과 D-UF-008의 실제 참조 범위를 유지하고 섹션 구분을 이유로 필드별 독립 버전을 도입하거나 검증 범위를 축소하지 않습니다.
- **Chip·권한·해제 연계:** Chip의 자원 식별·권한·연결 상태와 실제 조회·모델 입력의 관계, 자료 해제·삭제·권한 변경·조회 실패의 전달 방식. 사용자가 언제부터 무엇을 참고하도록 선택·해제하는지는 먼저 사용자 기능 P0에서 결정하고 내부 구현으로 대신 정하지 않습니다.
- **최신 결정과 저장 경계:** 과거 섹션 요약이나 늦게 도착한 자료가 최신 사용자 결정을 덮어쓰지 않도록 연결합니다. 최신 결정의 변경 요약·사용자 편집안 반영 선택과 저장 종류 유지·사용자 최종 반영(D-UF-060·061)을 지키며, 컨텍스트 갱신이 업무 체크리스트의 자동 저장 권한이 되지 않도록 합니다.

선행 사용자 계약은 [웹 검색·프로젝트 컨텍스트 Chip P0 질문지](../02-user-feature-spec/context-and-web-grill.md)의 CHIP-01~03·WEB-02와 U-07, C-01·03입니다. 검색 MCP 연결·도구 입출력은 M-06, 루프·실행은 M-03·05와 연계하되 검색 시작 조건·참조 허용의 사용자 의미를 여기서 먼저 정하지 않습니다.

## 4. 잘못된 이관을 막는 기준

| 먼저 사용자·공통 계약에서 정할 것 | 그다음 이관할 구현 문제 |
| --- | --- |
| 여러 항목 중 일부 저장만 성공해도 되는지와 사용자 결과 | 원자성·부분 처리·조건부 쓰기의 실제 방식 |
| 가격에 수수료·배송비 등을 포함하는지, 어떤 금액을 보여주는지 | 선택한 산식을 구현하는 도구 입출력·단위·정밀도. 반올림이 결과 금액을 바꾸면 그 사업 기준도 먼저 확인 |
| 어떤 자료를 사용하도록 선택·허용·해제하는지 | 실제 조회 범위·프롬프트/Provider 입력·참조 추적 구조 |
| 재방문하면 무엇을 복구할 수 있고 삭제하면 무엇이 사라지는지 | 영속 테이블·이벤트·보존 집행·복구 프로토콜 |
| 사용자 취소·실패·재시도·보류 종료가 의미하는 결과 | 실행 상태 머신·큐·동시성·취소 전파·재시도 구현 |

사용자 기능명세의 완료와 모듈의 구현 가능성·구현 완료·실서비스 검증은 별개입니다. 이 대장을 작성한 것만으로 위 미정 계약을 닫거나 구현을 승인한 것으로 보지 않습니다. 미정인 제한값·스키마·성공 증거를 임의로 만들지 않습니다.

## 5. 후속 설계 시 추적 방법

각 실제 모듈에는 사용자 기능 UF ID·사용자 쟁점 U/C ID·기존 결정 D ID·관련 OPEN-UF·구현 검증 기준을 연결합니다. 기존 D 기록의 의미를 변경해야 하는 제안은 새 제품 결정과 구분해 검토하며, 이관을 이유로 기존 합의를 덮어쓰지 않습니다.

현재는 모듈 책임 분해·에이전트 수·프레임워크·API·DB·한도·루프 구현을 새로 확정하지 않습니다. [사용자 기능 정리·완료 계획](../02-user-feature-spec/user-feature-closure-plan.md)의 우선순위에 맞춰 선행 항목을 정리한 뒤 설계합니다.
