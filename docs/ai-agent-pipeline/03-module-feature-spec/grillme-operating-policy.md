## 1. 근거와 적용 경계

현행 사용자 동작은 작업 트리의 [사용자 기능명세 v0.2](../02-user-feature-spec/ai-pipeline-user-feature-spec-v0.2.md) 하나를 기준으로 합니다. UF-AI-01~16·D-UF-001~109와 말미의 제품 보류·공동 계약을 우선하며, 원격 커밋·과거 Grill·인계 스냅샷으로 미커밋 결정을 대체하지 않습니다. [모듈 기능명세](ai-pipeline-module-feature-spec-v0.1.md)는 이 제품 계약을 구현 가능한 계약으로 내립니다.

이 문서는 사용자 기능 본문을 복제하지 않습니다. **2026-11-06 사용자 지시로 현재 Grill 단계에서는 채택 결과를 [Grill 기능 결정표](grill-feature-decisions.md)에 먼저 기록하고, 사용자 정본 통합과 모듈 명세 작성은 그 이후에 진행합니다.** 여기에는 질문 상태와 결정 위치만 연결합니다. GQ 번호는 인터뷰 추적 ID이며 D-UF·P-01·C·MC의 번호나 업무 상태를 대신하지 않습니다.

현재 합의한 프로젝트 선행·프로젝트:Chat 1:1·고정 저장 대상, UI 최종 승인, 평가/저장 분리, 자료 제거/검색 끄기의 서로 다른 시점, AI 전용 압축·입력 예산·추가 압축 1회는 질문의 전제로 유지합니다. 여덟 M은 책임 구분안이고 에이전트 수의 채택이 아닙니다. Python 3.11·팀원 API를 호출하는 Python 어댑터 경계도 확인된 기반입니다. 이를 다시 선택하게 묻지 않습니다.

기존 보류를 바꾸거나 확장할 필요가 드러나면 영향을 받는 계약과 이유를 먼저 밝히고 그 범위만 질문합니다. 내부 설계 선택·추천·사용자의 침묵을 제품 승인으로 해석하지 않습니다.

## 2. 기둥질문·가지질문·물리 계약의 구분

| 구분 | 판별 기준 | 예시 | 다루는 시점 |
| --- | --- | --- | --- |
| 기둥질문 | 제품의 역할·도움의 범위·사용자 통제·완료 기대를 바꾸며 여러 후속 선택을 좌우 | 추가 기록을 이후 AI가 알아서 참고해도 되는가 | 첫 방향 확인 순회 |
| 가지질문 | 특정 기둥의 방향을 실제 정상·예외 상황에서 일관되게 적용하는 데 필요 | 자동 참고라면 오래된 아이디어와 현재 기획이 다를 때 어떻게 설명하는가 | 해당 기둥의 방향 확인 후 |
| 공동 제품·제공 약속 | 사용자가 기대할 접근·보존·계산 의미 등을 팀원과 함께 정해야 함 | 어떤 기록을 재방문 때 제공할지, 기획 계산에 어떤 비용이 포함되는지 | 관련 제품 방향을 정할 때 함께 확인. 팀원 답이 없으면 담당·영향 범위를 남김 |
| 물리 계약 | 정해진 사용자 결과를 구현하는 정확한 형식·호출·한도·데이터 연결 | API 경로·JSON 필드·버전 토큰·타임아웃·파서·시험 명령 | 제품 방향과 필요한 가지의 결과가 정해진 뒤 MC로 구체화 |

질문의 크기는 기술 용어의 유무로 정하지 않습니다. 저장 보류·결과 노출·재요청 조건을 바꾸는 선택은 사용자 결과의 결정입니다. 반대로 같은 사용자 결과를 유지하는 내부 필드명은 제품 질문으로 올리지 않습니다. C-01~03 전체를 물리 계약으로 미루지도 않습니다.

## 3. 진행 순서와 대화 행동

1. **현재 위치 확인:** 해당 기능 정본·최근 결정·질문 상태를 읽고 미응답과 실제 보류를 구별합니다. 작업 재개 시 브랜치·HEAD·작업 트리부터 확인하며 자동 pull/merge/reset은 하지 않습니다.
2. **기둥 먼저 순회:** 아래 GQ-01~05에서 큰 방향을 차례로 확인합니다. 한 기둥의 모든 가지·API 세부를 끝내고 다음 기둥으로 넘어가는 방식은 피합니다. 다음 기둥의 답을 좌우하는 필수 가지는 먼저 물을 수 있고, 그 의존 이유를 설명합니다.
3. **한 번에 한 중심 질문:** 기본은 기둥질문 하나입니다. 분리할 수 없는 선택만 함께 묻고, 여러 모듈의 기술 설문을 한꺼번에 제시하지 않습니다. 사용자가 다른 기둥을 먼저 지정하면 의존 관계를 확인해 순서를 바꿉니다.
4. **상황부터 설명:** 현재 사용자 목표·보유 자료·이미 한 행동을 구체적으로 제시합니다. 정상 상황을 설명하기 전에 실패·충돌 처리로 선택을 좁히지 않습니다.
5. **대안과 대가 제시:** 실제로 다른 사용자 결과를 주는 2~3개 대안을 비교합니다. 사용자 제3안·조건부 조합도 허용합니다. 추천에는 근거와 감수할 단점을 함께 적고, 추천을 채택된 결정처럼 쓰지 않습니다.
6. **답변을 비판적으로 검토:** 좋은 설계는 어떤 문제를 해결하는지 구체적으로 평가합니다. 모순·불필요한 사용자 부담·오해 가능성은 실제 발생 상황과 함께 지적하고 대안을 냅니다. 막연한 칭찬이나 같은 질문의 반복으로 끝내지 않습니다.
7. **정상·반례로 확인:** 선택한 방향에 정상 사례와 최소 한 개 반례를 적용합니다. 기존 승인·권한·저장 보류·출처 계약과 충돌하면 해당 부분으로 되돌아갑니다. 이미 명확한 답에는 같은 승인을 재요구하지 않고, 모호하거나 달라진 부분만 질문합니다.
8. **방향과 닫힘을 구분:** 기둥의 방향이 정해져도 중요한 가지·공동 약속이 남으면 전체 닫힘으로 표시하지 않습니다. 영향받지 않는 설계는 계속 진행합니다.
9. **제품 가지 다음 물리 계약:** 기둥을 순회한 뒤 의존성과 구현 영향이 큰 가지부터 정리합니다. 이후 필요한 C 제공물과 MC를 연결하며, 팀원 API 미제공을 임의 경로·DB 직접 접근·가짜 성공으로 채우지 않습니다.
10. **매 응답의 연결:** 이번에 정한 것, 남은 이유/담당, 다음 질문을 짧게 연결합니다. 답변으로 새로운 모순이 발견되면 닫힌 척하지 말고 추가 질문으로 결론에 수렴합니다.

질문은 아래 형식을 기본으로 합니다.

| 항목 | 반드시 담을 내용 |
| --- | --- |
| 질문 ID·의존 | 기둥/가지, 선행 결정, 관련 UF·OPEN/P/C·M |
| 현재 합의 | 이번에 유지할 기준과 실제로 선택할 부분 |
| 구체 상황 | 사용자 요청·현재 자료/편집·발생 사건. 숫자/문구가 합성 예시라면 구별 |
| 중심 질문 | 이번 답변으로 달라질 사용자 행동·결과 한 가지 |
| 대안·추천 | 2~3개 경로, 각각 얻는 것/잃는 것, 추천 이유·약점 |
| 반례·수용 | 선택이 모호해질 사례와 결정 후 명세에 적을 관찰 가능한 기대 결과 |

## 4. 기둥질문 지도

직전 대화의 일곱 주제를 다섯 기둥으로 묶습니다. 중단 결과는 GQ-03의 가지, 추가 기록 내보내기는 GQ-01의 가지입니다. 채택 여부는 각 행의 현재 상태와 [Grill 기능 결정표](grill-feature-decisions.md)에서 구별하며, 채택 표시가 없는 상황·대안은 질문 준비안입니다.

| 순서·ID | 기둥질문과 구체 상황 | 결정해야 할 방향·연결 | 현재 상태 |
| --- | --- | --- | --- |
| 1 · GQ-01 | **추가 기록은 이후 AI가 알아서 참고하는 프로젝트 지식인가?** 한 문서에 안내문·구매 후기·미검증 아이디어를 저장한 뒤, 기록 지정 없이 고객/가격 검토를 요청 | B안 관련 기록 자동 탐색·참고와 추가 호출을 통한 점진적 범위 확대 채택. OPEN-UF-16·UF-AI-16·14, M-01·02·06·07·08 | 방향 확인. [GD-001·002](grill-feature-decisions.md) 선기록, 관련 가지·정본 통합·모듈 반영 후속 |
| 2 · GQ-02 | **최초 계산 자동화는 사용자의 어떤 판단까지 도와야 하는가?** 구성·가격 가정과 일부 미정 비용으로 진행 여부나 조건 변경을 검토 | 현재 조건의 부분 계산 / 목표에 필요한 조건 역산 등 사용자가 얻어야 할 판단을 먼저 구체화. OPEN-UF-15·C-02·UF-AI-06·07, M-02·03·06·08 | 공동 확인 대기. 기초 계산/목표 역산 둘 다 미채택, 디자인팀 선행 논의 유지 |
| 3 · GQ-03 | **한 요청에서 어디까지 검토한 뒤 결과를 돌려주는가?** 쓸 수 있는 1차안은 있지만 추가 사례/비교로 중요한 판단을 더 개선할 여지가 있음 | 판단·제안 요청은 필요한 근거와 대안을 비교할 수 있을 만큼 같은 요청 안에서 탐색하는 B안 채택. UF-AI-04~08·13, M-03·05·06·08 | 방향 확인. [GD-003](grill-feature-decisions.md) 선기록. 충분성·진전 없음·일반 중단 결과의 가지는 후속 |
| 4 · GQ-04 | **편집 중 알려진 전제 불일치를 어느 단계까지 허용하는가?** 현재 편집은 카드 3장/1,500원, 새 후보는 5장/2,500원이고 비용만 가져오려 함 | 명확한 사용자 선택 부분을 적용하고 전제 차이·영향을 즉시 안내하는 A안 채택. UF-AI-09·08·12, M-02·04·08 | 방향 확인. [GD-004](grill-feature-decisions.md)로 P-01 사용자 경로 결정, 구체 UX·정본 통합·모듈 반영 후속 |
| 5 · GQ-05 | **참고 자료를 이용할 수 없을 때 사용자는 어떻게 작업을 이어가는가?** A Chat에 첨부한 B Chip의 읽기 실패, 재선택, 원본 삭제·권한 변화 | GD-005의 접근 허용이 확인된 일반 Chip 일시 읽기 실패 자율 보완 A안 채택. OPEN-UF-03·UF-AI-02·13·14·C-01·03, M-01·05·06·07·08 | 방향 확인. 일반 Chip 재선택 최신성·삭제/권한 변화의 가지는 남음. 파일 일시 실패의 기존 합의 유지 |

GQ-03은 기존 자동 검색·보완 검색 허용을 다시 묻는 질문이 아닙니다. 추가 검토가 주는 가치와 사용자에게 돌려줄 결과의 깊이를 구체화합니다. 여섯 CK의 완료 기준, 매 답변 전체 평가를 강제하지 않는 합의, 명시 요청이 필요한 저장 기획 후속 검토는 유지합니다.

## 5. 가지질문 트리

각 가지는 부모 기둥의 답에 따라 필요한 경우에만 묻습니다. 아직 질문하지 않은 대안을 채택된 기능으로 사용하지 않습니다.

| 부모 → 가지 ID | 구체화할 사용자 결과 | 진행 조건·유지 경계 |
| --- | --- | --- |
| GQ-01 → GQ-01-01 | 자동 참고를 택한다면 어떤 요청에서 어느 범위의 기록을 읽고, 실제 참고/누락을 어떻게 알리는가 | GD-001·002의 관련 기록 자동·점진 탐색 채택. 정본 G-11의 실제 읽기 범위·중요 누락/판단 영향 안내 적용. 이를 재투표하지 않으며 구체 선별·표시는 후속, 비AI 요약 대체 금지 유지 |
| GQ-01 → GQ-01-02 | 오래된 안내·미검증 아이디어가 현재 기획/사용자 결정과 다를 때 어떤 차이를 설명하는가 | 저장된 기록을 현재 진행 가설·검증 사실·자동 저장 승인으로 승격하지 않음. 기존 최신 결정/편집 보호 원칙으로 해결되는 부분은 재질문하지 않음 |

## 6. 결정 반영과 질문 종료 기준

질문 상태는 `미질문`, `질문 제시·미응답`, `방향 확인`, `가지 검토 중`, `공동 확인 대기`, `닫힘`, `보류`로 기록할 수 있습니다. 인터뷰 진행을 설명하는 표식이며 새 제품/업무 enum이 아닙니다. 기둥의 방향 확인은 전체 가지의 닫힘을 뜻하지 않고, 공동 대기·보류는 담당과 막히는 범위를 함께 남깁니다.

| 답변의 성격 | 반영 위치·방법 |
| --- | --- |
| 사용자 동작·결과 채택 | 현재는 Grill 기능 결정표에 근거·채택 결과·잔여를 선기록. 후속 명세 작성 때 사용자 정본의 기능 본문·예외·상태·남은 계약·D-UF 추적에 통합하고 모듈 계약으로 연결 |
| 공동 제품/제공 조건 | 현재는 결정표에 확인된 부분·담당·잔여를 선기록. 후속 통합 때 사용자 정본 C-01~03과 해당 MC에 제공물·미제공 영향을 연결 |
| 같은 사용자 결과의 내부 설계 | 현재 제품 Grill에서는 필요한 검토 대상으로 남기고 구체 물리 설계는 후속 모듈 작성에서 정함. 새 사용자 결정처럼 D-UF에 추가하지 않음 |
| 모호·보류·미응답 | 해당 질문 상태와 필요한 다음 확인만 기록. 추천을 기능 본문에 적용하지 않음 |

한 질문을 닫으려면 **채택한 사용자 결과·적용 범위·유지 조건이 명확하고**, 정상·반례의 기대 결과가 기존 계약과 모순 없이 설명돼야 합니다. 공동 확인이 꼭 필요한 결과를 추정으로 닫지 않습니다. 구현·시험 통과나 자연어 품질 검증까지 완료했다는 뜻도 아닙니다.

대화에서 명확히 결정된 내용은 추가 승인 단계를 만들지 않고 결정표에 기록합니다. **제품 Grill → 정본 통합 → 모듈 명세 작성** 순서를 지키며 선기록된 결정을 미응답으로 되돌리지 않습니다. 이 문서의 지도/상태에는 결정 위치를 연결하고, 후속 통합이 끝나면 최종 사용자 기능은 정본 하나에서 읽게 합니다. 모든 기둥을 다시 묻는 대신 새로운 반례가 영향을 주는 결정만 재검토합니다.

## 7. 명세 단계의 작업 경계와 재개

- 변경은 `docs/ai-agent-pipeline/` 안에서 수행하고 기존 HandOff와 `docs/interview/` 작업은 보존합니다. Figma는 필요한 현행 흐름의 읽기 근거이며 사용자 정본이 우선입니다. 보드 수정은 이번 범위가 아닙니다.
- Python 구현·의존성 설치/갱신·테스트 작성/실행·Docker/Atlas·DB 변경·LLM 실호출은 별도 구현 요청 전까지 수행하지 않습니다. 비밀키·환경변수 값·연결 문자열은 열람·출력·문서화하지 않습니다.
- 한글 변경 문서는 UTF-8·로컬 링크·diff 공백을 확인합니다. 커밋·푸시는 하지 않고, 추적 파일 수정 시 추천 커밋 메시지를 제공합니다.
- 모듈의 수용 사례는 **시험 계획**입니다. 이후 기본 시험은 가짜 Provider/저장소/시계/토큰 계산기를 사용하고 실제 어댑터 payload/파싱도 검증하도록 명세합니다. 구현·단위시험·live LLM/DB·통합/E2E·브라우저·자연어 품질의 증거를 구분하고 미실행은 NOT_RUN으로 표시합니다.

현재 방향은 [GD-001~013](grill-feature-decisions.md)를 따릅니다. 계산 자동화 GQ-02와 기본 보관의 실제 제공 보장은 공동 확인 대기를 유지하고, 다음에는 **GQ-05-02/C-01: B 접근 권한 상실 후 A Chat의 과거 답변에 이미 기록된 B 유래 정보의 열람 범위를 어떻게 정할지**를 확인합니다. 원문 재접근·새 AI 자동 재사용 금지와 A 명시 채택/저장 가정 보존은 유지합니다. 참조 제거≠원문 삭제 등 이미 합의한 규칙을 재질문하지 않습니다. 제품 방향을 정해도 실제 접근·제공 보장은 공동 확인 전까지 닫지 않습니다. 정확한 호출 횟수·시간·API·출력 스키마는 제품 방향 수렴 뒤 모듈 명세 작성에서 다룹니다.
