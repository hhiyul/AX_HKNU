GD-018에서는 서로 다른 프로젝트의 대기 시간을 활용하는 편의와 여러 실행의 상태·중단·결과 및 서비스 동시 이용 조건을 관리해야 하는 대가를 채택했습니다. 정상 예에서는 A 실행 중 B 요청을 시작해도 A가 취소되거나 저장 대상이 B로 바뀌지 않습니다. 반례로 A Chat을 두 탭에서 열어도 두 번째 답변 실행을 허용하는 근거가 되지 않습니다. 서비스 제공 조건 확인이 남아 있지만 이를 기획자 전체의 단일 실행 A안으로 되돌리는 기본값으로 사용하지 않습니다. 이전 질문에서 제시한 A안 추천은 채택된 제품 방향이 아니며 B안으로 정리합니다.

GD-019에서 비교한 대가는 화면 연결을 유지하지 않아도 원래 요청의 결과를 얻을 수 있는 편의와, 사용자가 보고 있지 않아도 남은 모델/도구 호출이 계속될 수 있다는 점입니다. 정상 예에서는 네트워크가 끊겨도 살아 있는 실행이 계속되고, 재접속으로 기존 실행의 상태/결과를 확인합니다. 반례로 실제 서버 작업이 이미 종료됐거나 사용자가 명시적으로 중단한 경우, 재접속을 이유로 이를 자동 재개하지 않습니다. 살아 있는 원래 실행의 계속과 중단 작업 복구를 구별하며, 정상 완료·저장 성공·실제 제공 보장의 검증 완료를 뜻하지 않습니다.

GD-020에서는 진행 중인 AI보다 사용자의 프로젝트 삭제 의도를 우선하고, 완료되지 않은 작업 결과를 포기할 수 있는 대가를 채택했습니다. 정상 예에서는 서버에서 프로젝트 삭제가 확인된 뒤 Provider의 늦은 결과가 와도 그 Chat/기획에 추가되지 않으며 같은 식별자의 소유 자원을 되살리지 않습니다. 반례로 삭제 실패·미확인이나 UI 동의만 있는 상태를 삭제 완료로 표시하지 않습니다. 다른 프로젝트에 이미 남은 참고 정보의 자동 이용은 후속 GQ-07-02의 GD-021 채택으로 연결합니다.

GD-021은 GD-020에 남긴 다른 프로젝트의 기존 획득 정보 이용 범위를 A안으로 정한 후속 결정입니다. 프로젝트별 대화 연속성을 유지하는 편의와, 원본 B를 삭제해도 이미 A에 전달된 정보가 AI 검토에 활용될 수 있다는 대가를 채택했습니다. 정상 예에서는 A가 이미 읽은 B 정보를 당시 자료로 참고하며 원문을 현재 다시 확인했다고 표시하지 않습니다. 반례로 B의 삭제 후 늦은 작업 결과를 새로 받아 A의 기존 획득 정보라고 주장할 수 없고, 사용자가 A에서 B를 제거/제외했다면 기존 다음-run 제외 규칙이 우선합니다. A의 기존 획득 기록 참고와 B 원문/사본의 새 조회를 구별하며, 실제 이력 제공·권한 정책의 정합 확인은 별도입니다.

GD-022에서는 시스템 형식 오류의 재요청 부담을 줄이는 대신 추가 모델 호출·대기가 생길 수 있는 대가를 채택했습니다. 정상 예에서는 현재 출력의 검증 오류를 보정한 뒤 재검증을 통과한 제안만 전달합니다. 반례로 같은 오류가 다시 나오거나 진전이 없으면 무한 수정하지 않고 기존 실패 안내로 종료합니다. 응답이 왔는지 모르는 통신 실패나 저장 결과 미확인을 보정 대상으로 삼지 않으며, 형식 통과를 사실 검증·실제 저장 완료로 만들지 않습니다.

GD-023에서는 일시 혼잡의 재요청 부담을 줄이는 편의와 같은 요청의 대기가 길어질 수 있는 대가를 채택했습니다. 정상 예에서는 계약상 생성 미접수가 확인된 일시 반려만 활성 요청 안에서 제한적으로 다시 시도합니다. 반례로 응답이 오지 않거나 오류 코드만 있는 경우를 미실행으로 간주해 같은 생성을 자동 재전송하지 않습니다. 확인 수단이 없는 실제 어댑터에는 이 예외를 적용할 수 없으며, 미접수 확인/오류 분류와 재시도 한도는 아직 제공·검증됐다고 주장하지 않습니다.

기존 합의 적용 확인: 자동 참고한 추가 기록에도 정본 G-11의 실제 읽은 범위·중요한 누락/판단 영향·출처/시점/한계 안내를 적용합니다. 이는 새 선택이 아니므로 별도 GD를 만들거나 같은 원칙을 재투표하지 않습니다.

GD-024에서는 원격 종료 확인 지연으로 같은 Chat이 잠기는 일을 줄이는 편의와, 이전 외부 호출이 아직 처리 중일 수 있다는 대가를 채택했습니다. 정상 예에서는 AX가 기존 답변 실행을 종료하고 늦은 본문/제안 반영을 차단한 사실을 확인한 뒤 새 직접 전송을 받되 원격 종료는 미확인으로 안내합니다. 반례로 중단 요청만 접수됐거나 AX 종료/차단을 확인하지 못했다면 같은 Chat의 추가 전송 제한을 유지합니다. 새 질문 허용과 미확인인 동일 변경의 재쓰기 조건은 별개이며, 실행/쓰기의 확인 상태 갱신을 본문 추가로 취급하지 않습니다.

GD-025에서는 이전에 참고한 B가 그대로라고 오해할 가능성을 줄이는 편의와, 관련 변경 설명이 응답에 추가되는 대가를 채택했습니다. 정상 예에서는 과거 확인한 B의 카드 3장/1,500원과 이번 실제 읽기의 5장/2,500원이 제안에 영향을 주면 기준 차이를 짧게 설명하며 A 편집안은 보존합니다. 반례로 과거 실제 확인값이 없거나 비교 가능한 범위가 아니면 차이를 만들어 내거나 전체 변경을 검토했다고 주장하지 않습니다. 일반 참조 재선택 안내와 별도의 평가/저장 보류 해제를 구별합니다.

GD-026에서는 프로젝트 전체 정리를 한 흐름으로 수행하는 편의와 전용 파일도 삭제 영향 범위에 포함되는 대가를 채택했습니다. 실제 소유와 삭제 결과를 공통 서버에서 확인하며 타 소유 원본을 함께 지우지 않습니다.

GD-027은 기존 정본의 1:1 관계를 사용자가 1:n의 독립 Chat 세션 관계로 정정한 최신 결정입니다. 기존 기록이 처음부터 1:n이었다고 바꾸지 않고 대체 이력을 남깁니다. 같은 프로젝트의 다른 세션도 병렬 대상이며 같은 세션의 복수 접속과 구별합니다. 세션 독립과 프로젝트 업무 저장 공유를 함께 유지하고 실제 식별/권한/버전·맥락 경계의 정합은 후속입니다.

GD-028은 “최신 사용자 결정”과 “A에 명시 채택한 가정”의 **미저장 범위를 해당 세션으로 한정**합니다. 예를 들어 S1의 3장 결정은 프로젝트 등록 전 S2의 5장 검토 기준을 자동 변경하지 않습니다. 기존 승인으로 프로젝트에 등록된 내용은 공통 자료로 읽되, 대화 전문·미저장 편집까지 함께 공유하지 않습니다.

GD-029에 따라 생성·재방문 UX를 큰 제품 쟁점으로 먼저 확정해야 한다는 이전 검토의 분류를 정정합니다. 독립 세션 사용은 확정이며 구체 UX는 디자인팀 후속입니다. 최근 세션 우선/목록 선택 어느 쪽도 이번에 대신 채택하지 않습니다.

GD-030은 “미확인 항목의 모든 새 저장 대기”라는 확대 해석을 배제합니다. 예를 들어 S1의 가격 10,000원 저장이 미확인이어도 S2의 별개 가격 12,000원 변경은 승인·현행 검증을 거쳐 시도할 수 있습니다. **허용은 항상 성공한다는 뜻이 아니며**, 버전 충돌이면 미반영·편집 보존·사용자 선택 대기입니다. S1의 원 요청은 결과 조회만 자동으로 계속하며, 늦은 성공 통지는 그 요청의 반영 사실만 갱신하고 S2의 더 최신 저장값을 이전 값으로 되돌리지 않습니다.

GD-031은 개별 Chat 세션 삭제를 제공하는 A안 채택입니다. S1을 삭제해도 프로젝트에 이미 등록한 CK·추가 기록과 다른 S2는 유지됩니다. 삭제된 S1의 미등록 결정·대화/캡슐을 계속 열람·자동 참고시키는 기본값은 두지 않습니다. 프로젝트 존속 기간 기본 보관(GD-013)은 사용자 삭제 예외를 포함하며, 개별 삭제를 미정으로 남겼던 GD-027 영향 검토·정합 메모를 이 결정으로 갱신합니다. 서버 삭제 확인·실패/미확인 구분은 필요하지만 휴지통/복원을 추가하지 않습니다. 이미 전송한 승인 저장의 미확인 결과는 후속 GD-032로 Chat 삭제 허용·별도 결과 확인을 채택했습니다. 진행 중 AI 생성·첨부 원본 범위는 당시 실행 종료/무첨부 사례의 채택으로 확정하지 않습니다.


GD-032는 Chat 삭제와 이미 UI 승인·전송한 프로젝트 저장의 결과 확인을 분리하는 A안 채택입니다. 프로젝트 저장 결과 미확인을 이유로 해당 Chat 전체 삭제를 기다리게 하지 않습니다. 원 저장 요청은 실제 검증/반영 결과를 계속 확인하되 자동은 조회뿐이며, 원 Chat이 없다는 사유만으로 이미 한 저장 승인을 취소하거나 결과를 미반영으로 단정하지 않습니다. 원 요청/결과 확인의 최소 연결은 남기더라도 삭제한 대화/캡슐을 열람·모델 맥락으로 복원하지 않습니다. 이는 프로젝트 전체 삭제 뒤 늦은 반영을 막는 GD-020과 함께 적용하며 Chat 삭제만으로 프로젝트 삭제를 추정하지 않습니다.


GD-033은 Chat 첨부 원본을 해당 세션의 참고 범위에 두는 A안 채택입니다. S1에 첨부했다는 이유만으로 S2의 에이전트가 원본을 자동 탐색/조회하지 않습니다. CK·추가 기록에 승인 등록한 내용의 공통 참고와 그 출처 원본의 새 조회는 구별합니다. GD-002의 점진적 탐색은 이 허용 범위 안에서만 수행하며, 자동 탐색 도구가 원본의 공유 등록·권한을 만들어 주지 않습니다. 이 결정은 논리적 자료 사용 범위이며 실제 저장 위치·물리 소유·보존/정리·UI 경로는 별도 계약입니다.


GD-034는 개별 Chat의 AI 답변 생성 중 삭제를 허용하지 않는 B안 채택입니다. 앞서 질문에서 추천한 생성 중 삭제 허용 A안은 미채택입니다. 먼저 정상 종료 또는 사용자 중단 후 AX 실행 종료/출력 차단을 확인해야 하며, 중단 요청 접수나 Provider 원격 종료 상태를 AX 종료와 혼동하지 않습니다. GD-032의 이미 승인·전송한 저장 결과 미확인은 AI 답변 생성 상태와 별개이므로, AI 실행이 종료됐다면 그 저장 결과만 미확인이라는 이유로 삭제를 막지 않습니다. GD-020의 프로젝트 전체 삭제와 GD-034의 개별 Chat 삭제는 서로 다른 사용자 결과로 유지합니다.

### 공동 확인 대기 · GQ-02/C-02: 계산 자동화 최초 범위의 디자인팀 논의

합성 상황: 사용자가 “A 상품 구성을 점검하고 B 사례와 비교해 개선안을 주세요”라고 요청했습니다. A/B를 허용된 상태에서 읽어 설명 일부를 전달하고 추가 검토 중, 현재 B 접근 권한이 상실됐다는 사실이 확인됐습니다. A와 A Chat의 접근 권한은 유지되며 사용자는 중단을 누르거나 Chip을 제거하지 않았습니다. 아직 업무 쓰기를 실행하지 않은 일반 검토 요청입니다.

질문은 **B에 의존한 미전달 결과의 사용을 막은 뒤, B 없이 수행 가능한 A 작업을 현재 실행 안에서 계속할지, 전체 실행을 끝내고 새 사용자 요청을 기다릴지**입니다. B에 의존한 비교 판단을 완료로 표시하거나 과거 사본으로 제한을 우회하는 안은 제시하지 않습니다. 이미 전달된 답변은 GD-014에 따라 열람을 유지합니다.

| 대안 | 사용자 결과 | 대가·범위 |
| --- | --- | --- |
| A · 독립 가능한 A 작업 계속 | B에 의존한 미전달 결과를 제외하고, B 없이 수행 가능한 A 검토만 현재 실행 안에서 이어감. B 비교 미완료와 실제 수행 범위를 안내 | 재요청 부담이 줄지만 추가 처리·대기가 생기고 원래 비교 요청 전체를 마치지는 못함. B 인용 문장만 지우는 것으로 독립성을 보장하지 않으며, B 영향의 배제를 확인할 수 없으면 멈춤 |

공통 유지: 사용자 참조 제거/자료 제외의 다음-run 적용과 고유 정보 자동 재사용 제외, A에 명시 채택·저장한 가정 보존, 최신 사실 확인이 필요한 판단의 보류·실제 근거/시점 안내, 저장 검증/승인 유지. 채택한 A안에 따라 허용한 과거 답변과 그 AI 캡슐에 같은 정책을 적용하며, 압축으로 허용 범위를 넓히지 않습니다. 실제 공통 권한·이력 제공 정책의 정합은 C-01·03 공동 후속입니다.

### 응답 완료 · GQ-06/C-01: MVP의 실제 이용 단위

합성 상황: 한 브랜드의 A 프로젝트를 기획하는 사람이 있고 다른 담당자도 그 기획을 검토하려 합니다. 다른 담당자가 같은 A Chat을 읽고 AI에 질문하거나 저장 승인을 할 수 있어야 하는지, MVP에서는 지정된 한 기획자만 Chat을 이용하는지 아직 정하지 않았습니다. 실제 공통 시스템에 공동 사용이 구현됐다고 가정하는 상황은 아닙니다.

| 대안 | MVP가 약속할 이용 범위 | 대가·범위 |
| --- | --- | --- |
| A · 프로젝트별 한 명의 기획자 이용 | 한 프로젝트 Chat의 열람·AI 요청·저장 승인을 지정된 한 기획자의 작업으로 제한. 다른 사람의 공동 Chat 이용은 MVP에 포함하지 않음 | 실행/승인 주체가 단순하지만 다른 담당자가 같은 Chat에서 이어 작업할 수 없음. 실제 이용자 연결·접근 검증은 공통 담당과 확인 필요 |

### 응답 완료 · GQ-06-02/C-03: 한 기획자의 여러 프로젝트 AI 작업 병행

상태는 **GD-018 병렬 지원 B안 채택 / 범위는 GD-027로 정정**입니다. 아래는 당시 1:1 전제의 질문 기록입니다. 같은 프로젝트 안을 포함한 서로 다른 Chat 세션은 병렬 대상이며 동일 세션의 복수 탭/접속은 단일 활성 실행을 유지합니다. 기획자 전체 하나씩 제한 A안은 미채택입니다.

합성 상황: 기획자가 A 프로젝트 Chat에서 사례 조사·비교를 요청했고 답변이 진행 중입니다. 같은 앱 실행을 유지한 채 자신이 이용 가능한 B 프로젝트의 전용 Chat으로 이동해 B 가격안 검토도 요청하려 합니다. A/B는 각각 고정된 별도 저장 대상을 유지합니다. 사용자 중단·앱 종료·중단 작업 복구 상황은 아닙니다.

| 대안 | 사용자 경험 | 대가·범위 |
| --- | --- | --- |
| A · 한 기획자 전체에서 AI 답변 하나씩 | A 답변이 진행 중이면 B에서 새 AI 요청 전송을 보류. A 종료 또는 중단 후 종료를 확인한 뒤 사용자가 B 요청을 직접 전송 | 현재 작업과 이용 한도 관리가 단순하지만 긴 A 검토가 다른 프로젝트의 AI 요청도 막음. 프로젝트 열람·미전송 작성 등 기존 가능한 작업은 이 답변 생성 제한과 구별 |
| B · 서로 다른 프로젝트의 AI 작업 병행 | A 답변을 유지하면서 B 전용 Chat에서도 별도 AI 요청 실행을 지원. 각 Chat 안에서는 기존 단일 실행 유지 | 대기 시간을 활용하지만 여러 프로젝트의 진행·중단·결과를 구별해 관리하고 서비스의 동시 실행 지원을 확인해야 함. 무제한 실행 보장은 아님 |

두 안 모두 큐잉·예약·종료 후 자동 전송·자동 작업 전환을 추가하지 않습니다. B로 이동했다는 이유만으로 A를 자동 취소하거나 A의 저장 대상을 B로 변경하지 않습니다. 제한 대상은 새 AI 답변 실행이며, 저장 미확인의 자동 결과 조회를 답변 생성과 합쳐 기존 다른 Chat/항목 작업 허용을 막지 않습니다. 실제 이용 한도·서버의 실행/종료 확인·여러 탭의 중복 제어는 C-03/MC 후속입니다. 이번에는 정확한 병행 개수·타임아웃·API·락 구조를 정하지 않습니다.

### 응답 완료 · GQ-06-03/C-03: 화면 연결 단절과 이미 시작한 실행

상태는 **GD-019로 A안 제품 방향 채택 / 실제 실행 유지·조회 제공 조건 공동 확인 대기**입니다. 아래는 GD-018에 이어 제시한 질문 당시 비교안입니다. 화면 연결 단절을 중단 의사로 취급하지 않으며 살아 있는 원래 작업을 계속합니다. UF-AI-05 EX-04의 재접속 자체로 새 AI/도구 실행 금지와 UF-AI-13의 중단 작업 자동 복구 제외는 유지합니다. 영향 모듈은 M-05·07·08입니다.

합성 상황: A와 B Chat의 답변이 각각 진행 중입니다. 사용자가 중단 버튼은 누르지 않고 탭을 닫거나 화면 연결이 끊겼습니다. 서버 프로세스와 원래 요청은 아직 살아 있습니다. 사용자가 나중에 다시 Chat을 엽니다. 브라우저의 미전송 입력·미저장 편집안은 기존 인메모리 복원 비보장 범위를 유지합니다.

| 대안 | 이미 시작한 요청의 처리와 재접속 결과 | 대가·범위 |

CK/추가 기록의 UI 최종 승인·저장 검증·미확인 결과 조회 원칙을 유지하고, 화면이 없다는 사유로 업무 저장을 자동 승인하지 않습니다. 서버 재시작·프로세스 종료 뒤의 작업 복구·durable 큐·새 미전송 내용의 자동 전송은 범위에 추가하지 않습니다. 실제 실행 유지/조회/보존 제공 보장은 C-01·03 공동 후속이며 연결 단절 판정·시간·전송 방식은 MC 후속입니다.

### 응답 완료 · GQ-07/C-01: 진행 중인 AI 작업과 프로젝트 삭제

상태는 **GD-020 진행 중 삭제/늦은 결과 미반영 A안 채택 / 실제 공통 계약 후속**입니다. 아래는 당시 질문 기록입니다. 최신 GD-027의 1:n에 따라 프로젝트 삭제는 모든 귀속 Chat 세션/작업에 적용하고 파일 정리는 GD-026을 따릅니다. 실행 종료까지 삭제 보류 B안은 미채택이며 아래의 1:1 전제는 대체됐습니다.

합성 상황: A 프로젝트 Chat에서 긴 조사·비교가 진행 중이고 사용자는 프로젝트 목록으로 이동했습니다. 사용자가 A 프로젝트 자체의 삭제를 최종 확인하려 합니다. A Chat의 Chip 제거·항목 전체 비우기·화면 닫기는 아닙니다. 현재 공통 API가 아래 어느 정책을 제공하는지는 확인되지 않았습니다.

| 대안 | 사용자 결과 | 대가·범위 |
| --- | --- | --- |
| A · 진행 중에도 프로젝트 삭제 허용 | AI 작업 중에도 삭제 요청 가능. 공통 서버에서 삭제 성공이 확인되면 A 프로젝트와 그 소유 Chat의 접근을 종료하고, 새 A 작업/호출을 막고 진행 중인 호출의 중단을 시도. 늦은 결과로 A Chat/기획을 다시 만들거나 사용자 결과를 추가하지 않음 | 삭제 의도를 우선하지만 끝나지 않은 작업의 결과를 포기할 수 있으며, 삭제 후 도착 결과의 처리와 쓰기 방지가 필요 |
| B · 실행 종료 전 프로젝트 삭제 보류 | A의 AI 실행 중에는 삭제를 반영하지 않음. 사용자가 종료를 기다리거나 명시적으로 중단하고 종료 확인 후 삭제를 다시 직접 요청 | 실행 중 대상이 사라지는 상황을 줄이지만 긴 작업·종료 미확인이 프로젝트 삭제까지 막을 수 있음. 삭제를 자동 대기열에 넣지 않음 |

질문은 **프로젝트를 삭제하려는 사용자 의도를 진행 중인 AI보다 우선할지, AI 실행이 끝날 때까지 삭제를 보류할지**입니다. 두 안 모두 삭제가 실제로 완료되면 독립된 Chat 보관/복원 경로를 새로 만들지 않습니다. 삭제 실패·결과 미확인을 삭제 완료로 표시하지 않으며, A 삭제를 다른 프로젝트 B의 참조 원본·B의 명시 채택/저장 가정 삭제로 확대하지 않습니다. 이미 실행된 외부 호출의 취소 성공·되돌림을 보장하지 않습니다. 휴지통·복원·중단 작업 자동 복구·자동 저장은 추가하지 않습니다. 실제 삭제 수락/완료 의미·A 소유 자료의 정리 범위·물리 보존 조건·실행 종료 확인은 사용자·공통 백엔드/제품 담당의 C-01·03 후속입니다. 어느 안도 현재 제공되는 삭제 동작으로 간주하지 않습니다.

### 응답 완료 · GQ-07-02/C-01: 참고 원본 삭제의 다른 프로젝트 파급 범위

상태는 **GD-021로 A안 제품 방향 채택 / 실제 공통 자료·이력 제공 계약 확인 대기**입니다. 아래는 GQ-05의 원본 삭제 잔여를 다룬 질문 당시 비교안입니다. 별도 A가 삭제 전에 받아 둔 정보와 답변의 이용은 유지하며, 원본 삭제를 A의 자동 이용 제외로 전파하는 B안은 미채택입니다. GD-020의 삭제된 소유 작업 늦은 결과 미반영은 유지합니다. 영향 모듈은 M-01·02·05·07·08입니다.

합성 상황: A Chat이 B Chip을 참고해 B의 포장 구성과 비용을 읽고 A 개선안을 설명했습니다. A의 현재 실행에도 이미 읽은 B 자료가 있습니다. 아직 A의 기획 가정으로 명시 채택·저장한 상태는 아닙니다. 이후 B 프로젝트 자체의 삭제 성공이 확인됐지만 A는 유지됩니다. B Chip은 사용 불가 참조로 남고, 사용자가 A에서 B Chip을 직접 제거하거나 자료 제외를 지시하지는 않았습니다. A가 이미 받아 둔 정보와 설명을 현재/이후 검토에 계속 활용할 수 있을지가 질문입니다.

### 2. 후속 제품 검토의 확정 결과 · GD-028~030

아래는 검토 당시 대안과 이후 사용자의 확정 결과입니다. 세 항목을 더 이상 제품 미응답으로 두지 않습니다. 구체 UX 위임과 실제 API 보장 후속을 제품 방향 미정으로 되돌리지 않습니다.

| 검토 쟁점 | 사용자 확정 결과·상황 적용 | 과거 대안의 처리·남은 담당 |
| --- | --- | --- |
| 1 · 명시 채택한 미저장 가정의 공유 범위 | **GD-028 채택.** S1에서 “카드 3장으로 진행”을 채택해도 프로젝트 등록 전에는 S1에만 유지. S2의 5장 검토에 자동 전파하지 않음. 프로젝트에 별도 등록·반영 확인한 내용부터 공통 자료로 참고 | 세션 안에서 유지하는 방향 확정, 별도 프로젝트 공통 미저장 가정 공유안은 미채택. 중요한 미저장 결정이 다른 세션에 자동 전달되지 않는 대가를 수용. 실제 데이터/출처에 세션 귀속과 등록 확인 범위를 구별하는 계약은 M-01/02/07·MC-04/05 후속 |
| 2 · 세션 생성·프로젝트 재방문 기본 동작 | **GD-029 확정·UX 위임.** 일반 AI 서비스처럼 독립 세션을 나누어 이용. 구체 생성/선택/전환/재방문 UX는 나중에 디자인팀 논의 후 담당 팀이 결정 | 최근 세션 우선/목록 선택 비교안은 어느 쪽도 채택하지 않음. 이를 큰 제품 결정의 선행 미응답으로 올린 이전 분류 정정. 1:n·세션 맥락 격리·재방문만으로 새 실행 금지에 근거한 모듈 설계는 진행 가능. 새 세션에 다른 세션 이력을 자동 주입하지 않음 |
| 3 · 같은 항목에 미확인 쓰기가 있을 때 별개 변경 | **GD-030 채택.** S1의 가격 10,000원 저장이 미확인이어도 S2의 별개 가격 12,000원 변경은 별도 승인·현재 검증을 거쳐 시도 가능. 동일 변경 재전송 금지는 유지 | 항목 전체 결과 확인 대기안은 미채택. 별개 변경의 충돌 가능성·원 요청과 별도 결과 관리를 수용. 제품 방향은 확정이며 C-01/MC-09·10에서 조건부 쓰기·중복 방지·순서/결과 보장을 맞춤. API 확인 후 다시 제품 대안을 고르는 보류로 두지 않음 |

**독립 세션은 다른 세션의 대화를 자동으로 기억한다는 뜻이 아닙니다.** 기존 다른 프로젝트 Chip과 추가 기록의 점진적 탐색 결정을 같은 프로젝트의 모든 Chat 이력 자동 검색 권한으로 넓히지 않습니다. 세션 간 대화 검색/인용·분기/복제·공통 AI 기억을 원한다면 별도 기능 검토 대상이며 현재 필수 기능으로 추가하지 않습니다.

**개별 Chat 세션 삭제는 GD-031로 A안 채택 완료입니다.** 삭제 확인된 해당 세션의 대화/캡슐·미등록 결정은 열람/자동 참고 대상에서 제외하며 프로젝트에 등록된 CK·추가 기록과 다른 세션은 유지합니다. 미확인인 기전송 승인 저장은 GD-032로 Chat 삭제 허용·별도 결과 확인을 채택했습니다. AI 생성 중 해당 Chat 삭제는 GD-034의 B안으로 금지하고 AX 실행 종료/출력 차단 확인 뒤 허용합니다. 첨부의 세션 참고 범위는 GD-033 채택, 실제 물리 소유/정리·보존은 후속입니다. 초기화 편의·세션 이름 변경·휴지통/복원은 계속 제외입니다.

다른 세션의 저장 직후 자동 알림·화면 실시간 동기화도 별도 UX 선택입니다. 새 요청의 현재 자료 조회·최종 저장의 버전 검증은 필요하지만, 이를 자동 편집 교체·자동 재검토·필수 알림 기능으로 확대하지 않습니다.

| 미채택 대안 | S2에서 허용할 사용자 결과 | 대가 |
| --- | --- | --- |
| A · Chat 첨부는 해당 세션 참고용, 프로젝트 공통 자료로 자동 등록하지 않음 — 추천 | S1에 첨부했다는 이유만으로 S2가 그 원본을 자동 탐색/사용하지 않음. S2에서 쓰려면 사용자가 S2의 참고 대상으로 별도로 제공하거나 프로젝트 공통 자료로 명시 등록한 범위를 이용 | 세션별 실험·자료 사용 범위가 예측 가능하지만 같은 파일을 다른 세션에서도 쓰려면 명시적인 제공/등록이 필요. 구체 선택/등록 UI는 별도 설계 |
| B · Chat 첨부 원본을 프로젝트 공통 참고 자료로도 취급 | 첨부 성공을 공통 원본 참고 범위 등록으로 간주해 같은 프로젝트의 S2에서도 필요할 때 자동으로 찾아 읽을 수 있음. 각 세션 활성 파일 목록을 그대로 복사하거나 매번 전문을 강제 주입하는 뜻은 아님 | 반복 제공 부담은 줄지만 한 세션에서 시험 삼아 넣은 옛 견적/대안 자료가 다른 세션의 판단에도 들어올 수 있어 공유 의미·출처/시점 안내가 필요. 기존 Chat별 참고에서 원본의 공통 탐색 허용 범위를 넓히는 제품 변경 |

**추천 근거와 한계:** A는 프로젝트 등록 전 결정은 세션에만 남는 GD-028 및 독립 세션의 자료 선택과 잘 맞습니다. 다만 원본 파일과 그 안에서 명시 채택한 기획 결정은 서로 다른 종류이므로 GD-028만으로 이 질문이 이미 해결됐다고 보지는 않습니다. B는 자료 재사용 편의가 크지만 첨부를 공통 등록 의도로 해석하는 대가가 있습니다. 어느 안도 프로젝트 파일 관리 화면·새 파일 라이브러리·복제/이동 기능을 일괄 도입하는 결정이 아닙니다.

**정상·반례:** A라도 사용자가 S1에서 견적값을 프로젝트 CK/추가 기록에 승인 등록했다면 S2는 그 공통 등록 내용을 기존 범위로 참고할 수 있습니다. 등록 내용의 참고와 S1 첨부 원본의 새 조회는 구별합니다. B라도 S1 대화/캡슐·미등록 AI 제안/명시 결정을 통째로 S2에 공유하거나, 원본을 최신 확정 원가로 표시하거나, S1 검색 허용을 S2에 전파해서는 안 됩니다. 실제 접근 확인·원문 읽기 범위/출처 안내는 어느 안에서도 필요합니다.

**질문:** **A처럼 Chat 첨부 원본을 해당 세션의 참고 범위에 두고 공통 등록은 분리**할까요, 아니면 **B처럼 같은 프로젝트의 다른 세션도 자동 탐색할 수 있는 공통 원본으로 취급**할까요? 대안·추천은 답변 전 미채택입니다. 프로젝트 공통 자료 제공 경로·현재 API의 지원·원본 보존/정리 방법은 제품 범위 이후 C-01·03/MC로 연결합니다. 구현/시험은 NOT_RUN입니다.


### 응답 완료 · GQ-06-09/C-01: AI 답변 생성 중 개별 Chat 삭제를 허용할지

상태는 **2026-11-11 GD-034로 B안 채택 / AI 생성 중 개별 Chat 삭제 금지**입니다. 아래는 2026-11-07 질문 당시 비교안이며 추천했던 생성 중 삭제 허용 A안은 미채택입니다. 해당 AX 실행이 정상 종료되거나 사용자 중단 후 종료/이전 출력 차단이 확인되면 삭제를 허용합니다. Provider 원격 종료 미확인은 추가 대기 조건이 아니며 실제 종료/삭제 접수 검증은 공동·물리 후속입니다.

**합성 상황:** 프로젝트의 S1에서 AI가 판매 대안을 비교하며 추가 자료를 읽고 답변을 생성하고 있습니다. 사용자는 그 검토가 더 필요 없어 S1을 삭제하려 합니다. 같은 프로젝트의 S2는 별도 실행 중이고, 두 세션에 첨부 파일과 이미 UI 승인·전송한 업무 저장은 없습니다. 프로젝트와 S2는 계속 사용하려 합니다.

**이미 확정된 경계:** 개별 Chat 삭제는 제공하며 프로젝트 등록 CK·추가 기록과 다른 세션은 보존(GD-031). 창 닫기/통신 단절만으로 살아 있는 실행을 멈추지 않음(GD-019). 프로젝트 전체 삭제는 진행 중에도 허용하며 모든 자식의 늦은 반영 차단(GD-020). 이미 승인·전송한 프로젝트 저장이 있다면 Chat 삭제와 별도로 결과 확인(GD-032). 이번 질문은 이 합의를 유지한 채 S1의 **AI 생성 작업**을 언제 삭제할 수 있는지 정합니다.

| 미채택 대안 | 사용자 행동·결과 | 대가 |
| --- | --- | --- |
| A · 생성 중에도 Chat 삭제 허용, 해당 AI 작업 종료/반영 차단 — 추천 | 삭제 성공 확인 뒤 S1의 새 모델/도구 호출을 막고 진행 중 호출의 중단을 시도. 늦은 답변·도구 결과로 S1을 되살리거나 S2/프로젝트에 자동 반영하지 않음. 프로젝트와 S2는 유지 | 사용자의 삭제 의도를 바로 따르지만 생성 중 답변과 남은 검토를 포기함. 이미 외부에 전송한 호출의 실제 취소 성공은 보장하지 않으며, 삭제에 따른 새 결과 반영 차단과 구별 필요 |
| B · 해당 AX 답변 실행이 종료된 뒤 Chat 삭제 허용 | 정상 종료를 기다리거나 사용자가 먼저 중단. AX 실행 종료/이전 출력 차단을 확인한 뒤 S1 삭제. Provider 원격 종료 미확인 자체를 추가 대기 조건으로 삼지 않음 | 결과를 보고 삭제할 기회는 있지만 원치 않는 작업 때문에 삭제가 지연되거나 중단→삭제의 추가 행동이 필요. 중단 요청 접수만으로 종료됐다고 처리할 수 없음 |

**추천 근거와 한계:** A는 프로젝트 전체 삭제의 GD-020과 일관된 사용자 통제를 제공하고 S1 삭제가 S2의 진행을 막지 않게 합니다. 다만 삭제는 단순한 창 닫기보다 강한 작업 포기이므로 생성 중 답변을 잃는 의미가 분명해야 합니다. B는 삭제 전 결과 확인을 우선하지만 이미 삭제 의사를 밝힌 사용자에게 대기/추가 행동을 요구합니다.

**정상·반례:** A 선택 시 S1 삭제 성공 뒤 새 모델/도구 호출·늦은 대화/제안 반영은 0이어야 하며 S2 실행은 유지되어야 합니다. 기존에 UI 승인·전송한 업무 저장까지 함께 취소/재전송하는 것으로 확대하면 GD-032 위반입니다. B 선택 시 실제 AX 종료/출력 차단 전 삭제 완료로 안내하지 않으며 원격 Provider 종료 확인까지 기다리는 규칙을 추가하지 않습니다. 어느 안도 프로젝트/다른 세션 삭제·새 실행/자동 복구·외부 호출 되돌림 보장을 추가하지 않습니다.

**질문:** **A처럼 생성 중에도 Chat을 삭제하고 그 AI 작업의 종료/늦은 반영 차단을 처리**할까요, 아니면 **B처럼 해당 AX 실행 종료 후 삭제를 허용**할까요? 대안은 답변 전 미채택입니다. 실제 삭제 성공/실행 종료/반영 차단 증거·취소 제공 여부·물리 보존은 C-01·03/MC에서 후속 구체화합니다. 구현/시험은 NOT_RUN입니다.


## 2026-11-11 잔여 제품 쟁점 검토 · 큰 방향 1차 수렴

GD-034까지 반영한 뒤 사용자 정본의 OPEN-UF-01~16·P-01/C-01~03과 현재 Grill 기둥/가지의 잔여를 대조했습니다. **디자인팀 위임·이미 채택한 규칙의 적용·공동 제공 약속·세부 물리 계약을 제외하고, 지금 새로 선택해야 할 큰 제품 쟁점은 확인되지 않았습니다.** 큰 제품 방향은 1차 수렴으로 분류하며 질문을 만들기 위해 기존 결정을 재투표하거나 신규 기능을 추가하지 않습니다. 이는 모든 제품 가지·공동 약속·모듈 계약이 닫혔다는 선언이 아니고, 사용자의 일시중지 요청으로 기록하는 상태도 아닙니다.
