## 1. 목적과 적용 범위

이 문서는 에이전트가 실제로 무엇을 읽고, 어떤 후보를 만들며, 사용자 확인 뒤 어느 서비스가 저장하는지를 구체화한다. GD-046~070의 제품 방향을 다시 결정하지 않는다. 기존 D-01~07·J-01~05를 대체하는 별도 제품 정본이 아니라, 해당 계약의 기능별 보완 명세다. 아래 논리 필드·도구 이름은 설계용이며 현재 공개 API나 팀의 제공 약속이 아니다.

일정 **읽기는 이미 일부 구현**되어 있다. 일반 채팅은 요청 시작 시 현재 프로젝트의 미완료 일정 최대 30개와 완료 개수를 입력에 넣는다. 그러나 특정 날짜·완료 상태·ID로 추가 조회하는 모델 도구와 일반 채팅의 일정 제안 도구는 현재 등록되어 있지 않다. 문서 항목 전용 할 일 제안 및 사용자가 등록·수정·완료·삭제·복구하는 API는 별도로 존재한다. 따라서 문제는 일정 기능 전체의 부재가 아니라 **자료 조회와 일반 대화의 제안·등록 경로가 끝까지 연결되지 않은 것**이다.

조사 기준은 로컬 `feature/ai-agent-pipeline`, HEAD `c97b411`, 시작 시 작업 트리 clean이다. `backend/main.py`에 연결된 서비스와 프런트를 읽었으며 과거 `app/ai/p5` 독립 서버를 현행 앱으로 취급하지 않았다. 실행 서버·배포·DB·환경변수·실제 모델 호출은 확인하지 않았다. 구현 코드·Grill 결정·HandOff·Figma는 수정하지 않는다.

## 4. 구현 전 논리 계약

### 4.1 요청 범위와 실행 도구의 권한

모델 도구는 **읽기·후보 제시·작업 이동 요청**만 맡는다. 사용자 확인 후 저장은 인증된 UI 요청을 받은 해당 자원 owner가 수행한다. 도구 목록에서 숨기는 것뿐 아니라 서버 dispatch에서도 허용 여부를 검사한다. 도구 호출 내용·문서 본문·파일의 지시를 사용자 승인으로 취급하지 않는다.

| 동작 | 이번 명세의 허용 경계 |
| --- | --- |
| 허용 자료 검색·읽기·원본 링크 제시 | 현재 요청의 범위 안에서 수행. 목록 권한과 원문 읽기 권한 별도 검사 |
| 새 할 일·기록 후보 제시 | 저장 없는 후보. UI가 내용과 날짜 등 필요한 값을 확인 |
| 확인된 새 할 일·기록 등록 | 자원 owner가 확인 payload와 실제 결과를 관리. AI가 등록 성공을 만들어내지 않음 |
| 문서 항목 수정 후보 | 요청 대상 고정, 비교·사용자 반영 뒤 별도 저장. CK 자동 수정 아님 |
| 기존 일정 수정·완료·삭제·복구 | 현재 사용자 일정 UI/API 경로 유지. 이번 명세로 모델 도구에 추가하지 않음. 확장 여부는 §6의 범위 질문 |
| 제품 가격·거래처·정산·재고·홈 메모 쓰기, 외부 발송/게시 | 읽기 권한에서 유추하지 않음. 기존 사용자 관리 경로와 별도이며 이번 에이전트 쓰기 범위에 추가하지 않음 |

요청별 `ContextScope` 논리 레코드는 인증 주체, project_id, conversation_id 또는 doc_id/section_id, 선택 범위의 revision, 포함 유형/자료, 제외 ID, 원 대화에서 승계한 제외, 적용 시점을 가진다. actor/소유 범위는 서버가 결정하며 모델이 인자로 넓힐 수 없다. 외부 참고 0개면 허용된 현재 대화 이력으로 계속한다. 다른 대화는 사용자가 지정한 경우에만, 다른 프로젝트는 명시 허용된 범위에서만 읽는다.

선택 범위는 다음 요청에 적용한다. 실행 중 선택 UI 변경이 과거 답변을 다시 쓰지는 않는다. 실제 읽기 직전에는 현재 접근 권한·삭제 여부를 재확인하고, 새 요청·이어서 생성에는 최신 범위와 제외를 다시 적용한다. 같은 항목의 선택은 유지하고 다른 항목의 선택을 자동 복사하지 않는다.

### 4.2 내부 검색과 원문 읽기

논리 포트는 `search_sources(scope, query, kinds, cursor)`와 `read_sources(scope, source_refs, range)`로 분리한다. 공개 endpoint 이름·검색 엔진은 미확정이다. 기존 `read_project_sections`를 유지하더라도 준비된 요약 반환과 추가 원문 조회를 결과에 구별한다.

- 검색은 허용된 자료의 ID·유형·제목·범위·일치 부분·원본 이동 대상만 반환한다. 명시 선택 없는 과거 대화 본문은 검색 대상으로 넣지 않는다. 검색 결과에 없다는 이유로 자료 자체가 없다고 단정하지 않는다.
- 원문 읽기는 검색에서 받은 식별자 또는 사용자가 지정한 식별자를 자원 owner에서 검증한다. 모델이 만든 임의 ID·다른 프로젝트 ID를 그대로 조회하지 않는다. 사용자 지정 파일은 GD-048에 따라 지원/접근 확인 뒤 원문을 읽는다. 목록의 모든 파일 원문을 자동으로 읽는 규칙은 추가하지 않는다.
- `SourceRef`는 kind, id, 소유 범위, 필요 시 doc/section, 읽은 revision 또는 버전 미제공 표시, fetched_at, 읽은 구간, 원본 이동 대상, 읽기 상태를 가진다. 목록 조회·입력에 실제 제공·답변 근거 연결을 구분한다. 사용 출처 안내에 단순 목록 노출 자료를 섞지 않는다.
- 결과는 `complete / partial / empty / unavailable / forbidden / unsupported`의 의미를 구분한다. 실제 공개 enum은 owner와 합의한다. 부분 결과에는 읽은 범위·남은 범위 또는 cursor·잘림 이유를 제공한다. 자료 없음과 조회 실패를 같은 빈 배열로 표현하지 않는다. 권한 없는 자료의 존재/제목을 오류로 노출하지 않는다.
- 다음 원문 구간·검색 페이지를 읽어 더 탐색할 수 있어야 한다(GD-001~003). 같은 입력으로 같은 실패를 무한 반복하지 않는다. 기존 실행 예산·중단·진전 없음 경계를 유지하며, 상한에 도달하면 확인 범위와 남은 부분을 알린다. 최신 20개/5개/30개를 제품 전체 검색 범위로 확정하지 않는다.
- 이력·요약·선택 답변·후보가 참조한 출처를 추적한다. 제외된 자료에서만 나온 내용은 재사용하지 않는다. 섞인 정보에서 허용 부분을 검증해 분리할 수 없으면 그 단위를 입력에서 뺀다. 원문이 접근 불가여도 이전 답변에 있었다는 이유로 우회하지 않는다.

일반 대화에는 필요한 기본 정보와 범위 내 자료를 제공하되, 모든 원문을 한 번에 밀어 넣는 방법을 검색 완료로 간주하지 않는다. 원문 prefix를 요약으로 대체하는 압축 정책 변경도 이번 보완에 포함하지 않는다. 실제 입력 예산·발송 계수는 기존 D-02를 따른다.

### 4.3 일정 읽기

`query_tasks(scope, date_from?, date_to?, completion?, ids?, cursor?)`를 일정 owner에 연결하는 논리 포트를 둔다. 날짜 구간은 **할 일에 정한 날짜**를 뜻한다. 날짜를 빼면 허용된 프로젝트 범위에서 조회하며, 완료/미완료는 명시 조건을 따른다. 시간대는 현재 제품의 한국 날짜 기준을 사용한다. 상대 날짜는 실제 날짜 범위를 함께 안내한다.

각 결과에는 task_id, title, date, note, done, revision, 읽은 시점, 사용 가능한 원 문서/항목/대화 연결, 목적 ID 목록을 포함한다. 아직 owner가 제공하지 않는 연결/목적은 미제공으로 표시하며 모델이 채우지 않는다. 전체 결과인지, 더 읽을 결과가 있는지 반환한다. 같은 일정은 홈·문서·채팅에서 같은 ID로 식별한다.

‘다음 주 미완료 일정’은 날짜 구간+미완료 조회다. ‘완료된 일정 중 다음 주 날짜로 잡힌 일’은 날짜 구간+완료 조회다. **‘지난주에 완료 처리한 일’은 완료 시점 데이터가 필요**하며 현재 done만으로는 답할 수 없다. owner가 완료 시점 이력을 제공하기 전에는 조회 가능 범위를 설명한다. due date나 updated_at을 완료일로 가장하지 않는다.

사용자가 현재 상태를 다시 물으면 새 요청에서 재조회한다. 이전 답변의 ‘미완료’를 현재 상태로 복사하지 않는다. 삭제/접근 불가와 상태 변경을 구별하며, 이 조회가 문서 완료·할 일 완료를 바꾸지 않는다. 계정 전체 일정 UI가 있더라도 현재 프로젝트 AI의 자동 조회 범위를 계정 전체로 확대하지 않는다.

### 4.4 일반 대화와 문서가 공유하는 할 일 제안·등록

`propose_tasks`는 일반 대화 또는 문서 항목에서 **후보**를 만드는 공통 논리 동작이다. 현재 문서 전용 `suggest_tasks` 파서·등록 중복 방지를 재사용 가능한 부분으로 검토한다. 일반 대화에서 별도 가짜 문서/항목을 생성하여 기존 API에 끼워 넣지 않는다.

1. 서버가 proposal_id와 출처를 부여한다. 후보는 원 project/conversation/message/run 및 선택적 doc/section, title, note, suggested_date, 날짜 근거, 사용 출처, 후보 버전을 가진다. 원 출처는 클라이언트·모델이 임의로 바꾸지 못한다.
2. 근거가 부족한 날짜는 미정 후보로 둔다. 상대 날짜의 기준일과 환산 날짜를 확인한다. 후보는 아직 일정이 아니며 미정 상태로 대화에 남길 수 있다. **실제 등록은 선택한 모든 후보의 날짜를 사용자가 확인한 뒤** 실행한다(GD-055).
3. UI에서 후보별 선택·내용·날짜·목적을 검토한다. 목적은 0개 또는 복수 가능, 사용자 선택이며 전부 자동 선택하지 않는다. 문서에서 유래하면 GD-064의 문서 목적 후보를 적용한다. 취소·더 이야기하기·닫기·응답 없음은 등록하지 않는다.
4. 등록 요청은 확인한 후보 버전과 수정 payload, 선택 ID, 요청 식별자를 보낸다. 실제 필드명·확인 저장 위치는 J-02에서 합의한다. 서버는 소유·현재 허용 상태·날짜·목적 유효성과 확인 내용 일치를 검증한다. 사용자 수정이 반영되지 않은 최초 AI 후보를 대신 저장하지 않는다.
5. 한 후보는 한 일정에 연결한다. 이미 등록된 후보는 기존 task_id·현재 상태를 반환한다. 동일 후보를 다른 내용으로 재전송해 기존 일정을 몰래 수정하지 않는다. 삭제된 연결 일정도 새 일정 생성이나 복구로 자동 처리하지 않고 상태와 사용자 관리 경로를 안내한다.
6. 일괄 요청은 건별 `registered / already_linked / failed / unknown` 결과를 가진다. 성공한 건은 유지, 확정 실패한 건만 재시도한다. 응답 유실·시간 초과는 등록 실패로 간주하지 않고 원 요청 결과를 먼저 조회한다. 제안 ID의 중복 방지만으로 결과 조회 수명·응답 유실까지 해결했다고 주장하지 않는다.
7. 원 대화에 실제 성공 결과·task_id를 연결하고 재방문 시 같은 일정에서 현재 상태를 읽는다. 등록 뒤 자연어 확인 문구는 이 결과를 근거로 표시한다. 문서 완료와 실행 완료는 변경하지 않는다. 문서에서 명시한 별도 완료 요청도 문서 owner가 독립 처리한다.

논리 상태는 `후보 → 확인 대기 → 등록 처리 → 건별 결과`다. 사용자 확인 전 날짜 수정은 후보 편집이며, 등록된 일정의 수정은 별도 행위다. 실패한 한 건 때문에 성공한 일정을 롤백하거나 전체를 재등록하지 않는다. 실제 동시성·고유 인덱스 설치·응답 유실 보장은 J-02의 검증 대상으로 남는다.

### 4.5 기록 제안과 저장

기존 `propose_record`를 새 기능으로 다시 만들지 않는다. 제목·본문 후보를 사용자에게 보여주고, 사용자가 확인한 내용을 record owner가 저장한다. saved record ID와 원 대화/메시지·실제 사용 출처를 연결한다. 저장 성공 전에는 ‘기록했어요’라고 표시하지 않는다. 저장 실패/미확인 시 후보를 유지하고 원 요청 결과를 확인한다.

새 기록 생성은 CK·기존 기록·홈 메모의 덮어쓰기 권한이 아니다. 거래처 기록 원본 읽기도 연락처 등록·변경·외부 연락 발송의 승인이 아니다. 기존 사용자 직접 편집 경로는 유지한다.

### 4.6 답변→문서와 항목 도움

전용 문서 이동 시 `origin_conversation_id / origin_message_id`, 제품 선택 결과, 선택 답변 한 건, 제외 승계 정보를 연결한다. 이 답변은 첫 AI 요청의 제거·교체 가능한 참고이고, 메뉴 진입만으로 문서를 생성하거나 본문에 반영하지 않는다(GD-068). 펀딩/프로젝트 사업계획서만 첫 출시 대상이다. 제품 목록·등록 상태·옵션·가격은 제품 owner 자료를 사용한다. 자유형 `route_document`의 전체 대화 기본 입력을 이 경로에 그대로 사용하지 않는다.

항목 도움의 입력은 대상 항목과 현재 편집 내용, 관련 있는 **같은 문서의 저장 항목**, 같은 항목의 이전 사용자 요청·필요한 답변, 명시 선택한 외부 참고다. 다른 항목의 미저장 초안·도움 이력은 자동으로 읽지 않는다. 같은 항목 이력을 재열람하는 API의 존재만으로 다음 요청에 전달된다고 간주하지 않는다. 항목별 참고 선택은 복원하며 원 대화 제외를 승계한다. 독립적으로 만든 문서는 임의 대화의 제외 설정을 상속하지 않는다.

후보에는 대상 doc/section, 기준 저장 revision·초안 revision, 사용 출처를 고정한다. 스크롤·다른 항목 선택·늦은 응답으로 반영 대상이 바뀌면 안 된다. 비교 확인 뒤 대상에만 반영하고 저장은 별도다. 참조 원본 변경은 GD-052·063·066의 현재 사실/계획값/과거값/접근 불가 의미로 판단한다.

### 4.7 파일 원문과 답변 출처

파일 owner는 형식·크기·페이지/구간·인코딩·텍스트/이미지 처리·계수·권한·원본 위치 지원표를 제공한다. 채팅과 항목 도움 각각의 실제 지원 여부를 명시한다. 설정이 꺼져 있거나 지원하지 않으면 원문을 읽지 못했다고 안내하고 가능한 작업만 진행한다. PDF를 읽을 수 있다고 가정하거나 파일명으로 내용을 요약하지 않는다.

파일별 상태는 지정됨, 접근 확인, 실제 읽음, 일부 읽음, 미지원, 실패를 구분한다. 10개/50,000자/4장 등의 현 코드 상한은 조사값이며 새 제품 보장치가 아니다. 초과·손상·누락을 조용히 건너뛰고 ‘모두 참고함’이라고 안내하지 않는다. 전체 읽기가 불가능하면 실제 범위를 제시하고 허용된 후속 구간 조회 또는 사용자 선택으로 이어간다.

답변 출처는 실제 입력된 원문·이미지와 해당 범위를 근거로 남긴다. 원본 링크의 현재 값이 답변 당시 값과 다를 수 있음을 구분한다. 프로젝트 수정시각을 모든 파일·항목·일정 revision으로 대신 사용하지 않는다. 파서·이미지 해석의 실서비스 지원과 내용 정확성은 실행 검증 전이다.

### 4.8 검토와 이어서 생성

기본 문서 검토는 저장 버전에 대한 필수값·합계·현재 사실 불일치 등 제공된 규칙 검사다. 모델 호출은 0회다. 사용자가 AI 점검을 명시 요청하면 별도 run으로 조언을 제공하고, 대상 문서/항목·검사 버전·참고 범위·결과 상태를 기록한다. AI 점검 실패나 의견만으로 직접 확인·검토 완료를 바꾸지 않는다. 핵심 원가 근거 부재의 최종 완료 정책은 기존 DOC-POL-01 그대로 남긴다.

‘이어서 생성’은 원 run과 부분 답변을 지정한 새 요청이다. 원래 질문·현재 허용되는 부분 답변·남은 작업을 입력하고 원 부분 답변은 보존한다. 이전 run의 로컬 종료·늦은 출력 반영 차단을 확인한 뒤 새 run을 시작한다. 이전 원격 결과 미확인은 자동 재전송하지 않는다. 현재 범위와 출처 제외를 다시 검사하고 동일 내용을 처음부터 덮어쓰는 일반 재시도와 구분한다(GD-070).

## 6. 다시 묻지 않을 결정과 실제 남은 범위

날짜 확인 후 등록, 목적 0개/복수, 실패한 건만 재시도, 문서 완료와 등록 분리, 지정 파일 원문, 같은 항목 이력·관련 저장 항목, 답변 한 건 참고, 기본 규칙/명시 AI 점검 분리, 남은 내용 이어서 생성은 이미 결정됐다. 이 항목들을 재차 Grill 질문으로 올리지 않는다. 자료 검색·ID/버전·결과 조회 포트를 정의하는 일은 내부/공동 설계이며 새 제품 질문이 아니다.
