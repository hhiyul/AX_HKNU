## 2. 사용자 결정과 내부 설계의 경계

GD-035로 AI 문서 수정·삭제는 **대상과 내용을 확인한 UI 최종 승인**, GD-036으로 04 생성·편집·저장 본문은 **Markdown 문자열**, GD-037로 내보내기는 **저장본 기준**, GD-038로 삭제 전 최종 확인과 **사용자 복구 없음**이 FIXED입니다. 작성·수정·삭제의 도구 owner는 04이고 03은 라우팅합니다(Q20). CK 승인(D-UF-041 등), 04 생성 후보의 사용자 저장 선택, 04 AI 수정·삭제 승인은 각기 다른 행위입니다. 승인 화면 배치·문구 및 추가 위임은 미결입니다. 문서 직접 편집의 저장도 현재 사용자 명시 저장 의도를 따릅니다.

아래 3~5절은 새로운 사용자 기능을 추가하지 않는 **내부 어댑터 설계 기준**입니다. 식별자와 오류 이름은 04 내부 Python DTO/포트의 이름이며 공개 HTTP, MongoDB 컬렉션·필드 또는 팀원이 제공한 API 이름이 아닙니다. 외부 매핑은 제공된 명세와 계약 시험 뒤 결정합니다. Markdown 세부 문법과 입력 최대 크기를 임의로 제품 약속으로 확정하지 않습니다.

## 3. 04 내부 자료와 포트 — DESIGNED, 외부 제공은 별도

공통 규칙: 모든 `*_ref`와 `revision`은 불투명한 비어 있지 않은 문자열입니다. 클라이언트/모델의 소유 주장 대신 서버가 인증한 actor와 프로젝트 연결을 재검증합니다. 값이 없는 것, 접근 불가, 읽기 실패, 삭제, 미확인을 구분합니다. 다음 자료는 논리 DTO이고 직렬화·DB 구조의 승인이나 이력 전체 보관 약속이 아닙니다.

| `QueryWriteResult` | 인증 actor·원 요청 ID → `WriteReceipt` | 실제 원 요청 결과를 조회. 결과 조회와 동일 쓰기 재전송 분리. 조회 수명·권한·종료 보장은 owner 확인 필요 |

GD-039에 따라 저장 문서의 출처 manifest에는 원본 사본을 넣지 않습니다. 원본의 식별·상태·revision·출처 및 결손은 보존합니다. `FrozenInput`의 실행 중 임시 원문 저장 위치·암호화·수명·폐기와 백업 정책은 미정이며 삭제된 Chat의 원문 복원을 의미하지 않습니다. revision은 동등성만 비교하며 재사용 불가/변경 시 교체 등 보장이 없으면 변경 감지에 쓸 수 없습니다. 프로젝트·브랜드 등 revision을 제공하지 않는 자료는 비교 불가를 나타냅니다.

## 4. 실행·쓰기 상태와 경합 — DESIGNED 조건부

1. 요청 접수 → 권한/자료 확인 → 일관성 증명된 입력 고정 → 생성 → 후보 또는 질문/실패/중단. 각 실행은 서버 식별자를 갖고 재진입만으로 재실행하지 않습니다. Chat 삭제의 GD-034 적용 범위와 04 별도 실행의 결합은 실제 실행 경계 확인이 필요합니다.
2. 후보 검토 후 사용자가 저장 선택 → 새 Document 저장 요청 → 확인 성공 / 확인된 미반영 종료 / 처리 중·미확인. 성공은 저장소의 확인 결과로만 표시합니다. 미확인은 `QueryWriteResult`로 조회하며 같은 변경을 자동 재전송하지 않습니다.
3. 직접 편집은 같은 문서의 기준 revision에 조건부 저장합니다. AI 수정·삭제는 UI 승인 증거를 대상·기준 revision·승인 범위/내용에 결박해 검증합니다. 내용·대상·revision이 바뀌면 승인 증거를 재사용하지 않고 사용자가 다시 확인·승인해야 합니다.
4. 전체 재생성은 최신으로 선택된 소스의 새 snapshot을 고정하고 전체 후보를 만듭니다. 사용자가 원하면 기존 편집 본문을 명시 참고합니다. 저장은 새 ID이며 원본·미저장 편집을 자동 변경하지 않습니다.
5. 프로젝트 삭제 완료와 문서 저장이 경합할 때, 삭제 확인 뒤 뒤늦은 문서가 생기지 않도록 공통 owner가 **동일한 직렬화 경계**에서 프로젝트 상태 확인과 저장을 보호해야 합니다. 사전 읽기만으로는 보장할 수 없습니다. 트랜잭션/fence/서비스 조정의 실제 방식과 owner는 UPSTREAM_BLOCKED입니다. 개별 Chat 삭제는 이미 저장한 프로젝트 문서를 지우지 않습니다.
6. 다른 세션의 별개 변경은 GD-030을 따릅니다. 같은 원 요청의 결과 확인과 다른 변경의 승인·조건부 쓰기는 분리하며 어느 것도 늦은 원 쓰기로 최신 변경을 덮지 않도록 owner가 보장해야 합니다.

## 7. 구현 착수 순서

1. B-01~04에 대해 각 owner, 실제 명세·제공 시점·계약 시험 책임을 확인합니다. 외부 owner가 아직 동의하지 않은 설계는 제안으로 표시합니다.
2. E-01~03과 03 MC-06~07을 결과 변경 여부에 따라 사용자/디자인팀 또는 내부 설계로 마무리합니다. 04의 추가 편의 기능이 미결이어도 이미 채택된 저장본 출력 경로를 임의 변경하지 않습니다.
3. 별도 구현 승인 후 가짜 포트 중심의 내부 DTO·상태 제어와 PC 시험을 구현하고, 실제 adapter는 제공된 계약에만 바인딩합니다. 외부 동시성·삭제·인증 시험과 실제 Provider/파일 품질 시험은 별도로 기록합니다.
