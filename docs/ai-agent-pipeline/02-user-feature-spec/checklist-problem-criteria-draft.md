# 체크리스트 하위 문제·평가 기준 검토안

상태: **일부 결정 / 나머지 세부 필드·평가 기준 검토 중** · 기준일: 2026-10-30

연결 문서: [사용자 기능명세](ai-pipeline-user-feature-spec-v0.1.md) · [OPEN-UF-02와 결정 기록 D-UF-009~015](open-contracts.md)

## 1. 확정된 방향과 검토 범위

- 여섯 체크리스트는 상위 문제 영역이며 각 항목 내부에는 실제 문제를 분석할 하위 필드·질문·평가 기준이 필요합니다. 버전을 항목 단위로 관리한다고 해서 내용도 한 문단이나 단일 자유 텍스트로 제한하지 않습니다(D-UF-009).
- 각 체크리스트의 내용·상태를 하나의 버전 묶음으로 관리합니다. 내부 필드가 생겨도 필드마다 독립적인 버전이나 `UNSET / DRAFT / DECIDED` 상태를 추가하는 결정은 아닙니다.
- 주 흐름은 Chat입니다. 하위 필드를 모두 채우는 입력 폼이나 고정된 질문 순서를 도입한 것이 아니며, AI 평가·제안은 사용자의 저장·확정 선택을 대신하지 않습니다.
- 고객 접점·판매 경로 가설은 CK-02 고객 선정의 하위 필드로 포함해 저장·평가 대상으로 관리합니다(D-UF-010). 고객 선정의 내부 내용은 구매자·사용자, 구매 목적·상황, 접점·판매 경로와 접근 근거를 연결한 구매 상황별 고객 가설로 관리합니다(D-UF-011).
- 주 사용자는 펀딩을 준비하는 창작자입니다. 고객 가설의 구체화와 실제 검증을 분리하며, 아직 실측되지 않은 값이나 실제 고객 반응을 가설 구체화 완료의 필수 조건으로 요구하지 않습니다(D-UF-012).
- 고객 가설의 구체화 완료에는 접점 후보와 그 경로에서 해당 고객을 만날 수 있다고 보는 이유가 필수입니다. 실제 접근 실적·고객 반응은 필수가 아니며, 이 기준을 Chat 진행·초안 저장의 필수 조건으로 자동 적용하지 않습니다(D-UF-013). 이 요건은 완료 기준의 일부이며 그 자체로 전체 완료를 뜻하지 않습니다.
- 참여·구매 목적은 가설 구체화 완료의 필수 정보입니다. 구체적인 계기·시점은 제안에 영향을 줄 때만 추가 확인하며, 모든 가설에 특정 행사나 날짜를 요구하지 않습니다(D-UF-014). 목적은 가설로 설명할 수 있고 실제 참여 이력·실측 반응은 필수로 요구하지 않습니다.
- 참여·구매자와 실제 사용자의 관계는 제안에 영향을 줄 때만 추가 확인하며, 그렇지 않으면 미정으로 남길 수 있습니다. 응원 목적만으로 사용자가 없다고 추정하지 않습니다(D-UF-015). 관계의 미정과 사용 전제가 없다는 판단은 구분합니다.
- 나머지 세부 필드·평가 방식은 검토안입니다. 가설 개수·복수 가설의 동시 저장·선택 방식, 필드별 필수 수준·허용 미정, 실제 저장 구조, 내부 평가의 표현·세부 충족 조건, 첫 판매 실험 계획의 구성·저장 위치는 아직 합의하지 않았습니다.

## 2. 대표 문제: 상품은 있지만 어떻게 팔아야 할지 모른다

펀딩 준비 단계에서는 상품이나 시제품이 있어도 고객·참여 또는 구매 이유·구성·가격·공급 조건이 아직 가설일 수 있으며 실제 판매·구매 반응의 실측값도 없을 수 있습니다. 이미 확보한 상품 정보를 무시하고 처음부터 상품 선정을 반복할 필요는 없습니다. 무엇이 알려져 있고 무엇이 아직 기획 가설인지 나눠 질문과 제안을 달리해야 합니다. 미실측값을 필수로 제출하게 하거나 임의의 수치로 대신 채우지 않습니다.

예를 들어 구매자가 불분명하면 고객·구매 상황의 가설을, 구매 이유를 설명하기 어렵다면 가치·근거·메시지를, 고객을 만날 방법이 없다면 접점·판매 경로를 살펴봐야 합니다. 단순히 여섯 항목에 문장이 있다는 이유로 이 문제들이 해결됐다고 판정해서는 안 됩니다.

## 3. 항목별 하위 문제와 필드 후보·결정

CK-02에 고객 접점·판매 경로 가설을 포함하는 것은 **결정 D-UF-010**, 구매 상황별 고객 가설 안에서 요소들의 연결 관계를 설계하는 것은 **결정 D-UF-011**, 가설 구체화와 실제 검증을 분리하고 미실측값을 필수로 요구하지 않는 것은 **결정 D-UF-012**입니다. 그 밖의 하위 필드 후보와 세부 평가 기준은 **검토안**이며, 예시는 현재 상품과 사용자의 자료에 맞게 달라질 수 있습니다.

| 항목 | 풀어야 할 하위 문제 | 내부 필드 후보 | 평가·제안에서 구분할 것 |
| --- | --- | --- | --- |
| CK-01 상품 선정 | 무엇을 판매 대상으로 삼으며 이미 무엇을 갖고 있는가 | 기존 상품·시제품·자료, 판매 대상 후보, 선택 이유, 변경 가능한 부분과 제약 | 이미 존재하는 상품과 새 아이디어, 확인된 속성과 가정을 구분. 상품 보유를 다른 항목의 충족으로 취급하지 않음 |
| CK-02 고객 선정 | 누가 어떤 상황에서 누구를 위해 구매하고, 그 고객을 어디서 만날 수 있는가 | 구매자·사용자, 구매 목적·상황, 접점·판매 경로와 접근 근거를 구매 상황별 고객 가설 안에서 연결하는 방향은 결정. 현재 대안 등 추가 필드·실제 저장 구조는 미정 | 같은 가설의 고객·상황·접점이 서로 맞는지, 어떤 연결과 근거가 부족한지 설명. 구매 가능성 가설과 실제 반응을 구분. 필수 입력·충족·완료 조건은 미정 |
| CK-03 구매 가치 기획 | 고객이 다른 대안 대신 왜 이 상품을 선택하는가 | 고객의 문제·구매 동기, 대안과의 차이, 가치 주장과 근거, 전달할 메시지 가설 | 표현이 매력적인 것과 근거가 있는 것을 구분. 차별점 나열이 특정 고객의 구매 이유로 이어지는지 살펴봄 |
| CK-04 상품 구성 결정 | 고객에게 어떤 단위와 조건으로 제안할 것인가 | 판매 단위·규격·구성품·옵션, 포장, 주문·전달 조건 | 제작자가 가진 물건과 고객이 구매할 구성을 구분. 고객·가치 가설에 맞는 구성 대안을 설명 |
| CK-05 가격 원가 결정 | 어떤 가격을 시험하며 그 조건으로 공급할 수 있는가 | 가격 가설, 재료·공임·포장·배송·수수료 등의 비용 입력, 계산 가정·누락, 가격 제약 | 실제 입력과 추정·미확인 값을 구분. 비용을 모른다고 0으로 계산하거나 구매 의사를 검증한 것으로 표시하지 않음 |
| CK-06 제작 가능성 평가 | 제안한 구성·수량·납기를 실제로 감당할 수 있는가 | 제작 가능 수량·시간, 재료 확보, 반복 품질, 주문·배송 처리, 제작 제약 | 단품 제작 경험과 반복 공급 가능성을 구분. 자료가 부족한 납기·수량을 보증하지 않음 |

## 4. 하위 필드를 평가 기준으로 만드는 방법

다음은 단순한 필드 목록을 넘어 평가 계약을 만들기 위한 **작성 틀의 제안**입니다. 실제 필수 속성이나 API 스키마로 확정한 것은 아닙니다.

| 관점 | 정의할 질문 |
| --- | --- |
| 해결할 문제 | 이 정보를 알면 사용자의 어떤 선택이나 행동이 달라지는가? |
| 현재 내용 | 사용자 입력·관찰 자료·AI 가설 중 어떤 내용이 있는가? |
| 근거와 한계 | 무엇으로 뒷받침하며 어디까지 확인되지 않았는가? |
| 부족한 정보 | 어떤 정보가 없어서 다음 제안이나 판단이 달라지는가? |
| 다음 질문·행동 | 더 물을 것, 비교할 대안, 작게 확인할 행동 중 무엇이 도움이 되는가? |

가설을 구체적으로 적었다는 것과 실제 고객 반응으로 검증했다는 것을 같은 의미로 취급하지 않습니다. 사용자 `DECIDED` 상태는 기획 결정이며 검증 완료의 보증이 아니라는 기존 기준을 유지합니다.

## 5. 합의한 제품 범위와 다음 쟁점

### 5.1 고객 접점·판매 경로 가설의 포함 — 결정 D-UF-010

‘어디서 고객을 만나고 판매를 시도할지’를 고객 선정의 하위 필드로 포함해 저장·평가 대상으로 관리합니다. 특정 채널의 선택 이유와 아직 확인하지 못한 가정도 구분해 검토할 수 있어야 합니다. 이 내용을 Chat의 일회성 조언으로만 두는 안은 채택하지 않았습니다.

AI의 가설·제안은 사용자 검토·저장·확정 선택과 서버 검증을 거쳐 CK-02에 반영합니다. CK-02의 내용·상태를 하나의 버전 묶음으로 관리하는 기존 기준을 따릅니다. 고객 접점이나 채널 이름이 있다는 사실만으로 실제 접근 가능성·구매 의사가 검증됐다고 표시하지 않습니다. 연결 관계의 설계 방향은 5.2의 D-UF-011, 가설 구체화와 실제 검증의 분리는 5.3의 D-UF-012를 따릅니다. 실제 저장 구조·필드별 필수 수준·세부 평가 및 완료 판정·화면은 미정입니다.

### 5.2 구매 상황별 고객 가설의 연결 관계 — 결정 D-UF-011

‘20대 여성’, ‘선물’, ‘SNS’를 독립된 값으로만 나열하지 않고, 구매 상황별 고객 가설 안에서 구매자·사용자, 구매 목적·상황, 접점·판매 경로와 접근 근거를 연결해 관리합니다. 평가 시 같은 가설의 요소들이 서로 맞는지와 어떤 연결·근거가 부족한지 설명합니다. 연결 관계를 이후로 미루고 독립된 필드 목록으로만 관리하는 안은 채택하지 않았습니다.

다음 표는 연결 관계의 제품상 의미입니다. DB의 엔터티·관계 테이블·외래 키나 그래프 저장 방식을 지정한 것이 아닙니다.

| 연결 | 설계할 의미 |
| --- | --- |
| 구매자 ↔ 사용자 | 누가 구매하고 누가 사용하는가. 본인 사용과 선물 상황을 구분하며, 두 사람이 같을 수도 있음 |
| 구매자 ↔ 구매 목적·상황 | 그 구매자가 어떤 상황에서 무엇 때문에 구매하려는가 |
| 구매 상황의 고객 ↔ 접점·판매 경로 | 해당 상황의 고객을 그 경로에서 만날 수 있다고 보는 이유는 무엇인가 |
| 제작자 ↔ 접점·판매 경로 | 제작자가 실제로 그 경로에 접근할 수 있다고 보는 근거·제약은 무엇인가 |
| 각 연결 ↔ 근거·미확인 사항 | 사용자 입력·관찰·실제 반응·AI 가설 중 무엇에 기반하며, 아직 확인하지 못한 부분은 무엇인가 |

예를 들어 선물을 구매하는 사람과 선물을 받는 사람은 다를 수 있습니다. 다른 가설에서 제시한 판매 경로를 관계 확인 없이 가져와 이 구매자에게 접근 가능한 경로인 것처럼 취급하지 않습니다. 모르는 연결은 미정으로 남기고 대화에서 점진적으로 구체화합니다.

아래는 연결 관계를 살펴볼 때 사용할 **평가 질문 후보**입니다. 연결 관계를 검토하는 방향은 합의했지만, 질문의 정확한 표현·필수 입력·충족 조건·확정 조건으로 정한 것은 아닙니다.

| 하위 문제 | 평가 질문 후보 |
| --- | --- |
| 구매자와 사용자 | 본인 사용인지 선물인지, 결제하는 사람과 사용하는 사람이 다른지 구분할 수 있는가? |
| 구매 상황·목적 | 어떤 상황에서 무엇 때문에 이 상품을 사려는지 설명할 수 있는가? |
| 고객과 접점의 연결 | 그 접점에서 해당 고객을 만날 수 있다고 보는 이유가 있는가? 사용자가 실제로 접근할 수 있는 경로인가? |
| 근거와 부족한 정보 | 사용자 경험·관찰 자료·실제 반응과 아직 확인하지 않은 가설을 구분하고, 다음에 무엇을 물을지 설명할 수 있는가? |

연결 관계를 설계한다고 해서 모르는 값을 사실로 채우거나 모든 질문에 답해야 Chat을 계속할 수 있도록 만들지 않습니다. 버전과 저장 상태는 CK-02 단위를 유지하며 가설별 독립 버전·상태를 추가하지 않습니다.

### 5.3 고객 가설의 구체화와 실제 검증 분리 — 결정 D-UF-012

내부 평가에서 고객 가설의 구체화와 실제 검증을 분리합니다. 가설 구체화는 대상·구매 또는 참여 상황·접점의 연결을 설명하고, 미확인 사항과 다음에 확인할 행동을 구분할 수 있는 방향으로 평가합니다. 실제 접근 가능성이나 고객 반응의 실측 근거가 없다는 이유만으로 가설 구체화를 미완료로 판정하지 않습니다. 반대로 실측을 요구하지 않는다는 이유로 내용이 비어 있거나 연결이 불명확한 가설을 충분히 구체화했다고 평가하지 않습니다.

예를 들어 집들이 선물을 고르는 사람이 친구에게 줄 상품을 펀딩에서 발견할 수 있다는 가설과 접점 후보가 있어도, 실제 참여·구매 반응은 아직 없을 수 있습니다. 이때 실제 반응을 제출해야 기획을 계속하거나 고객 가설을 구체화할 수 있도록 만들지 않습니다. 알려진 사실·사용자 경험·관찰·AI 가설·추정·미정을 구분하며, 실제로 확보한 근거가 있으면 활용할 수 있습니다. 실측 부재를 0이나 검증된 수치로 대체하지 않습니다.

가설 구체화의 내부 평가, 실제 검증 근거, 사용자 저장 상태 `UNSET / DRAFT / DECIDED`는 구분합니다. 내부 평가의 완료가 자동 저장·확정이나 실제 검증 성공을 뜻하지 않으며, 가설별 새 저장 상태·버전을 추가하지 않습니다. 실제 검증을 분리한 결정만으로 고객 반응 수집 기능이나 외부 검증 절차를 새로 구현하기로 한 것은 아닙니다.

평가 완료의 의미와 펀딩 준비 사용자의 전제는 위 기준을 따릅니다. 접점 후보·연결 이유는 5.4의 D-UF-013, 참여·구매 목적과 계기·시점은 5.5의 D-UF-014, 참여·구매자와 사용자의 관계는 5.6의 D-UF-015로 필수 수준을 정했습니다. 대상 집단의 구체화 등 나머지 정보의 필수 수준·허용 미정과 전체 완료 판정은 아직 합의하지 않았습니다. 가설 구체화에 필요한 정보, Chat 진행·초안 저장·사용자 확정의 검증 조건을 일괄적으로 같은 필수 조건으로 취급하지 않습니다.

### 5.4 접점 후보와 고객을 만날 수 있다고 보는 이유 — 결정 D-UF-013

고객 가설의 구체화 완료로 평가하려면 접점 후보와 그 접점에서 해당 고객을 만날 수 있다고 보는 이유를 설명할 수 있어야 합니다. 이유는 가설 수준이어도 되며 실제 접근 실적이나 고객 반응을 필수로 요구하지 않습니다. 이유가 실제 자료인지 사용자 경험·AI 가설인지 구분하고, 아직 확인되지 않은 접근 가능성·반응은 미정으로 남길 수 있습니다.

| 현재 내용 | 이 필수 요건의 평가 |
| --- | --- |
| 접점 후보가 없음 | 아직 충족하지 않음. AI가 후보를 제안하거나 추가 질문으로 함께 구체화할 수 있음 |
| ‘SNS’ 등 경로 이름은 있지만 해당 고객과 연결하는 이유가 없음 | 아직 충족하지 않음. 그 경로에서 해당 고객을 만날 수 있다고 보는 이유를 구체화해야 함 |
| 접점 후보와 해당 고객을 만날 수 있다고 보는 이유가 가설로 설명됨 | 실제 접근 실적·반응이 없어도 이 요건은 충족할 수 있음. 다른 필수 기준과 전체 완료 판정은 별도 |

사용자가 미리 접점을 조사해 와야만 하는 필수 입력으로 만들지 않습니다. AI는 가설임을 표시해 후보·연결 이유를 제안할 수 있으며, 사용자와 대화에서 구체화합니다. 임의의 사실이나 실적을 만들어 충족한 것으로 표시해서는 안 됩니다.

이 필수 수준은 AI가 고객 가설을 구체화 완료로 평가할 때의 기준입니다. 요건이 미충족이어도 Chat을 계속하고 부분적인 제안을 받을 수 있으며, 초안 저장·사용자 확정의 검증 조건으로 자동 적용하지 않습니다. 저장·확정은 기존 사용자 선택과 서버 검증 기준을 따릅니다. 접점·연결 이유가 있다는 것만으로 고객 가설 전체를 완료 처리하거나 저장 상태를 바꾸지 않습니다.

### 5.5 참여·구매 목적 필수와 계기·시점의 조건부 확인 — 결정 D-UF-014

고객 가설의 구체화 완료로 평가하려면 해당 대상이 무엇을 위해 펀딩에 참여하거나 상품을 구매하려는지 설명할 수 있어야 합니다. 본인 사용·선물·창작자 응원·가치 공감 등은 목적의 예시이며 고정된 선택지나 실제 DB 값으로 정한 것은 아닙니다. 목적은 가설로 설명할 수 있으며 실제 참여 이력이나 반응을 제출해야 하는 기준이 아닙니다.

구체적인 계기·시점은 제안에 영향을 줄 때만 추가 확인합니다. 예를 들어 선물할 시점이 구성·납기·메시지·접점 제안을 바꾸는 상황이면 왜 필요한지 설명하고 확인할 수 있습니다. 창작자 응원처럼 특정 행사·날짜가 없어도 목적을 설명할 수 있다면 모든 가설에 계기·시점을 일괄 요구하지 않습니다.

| 현재 내용 | 이 요건에서의 처리 |
| --- | --- |
| 참여·구매 목적을 설명할 수 없음 | 목적 요건은 아직 충족하지 않음. 추가 질문이나 가설 제안으로 함께 구체화 |
| 목적은 설명되며 구체적인 계기·시점이 제안을 바꾸지 않음 | 목적 요건은 충족할 수 있고, 계기·시점 부재만으로 구체화 완료를 막지 않음 |
| 계기·시점에 따라 제안이 달라지는데 아직 모름 | 추가 확인하고 필요성을 설명. 임의의 행사·날짜를 넣지 않고 조건부 제안·판단 한계를 안내. 미정인 경우의 세부 완료 판정은 후속 계약 |

이 역시 고객 가설 내부 평가의 기준으로, Chat 진행·초안 저장·사용자 확정의 필수 조건으로 자동 적용하지 않습니다. 목적과 접점 요건을 충족한 것만으로 전체 완료·실제 검증 성공·자동 저장을 뜻하지 않습니다. 나머지 정보의 필수 수준과 전체 완료 판정은 미정입니다.

### 5.6 참여·구매자와 실제 사용자의 관계 — 결정 D-UF-015

사용 관계는 제안에 영향을 줄 때만 추가 확인하고, 그렇지 않으면 미정으로 남길 수 있습니다. 같은 사람이 구매·사용하는지, 다른 사람에게 전달하려는지에 따라 가치·메시지·구성·접점 제안이 달라지는 상황이면 필요한 이유를 설명하고 확인합니다. 대화에서 이미 관계가 명확하다면 같은 질문을 반복하지 않습니다.

참여 목적이 ‘창작자 응원’이라는 이유만으로 실제 사용자가 없거나 사용을 전제하지 않는 참여라고 추정하지 않습니다. 응원하면서 리워드를 직접 사용하거나 다른 사람에게 전달할 수도 있습니다. 사용 관계를 모른다는 것과 사용 전제가 없다는 것은 다른 내용이며, 실제로 알려진 범위와 가설·미정을 구분합니다.

| 현재 내용 | 이 요건에서의 처리 |
| --- | --- |
| 본인 사용·선물 등 관계가 대화에서 이미 설명됨 | 그 연결을 활용하며 불필요한 질문을 반복하지 않음 |
| 관계가 미정이고 관계에 따라 제안이 달라짐 | 필요한 이유를 설명하고 추가 확인. 모르면 값을 만들어 넣지 않고 조건부 제안·판단 한계를 안내 |
| 관계가 미정이나 그 정보가 제안을 바꾸지 않음 | 미정으로 남길 수 있으며 그 부재만으로 가설 구체화 완료를 막지 않음 |
| 응원 목적만 알려져 있고 사용 관계는 모름 | 응원을 근거로 사용자가 없다고 채우지 않음. 제안 영향 여부에 따라 위 기준을 적용 |

이는 내부 평가에서 사용 관계의 필수 수준을 정한 것입니다. 관계 구조 자체를 제거한 것이 아니며, 미정을 사용자 없음으로 대체하지 않습니다. 제안 영향의 구체적인 판단 기준과, 필요한 관계가 미정일 때의 세부 완료 판정은 후속 계약입니다. Chat 진행·초안 저장·사용자 확정 조건으로 자동 적용하지 않으며, 다른 필수 요건과 전체 완료 판정은 별도입니다.

### 5.7 남은 하위 계약

- 가설 개수, 여러 후보를 동시에 비교·저장하거나 최종 선택하는 방식.
- 대상 집단을 어느 수준으로 구체화해야 하는지 등 나머지 정보의 필수 수준·허용 미정, 계기·시점·사용 관계가 제안에 영향을 주는 구체적인 판단·질문 기준과 미정인 경우의 완료 판정. 실측값·실제 고객 반응은 필수 조건으로 두지 않음.
- 연결별 근거·미확인 사항의 구체적인 기록, 가설 구체화 평가의 세부 충족·완료 판정과 실제 검증 근거의 표현.
- 실제 필드명·저장 구조·화면, 첫 판매 실험의 구성·평가·저장 위치.

## 6. 검토 반례

- 상품 사진이 있다는 이유로 고객·가치·가격·제작 조건까지 충족됐다고 평가하지 않습니다.
- ‘20대 여성’처럼 넓은 분류만으로 구체적인 구매 상황과 접근 방법까지 확인됐다고 표시하지 않습니다.
- ‘SNS에서 판매’처럼 경로 이름을 적었다는 이유로 실제 고객 접근이나 구매 의사가 검증됐다고 표시하지 않습니다.
- 접점 후보만 적혀 있고 해당 고객을 만날 수 있다고 보는 이유가 없는데 구체화 완료로 평가하거나, 이유가 가설이라는 이유만으로 실제 실적을 필수로 요구하지 않습니다.
- 참여·구매 목적이 불명확한데 완료로 평가하거나, 제안에 영향을 주지 않는 특정 행사·날짜를 모든 가설에 필수로 요구하지 않습니다. 필요하지만 모르는 계기·시점을 임의로 만들어 넣지 않습니다.
- 서로 다른 고객 가설의 구매자·상황·접점을 관계 확인 없이 섞거나 구매자와 사용자가 항상 같다고 단정하지 않습니다.
- 응원 목적만으로 사용자가 없다고 추정하거나, 제안에 영향을 주지 않는 사용 관계의 미정만을 이유로 가설 구체화를 막지 않습니다. 필요한 관계가 불명확하면 사용자 없음으로 대체하지 않고 확인합니다.
- 내부 필드를 늘렸다는 이유로 사용자가 모든 질문에 답해야 대화를 계속할 수 있게 만들지 않습니다.
- 필드가 채워졌다는 것과 근거가 충분하다는 것, 사용자 저장 상태를 구분합니다.
- 펀딩 준비 사용자에게 아직 없는 실제 구매 수·전환율·고객 반응 같은 실측값을 필수로 요구하거나, 부재를 0·추정 사실로 대체하지 않습니다. 실측이 없다는 이유만으로 연결된 가설의 구체화 평가를 막지 않습니다.
- 버전 검증을 체크리스트 항목 단위로 한다는 이유로 내부 필드·질문·평가 기준을 없애지 않습니다.
