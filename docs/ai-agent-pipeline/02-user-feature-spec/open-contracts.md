# AI 파이프라인 사용자 기능명세: 미정 계약

연결 문서: [사용자 기능명세 v0.1](ai-pipeline-user-feature-spec-v0.1.md) · 상태: **일부 결정 / 잔여 계약 OPEN**

이 문서는 기능 초안을 구현 가능한 계약으로 구체화할 때 필요한 쟁점을 관리합니다. 아직 없는 값·스키마·상태 전이·권한을 임의로 확정하지 않습니다. 각 항목의 합의 완료 조건은 합의 결과를 검토하기 위한 기준이며, 그 결과 자체가 아닙니다.

## 현재 읽는 방법: 사용자 기능과 후속 설계의 구분

기존 OPEN-UF-01~15에는 사용자 동작·공통 시스템·구현 계약이 함께 들어 있습니다. 원래 미정·결정 기록은 아래에 유지하고, 현재 정리 순서는 [사용자 기능 정리·완료 계획](user-feature-closure-plan.md)을 따릅니다. 모든 세부 구현 계약을 사용자 기능 단계에서 닫으려는 목록으로 읽지 않습니다.

| 구분 | 현재 작업·읽을 위치 |
| --- | --- |
| 사용자 기능 P0 | 여섯 체크리스트의 목적·정보·평가·완료, 대표 흐름, 제안 수정·저장·확정·재편집·항목 간 영향. 정리·완료 계획 U-01~05 |
| 사용자 기능 P1 | 대표 실패·취소·충돌·결과 미확인, 자료 사용·이력·복구·설정의 사용자 결과. U-06~09 |
| 공동 확인 | 팀원 담당 권한·공통 데이터·삭제, 금액의 사업 기준, 서비스 범위·제한·보존 보장. C-01~03 |
| 후속 모듈 | 정확한 스키마·모델 입력 조립·버전·실행 상태·루프·도구·중복 방지·전달 구현. [이관 대장 M-01~08](../03-module-feature-spec/deferred-design-contracts.md) |

각 OPEN-UF의 세 계층별 대응은 정리·완료 계획 6절에 있습니다. 한 항목 전체를 모듈로 이관하거나, 기술 미정을 모두 닫아야 사용자 기능이 완료되는 것으로 해석하지 않습니다. 사용자 결과를 바꾸는 원자성·반올림·참조 허용·보존 보장 등의 의미는 사용자 기능·공동 계약에서 먼저 정합니다.

**D-UF-001~030은 모두 유효합니다.** 이미 정한 조회 시점·버전 경계·평가·보류·재시도·종료도 계속 유지할 제약입니다. 아래 결정의 이유·대안·트레이드오프·반례를 수정하거나 새 대안으로 대체하지 않습니다. 기존 ‘공통 기준 N’·본문 절·AC 번호는 재정리 전 [합의 세부 참조본](agreement-details-v0.1.md)을 기준으로 읽습니다. 새 사용자 본문은 번호 체계가 달라질 수 있으므로 과거 절 번호를 새 본문에 그대로 대입하지 않습니다.

아래 목록·미정 원문·결정 기록은 재정리 전 내용을 보존한 것입니다. 잔여 쟁점의 계층과 우선순위는 새 정리표를 따르며, 새 Grill 질문이나 전체 OPEN 항목의 완료 처리는 진행하지 않습니다.

## OPEN-UF-01 시스템 기능·권한·업무 분담 연결

- **현재 기준:** 전체 백엔드와 프로젝트 구성·브랜드 생성은 팀원 담당, AI 채팅 파이프라인·하네스는 이 세션의 명세 범위입니다. 상위 시스템 기능명세는 아직 연결되지 않았습니다.
- **미정:** 사용자·계정·역할과 자원 접근 권한, 시스템 기능 ID, UI·백엔드·AI 기능별 책임과 실제 저장 권한의 담당 계약.
- **합의 완료 조건:** 사용자 기능을 시스템 기능에 추적할 수 있고, 누가 조회·실행·저장을 검증하는지 공동으로 식별할 수 있어야 합니다.

## OPEN-UF-02 6개 체크리스트의 세부 평가와 완료 조건

- **상태:** 일부 결정(D-UF-009~020, D-UF-022~025) / 잔여 OPEN.
- **현재 기준:** 6개 항목의 개념과 독립적인 내용·저장 상태는 확인됐습니다. 각 체크리스트의 내용·상태를 하나의 버전 묶음으로 관리하되, 내부에는 실제 사용자 문제를 해결할 하위 필드·질문·평가 기준을 둡니다. CK-02 고객 선정은 구매 상황별 고객 가설 안에서 구매자·사용자, 구매 목적·상황, 고객 접점·판매 경로와 접근 근거를 연결해 저장·평가 대상으로 관리합니다. 평가 결과가 저장 상태를 자동 변경하지 않습니다.
- **평가 의미 결정:** 주 사용자는 펀딩 준비 단계의 창작자이며, 고객 가설의 구체화와 실제 검증을 분리합니다. 미실측값·실제 고객 반응의 확보를 가설 구체화 완료의 필수 조건으로 요구하지 않습니다. 가설의 연결·미확인 사항과 다음 확인 행동을 설명하는 평가와 실제 근거의 확인을 구분합니다(D-UF-012).
- **필수 요건 결정:** 가설 구체화 완료에는 접점 후보와 그 경로에서 해당 고객을 만날 수 있다고 보는 이유가 필수입니다(D-UF-013). 참여·구매 목적도 필수이며 구체적인 계기·시점은 제안에 영향을 줄 때만 추가 확인합니다(D-UF-014). 목적·이유는 가설로 설명할 수 있고 실제 접근 실적·반응은 비필수입니다. 이 요건들은 전체 완료 기준의 일부이며 Chat 진행·초안 저장 조건으로 자동 적용하지 않습니다.
- **사용 관계 결정:** 참여·구매자와 실제 사용자의 관계는 제안에 영향을 줄 때만 추가 확인하며, 그렇지 않으면 미정으로 남깁니다. 응원 목적만으로 사용자가 없다고 추정하지 않고 미정과 사용자 없음을 구분합니다(D-UF-015).
- **대상 구체화 결정:** 대상을 구별할 특성·관계는 가설 구체화 완료에 필수이며, 관심·행동·역할·창작자와의 관계 등으로 설명할 수 있습니다. 예시를 각각 모두 채울 필요는 없고 연령·성별·직업 등은 제안에 영향을 줄 때만 추가 확인합니다. 이미 파악한 내용을 반복 질문하거나 정형 페르소나 작성을 일괄 요구하지 않습니다(D-UF-016).
- **평가 보류 결정:** 중요한 정보가 미정이면 조건별 제안을 제공하고 해당 고객 가설 전체의 구체화 완료는 보류합니다. 구체화된 부분과 남은 미정 사항·영향을 설명하며 Chat과 부분 제안은 계속합니다. 같은 미정 질문을 반복하지 않으며 내부 평가 보류를 저장 상태 변경·별도 저장 제한이나 다른 체크리스트의 보류로 자동 확대하지 않습니다(D-UF-017).
- **중요성 판단 결정:** 조건부 확인 정보는 추천 대상·접점·구성·핵심 메시지·실행 조건 등 핵심 선택이 달라질 때만 중요하게 봅니다. AI는 어떤 선택이 어떻게 달라지는지 설명해야 하며, 단순한 말투·표현·개인화 차이만으로 추가 확인이나 완료 보류를 요구하지 않습니다. 기존 대상·목적·접점의 필수 요건과 반복 질문 방지 기준은 유지합니다(D-UF-018).
- **재질문 결정:** 사용자가 해당 미정 사항을 다시 다루도록 요청했거나 관련 상황의 실질적인 변화로 질문의 필요성·영향이 달라졌을 때만 이유를 설명하고 다시 확인합니다. 시간 경과·대화 진행·미정 값의 존재만으로 반복하지 않고, 이미 답을 확인할 수 있으면 활용합니다(D-UF-019).
- **평가 갱신 결정:** 진행 중인 Chat에서 새 정보가 들어오면 그 정보의 영향을 받는 기준과 남은 보류 사유를 별도 평가 요청 없이 같은 응답에서 갱신합니다. 해소된 사유와 남은 사유를 구분하고 일부 기준의 갱신만으로 전체 완료를 선언하지 않습니다. 평가만으로 저장된 내용·상태를 바꾸지 않으며 연결 전 제안의 프로젝트 기반 재검토는 기존 명시적 요청 원칙을 유지합니다(D-UF-020).
- **평가 표시 연결:** 변경된 평가와 남은 보류 사유는 짧게 안내하고 상세 기준별 결과는 사용자 요청 시 제공합니다. 상세 결과를 요청해야만 보류 사실을 알 수 있게 만들지 않습니다(D-UF-021, OPEN-UF-14).
- **평가 범위 결정:** 고객 선정의 전체 구체화 완료 판정에는 실제 진행 대상으로 정한 가설만 포함하며, 여러 진행 대상은 모두 평가합니다. 미선택 비교 후보의 미정 자체는 전체 완료를 막지 않지만 진행 대상에 영향을 주는 공통 정보·중요한 미정은 계속 평가합니다. 대상 지정은 D-UF-023을 따르며 변경의 세부 규칙·기록·복구는 미정입니다(D-UF-022).
- **진행 대상 지정 결정:** 사용자의 진행 의사와 대상·범위가 명확하면 추가 확인 없이 평가 범위에 반영하고 모호할 때만 확인합니다. 단순한 긍정·AI 추천·최근 언급만으로 진행 선택을 대신하지 않으며 대상 지정과 저장·확정은 구분합니다. 의도·대상 식별의 세부 기준·UX와 변경의 세부 규칙은 미정입니다(D-UF-023).
- **이전 가설 유지 결정:** 진행 대상에서 빠진 이전 가설은 현재 작업의 비교 후보로 남겨 다시 검토·선택할 수 있게 합니다. 비교 후보의 미정 자체는 전체 완료를 막지 않고 대상 변경·후보 유지·재선택만으로 저장된 내용·상태를 바꾸지 않습니다. 재선택 시 전체 재평가는 D-UF-025를 따르며 참조 자료의 갱신·조회와 실제 후보 표시·정리·별도 삭제·보관 기간·기록·복구는 미정입니다(D-UF-024).
- **재선택 평가 결정:** 이전 가설을 다시 진행 대상으로 선택하면 현재 대화·참조 자료로 해당 가설의 전체 기준과 남은 보류 사유를 같은 응답에서 다시 평가합니다. 과거 판정의 승계나 변경 부분만의 평가로 대체하지 않으며 평가만으로 저장된 내용·상태를 바꾸지 않습니다. 프로젝트 연결 Chat의 시작 직전 재조회는 D-UF-026을 따르며 정확한 필드·조회 범위·모델 입력과 실패·미완료·자료 변경 처리는 미정입니다(D-UF-025).
- **미정:** 나머지 하위 필드와 실제 필드·저장 구조, 가설 개수·복수 가설의 동시 저장·선택, 대상을 구별할 특성·관계의 세부 품질 판단과 나머지 정보의 필수 수준·허용 미정·세부 질문·누락 판단·연결별 근거 표현·전체 완료의 충분조건, 접점·연결 이유의 구체적인 표현·품질 판단, 핵심 선택에 미치는 영향 설명의 세부 품질·경계 사례, 전체 완료·보류 해제의 세부 충족 조건과 진행 중인 Chat의 새 정보 외 재평가 계기·범위, 평가 갱신 실패·미완료 처리, 재질문 조건에 대한 상황 변화·사용자 요청의 세부 식별·설명 품질, 미정 사항·질문 이력 및 내부 평가·실제 검증 근거의 표시·기록·복구, 첫 판매 실험 계획의 구성·평가·저장 위치, 확정 요청 시 필요한 검증 조건. [하위 문제·평가 기준 검토안](checklist-problem-criteria-draft.md)은 결정한 범위와 아직 미합의인 후보를 구분하며 전체 필드 계약의 확정을 뜻하지 않습니다.
- **합의 완료 조건:** 같은 자료에서 무엇을 확인할 수 있고 무엇이 부족한지 평가·설명할 기준과 대표 반례가 있어야 합니다. 내부 평가와 사용자 결정 상태를 구분해야 합니다.

### D-UF-009 체크리스트별 버전과 내부 하위 필드·문제 기준의 구분

- **결정일·근거:** 2026-10-30, 사용자가 체크리스트 항목 단위의 버전을 채택하되 내부 필드와 문제의 기준을 실제 문제를 해결할 정도로 세분화해야 한다고 설명했습니다. 대표 문제는 “상품은 있는데, 어떻게 팔아야 할지 모르겠다”입니다.
- **문제 상황:** 여섯 상위 제목이나 서술 칸의 존재 여부만으로는 상품을 이미 가진 사용자의 고객·가치·판매 방법·구성·가격·공급 문제를 분석하기 어렵습니다. 버전 검사 단위를 고르는 것과 도메인 내용을 설계하는 것을 혼동하면 필요한 내부 필드가 빠질 수 있습니다.
- **결정:** 각 체크리스트의 내용·상태를 하나의 자료 묶음으로 버전 관리합니다. 동시에 각 항목 내부에는 하위 필드·질문·평가 기준을 두어 실제 사용자 문제를 구체화합니다. 항목 단위 버전은 내용을 단일 문단이나 자유 텍스트 하나로 제한한다는 뜻이 아닙니다.
- **검토한 대안:** 버전 경계는 ① 체크리스트 항목 단위를 채택하고 ② 항목 내부 필드별 독립 버전은 채택하지 않았습니다. 이 선택을 내부 필드 자체가 불필요하다는 뜻으로 해석하지 않습니다.
- **선택 이유·트레이드오프:** 확정된 상위 제품 개념으로 변경을 추적하면서 문제 분석은 세부 기준으로 진행할 수 있습니다. 대신 같은 항목 내부의 일부만 바뀌어도 그 항목의 버전 변화가 참조 제안에 영향을 줄 수 있습니다.
- **결정 범위:** 여섯 체크리스트 각각의 버전 경계와 내부 필드·평가 기준의 필요성을 정했습니다. 정확한 필드명·계층·필수 여부·완료 조건·근거 표현, 필드별 편집·저장 계약, 실제 API·DB 구조는 미정입니다. 하위 필드별 별도 저장 상태나 버전을 추가하지 않았으며, 프로젝트 기본정보·브랜드·첨부자료의 묶음 경계도 이번 결정에 포함하지 않았습니다.
- **수용 반례:** 항목 단위 버전이라는 이유로 내부 필드·질문·평가 기준을 제거하거나, 여섯 칸에 문장이 있다는 이유로 판매 문제가 해결됐다고 평가하면 안 됩니다. 하위 필드의 존재만으로 필드별 독립 버전·상태나 필수 입력 폼을 도입하면 안 됩니다.
- **반영 위치:** 사용자 기능명세 공통 기준 17, 6절, UF-AI-06, AC-27·28 및 하위 문제·평가 기준 검토안. 세부 문제·평가 기준은 OPEN-UF-02, 실제 자료·저장 검증은 OPEN-UF-03·06·08, 화면은 OPEN-UF-14에 연결합니다. 체크리스트 외 버전 경계보다 하위 문제의 제품 기준을 먼저 논의합니다.
- **후속 결정:** D-UF-010에서 고객 접점·판매 경로 가설을 CK-02 고객 선정의 하위 필드로 포함해 저장·평가하도록 정했습니다. 그 밖의 세부 필드와 구체적인 평가·완료 기준은 미정입니다.

### D-UF-010 고객 접점·판매 경로 가설을 고객 선정의 하위 필드로 저장·평가

- **결정일·근거:** 2026-10-30, 사용자가 A안을 채택하고 고객 접점·판매 경로 가설을 고객 선정의 하위 필드로 포함하도록 반영을 요청했습니다.
- **문제 상황:** 상품이 있어도 고객을 어디서 만나 판매를 시도할지 모르면 판매 방법을 구체화하기 어렵습니다. 접점·경로를 대화 조언으로만 두면 다음 검토에서 현재 가설과 선택 이유·근거를 이어 다룰 기준이 약해집니다.
- **결정:** 고객 접점·판매 경로 가설을 CK-02 고객 선정의 하위 필드로 포함해 저장·평가 대상으로 관리합니다. 채널의 선택 이유와 아직 확인하지 못한 가정을 구분해 검토할 수 있어야 합니다. 실제 반영은 사용자 검토·저장·확정 선택과 서버 검증을 따릅니다.
- **검토한 대안:** A안인 고객 선정의 하위 필드로 관리하는 방식을 채택했습니다. B안인 고객 선정은 구매자·구매 상황 중심으로 두고 접점·판매 경로는 Chat의 실행 제안으로만 관리하는 방식은 채택하지 않았습니다.
- **선택 이유·트레이드오프:** 이후 대화에서 접점·판매 경로의 가설·선택 이유·근거를 이어서 검토할 수 있습니다. 대신 고객 선정에 관리할 기획 정보가 늘고, 구체적인 구조와 평가·편집 기준이 필요합니다.
- **결정 범위:** 고객 접점·판매 경로 가설의 소속과 저장·평가 대상 포함을 정했습니다. CK-02의 내용·상태를 하나의 버전 묶음으로 관리하며, 필드별 별도 상태·버전을 추가한 것은 아닙니다. 고객·구매 상황·접점의 연결 구조, 가설의 세부 구성·필수 입력·근거·완료 조건·화면, 첫 판매 실험 계획의 구성·저장 위치는 미정입니다.
- **수용 반례:** 접점·판매 경로를 일회성 조언으로만 취급해 고객 선정의 저장·평가 대상에서 제외하거나, AI가 생성한 가설을 사용자 선택 없이 저장하면 안 됩니다. 채널 이름만으로 실제 접근 가능성이나 구매 의사가 검증됐다고 표시하면 안 됩니다.
- **반영 위치:** 사용자 기능명세 공통 기준 18, 6절 CK-02, UF-AI-06, AC-29 및 하위 문제·평가 기준 검토안 1·3·5절. 세부 문제·평가는 OPEN-UF-02, 저장·편집·버전은 OPEN-UF-06·08, 이력·화면은 OPEN-UF-12·14와 연결합니다. D-UF-009의 당시 기록은 유지하고 하위 필드 범위의 일부를 구체화합니다.
- **후속 결정:** D-UF-011에서 구매 상황별 고객 가설 안에 고객·상황·접점·접근 근거를 연결해 관리하도록 정했습니다. 실제 저장 구조·가설 개수·필수 입력·완료 조건은 미정으로 유지합니다.

### D-UF-011 구매 상황별 고객 가설 안에서 고객·상황·접점·근거를 연결

- **결정일·근거:** 2026-10-30, 사용자가 A안을 채택하고 연결 관계를 설계하는 방향으로 반영하도록 요청했습니다.
- **문제 상황:** ‘20대 여성’, ‘선물’, ‘SNS’가 독립된 값으로만 있으면 누가 어떤 상황에서 누구를 위해 구매하고 그 고객을 어느 경로에서 만날 수 있는지 이어지지 않을 수 있습니다. 다른 후보의 고객·상황·접점이 섞이면 제안의 대상과 근거도 모호해집니다.

- **결정 범위:** 재선택한 가설의 전체 평가 범위와 기존 판정의 자동 승계 금지를 정했습니다. 기존 필수 수준·조건부 확인·미정 허용 기준은 유지하며 모든 미정 값을 필수 입력으로 바꾸지 않습니다. 다른 가설·모든 비교 후보·여섯 체크리스트 전체를 무조건 다시 평가하는 결정은 아니며 공통 영향 정보의 평가는 기존 기준을 따릅니다. 중요한 미정에는 D-UF-017을 적용하고 결과 표시는 D-UF-021을 유지합니다. 프로젝트 Projection 등의 재조회·갱신 시점·범위·실제 모델 입력, 자료 확인·평가 실패·미완료와 진행 중 자료 변경·기록·복구는 미정입니다. 연결 전 제안의 프로젝트 기반 재검토는 D-UF-003~008의 기존 계약을 유지하고 새 저장 상태·버전·API 필드는 추가하지 않습니다.
- **수용 반례:** 예전 완료 판정을 그대로 현재 결과로 표시하거나 변경된 일부 기준만 평가해 전체 재평가를 대체하면 안 됩니다. 재평가만으로 저장 내용·상태를 변경하거나 기존에 허용한 미정·실측 부재를 일괄 필수로 바꾸면 안 됩니다. 이 결정만으로 최신 프로젝트 자료가 재조회됐다고 보장하면 안 됩니다.
- **반영 위치:** 사용자 기능명세 공통 기준 33, UF-AI-06, AC-57~59 및 하위 문제·평가 기준 검토안 1·5.16절. 참조 자료 갱신·범위는 OPEN-UF-03, 평가·실패·전체 완료의 세부 계약은 OPEN-UF-02, 실제 참조 버전·저장·확정은 OPEN-UF-06·07·08, 표시·기록·복구는 OPEN-UF-12·14에 연결합니다. D-UF-024의 당시 미정 기록을 유지하고 재선택 평가의 범위를 구체화합니다.
- **후속 결정:** D-UF-026에서 프로젝트 연결 Chat의 재선택 평가 시작 직전에 같은 프로젝트의 Projection을 다시 조회하고 그 자료로 전체 기준·남은 보류 사유를 평가하도록 정했습니다. 재조회 실패·이전 자료 대체·재시도와 정확한 필드·조회 범위·모델 입력·자료 변경 처리는 미정입니다.







## OPEN-UF-03 컨텍스트 범위

- **상태:** 일부 결정(D-UF-001~008, D-UF-026) / 잔여 OPEN.
- **현재 기준:** 독립 Chat과 프로젝트 연결 Chat이 있습니다. 독립 Chat은 같은 대화에서 프로젝트를 최초 한 번 첨부하듯 연결하고 해당 프로젝트의 Projection 정보를 불러올 수 있습니다. 연결된 Chat의 체크리스트 저장 대상은 해당 프로젝트 하나로 고정하며, 다른 프로젝트 작업은 새 Chat에서 시작합니다. 필요한 프로젝트·브랜드·기획 항목을 조회해 참고하고 저장 상태와 새 제안을 구분합니다. 저장 대상 고정과 참고 자료의 선택·해제는 구분합니다.
- **추가 결정:** 연결 전 제안은 프로젝트의 Projection 정보를 바탕으로 재검토한 뒤 저장합니다(D-UF-003, OPEN-UF-06의 결정 기록). 직접 저장은 허용하지 않으며, 재검토만으로 저장되지 않습니다. 프로젝트 연결 시 Projection은 불러오되 재검토를 자동 실행하지 않고 사용자가 명시적으로 요청할 때 실행합니다(D-UF-004, OPEN-UF-10의 결정 기록).
- **대상 결정:** 명시적인 재검토 요청에서 요청·문맥상 대상이 명확하면 바로 실행하고, 모호한 경우에만 확인합니다. 최신 제안이나 전체 제안을 임의의 기본 대상으로 삼지 않습니다(D-UF-005, OPEN-UF-06의 결정 기록).
- **조회 시점 결정:** 명시적인 재검토 요청의 대상이 정해지면, 재검토 시작 직전에 Projection을 다시 조회하여 그 조회 결과를 재검토 자료로 사용합니다(D-UF-006).
- **재선택 평가 조회 결정:** 프로젝트 연결 Chat에서 이전 가설을 재선택하면 의사·대상·범위가 명확해진 뒤 실제 평가 시작 직전에 같은 프로젝트의 Projection을 다시 조회합니다. 그 자료로 전체 기준·남은 보류 사유를 평가하고 조회·평가만으로 저장된 내용·상태를 변경하지 않습니다. 실패 시 평가 보류·재시도 안내·Chat 지속은 D-UF-027을 따르며 재시도·평가 재개와 실제 필드·조회 범위·모델 입력·자료 변경의 세부 처리는 미정입니다(D-UF-026).
- **실행 중 변경 결정:** 시작 직전 조회 자료로 재검토를 완료한 뒤 변경 여부를 확인합니다. 변경이 확인된 해당 제안은 이전 정보 기반으로 표시해 저장을 보류하고, 사용자의 명시적인 재요청을 받습니다(D-UF-007, OPEN-UF-08의 결정 기록).
- **변경 판정 결정:** 제안별 실제 입력·조회 자료 묶음과 그 버전을 연결해 변경 여부를 판정하고, 저장 대상 항목의 버전도 별도로 검증합니다. Projection 전체를 AI에 전달하면 전체 자료 묶음을 참조 범위에 포함합니다(D-UF-008, OPEN-UF-08의 결정 기록).
- **미정:** 최초 연결의 구체적인 UX·조회 실패 시 연결 처리, Projection의 필드·조회 범위·조회 API·재검토 외 갱신 방식·모델 입력 범위, 자료 묶음의 정확한 경계·버전 형식·참조 추적과 이력·요약·이전 도구 결과의 포함 방식, 재조회 실패 시 복구·기존 정보 대체 사용 가능 여부, 변경 확인 실패 시 처리, 완료 후 저장까지의 근거 재검증·충돌 처리, 연결 전 이력·내부 평가의 모델 입력 취급, 재검토 요청의 UX·의도 및 대상 식별의 세부 기준·결과 비교, 다른 프로젝트의 읽기 전용 참조 허용 여부·범위, 항목의 수동 선택과 AI 선택 범위, 브랜드·사진 자동 포함, 참조 해제 후 기존 대화에 남은 정보의 취급, 전송 범위 안내.
- **합의 완료 조건:** 사용자 선택과 실제 모델 입력의 관계를 설명할 수 있어야 합니다. 연결 해제·권한 변경·자료 삭제 이후 무엇을 더 이상 사용할 수 없는지 정해야 합니다.

### D-UF-001 프로젝트 연결 Chat의 저장 대상 고정

- **결정일·근거:** 2026-10-30, 사용자가 A안을 선택하고 “프로젝트에 연결된 Chat은 저장 대상을 하나로 고정하고, 다른 프로젝트 작업은 새 Chat에서 시작”하도록 명세 반영을 요청했습니다.
- **문제 상황:** A 프로젝트의 가격을 논의하다 B 프로젝트로 주제가 바뀌었을 때, 기존 제안의 소속과 저장 대상이 모호해지면 다른 프로젝트에 반영할 수 있습니다.
- **결정:** 프로젝트에 연결된 Chat의 체크리스트 저장 대상은 해당 프로젝트 하나입니다. 연결된 Chat 안에서 대상을 바꾸거나 제안마다 다른 저장 대상을 선택하지 않습니다. 다른 프로젝트 작업은 새 Chat에서 시작합니다.
- **검토한 대안:** A안은 저장 대상 고정, B안은 대화 중 저장 대상 전환, C안은 제안마다 여러 프로젝트 중 저장 대상 선택이었습니다. B·C안은 이번 흐름에 채택하지 않았습니다.
- **선택 이유·트레이드오프:** 대화·평가·제안의 소속을 명확히 하고 오저장을 줄입니다. 대신 다른 프로젝트 작업에는 Chat 이동이 필요합니다. B·C안에서 필요한 이전 이력·평가·제안의 재귀속과 복수 저장 대상 관리를 현재 흐름에 도입하지 않습니다.
- **결정 범위:** 저장 대상의 수와 연결 이후 변경 금지를 정했습니다. 다른 프로젝트의 읽기 전용 참조와 독립 Chat의 최초 연결·이력 이전 방식은 결정하지 않았습니다. 삭제·권한 변경 이후의 안내·복구도 별도 미정 계약으로 유지합니다.
- **수용 반례:** A 연결 Chat의 대상을 B로 바꾸거나 A에서 만든 제안을 B의 체크리스트에 반영하면 안 됩니다. 참고 자료를 선택·해제한 것을 저장 대상 변경으로 취급하면 안 됩니다.
- **반영 위치:** 사용자 기능명세 공통 기준 9, 5.1·5.2, UF-AI-01·02, AC-15. 공통 백엔드와의 정확한 검증 계약은 OPEN-UF-01·08에 연결해 구체화합니다.

### D-UF-002 독립 Chat의 최초 프로젝트 연결·Projection 조회

- **결정일·근거:** 2026-10-30, 사용자가 ①안을 채택하고 프로젝트를 첨부하는 느낌으로 해당 프로젝트의 Projection 정보를 불러오되 UX는 아직 미정이라고 설명했습니다.
- **문제 상황:** 프로젝트 없이 상품 아이디어를 논의하다 방향이 잡히면, 그 대화를 해당 프로젝트의 실제 기획으로 이어갈 수 있어야 합니다.
- **결정:** 독립 Chat에서 같은 대화를 이어가며 프로젝트를 최초 한 번 연결할 수 있습니다. 프로젝트를 첨부하듯 연결하고 해당 프로젝트의 Projection 정보를 불러옵니다. 연결 이후에는 D-UF-001에 따라 저장 대상을 고정합니다.
- **검토한 대안:** ① 같은 Chat의 최초 연결 허용을 채택했습니다. ② 독립 Chat은 유지하고 프로젝트 작업에는 반드시 새 Chat을 시작하는 방식은 채택하지 않았습니다.
- **선택 이유·트레이드오프:** 아이디어 탐색에서 프로젝트 기획으로 대화를 이어갈 수 있습니다. 대신 연결 전 가정·평가·제안을 새로 불러온 프로젝트 정보와 어떻게 대조하고 재사용할지 추가 계약이 필요합니다.
- **결정 범위:** 첨부하는 느낌의 연결 의도와 Projection 조회를 정했습니다. 버튼·선택창·표시 위치·연결 완료 안내 등 UX는 OPEN-UF-14와 함께 미정으로 유지합니다. Projection의 정확한 스키마·조회 API·버전·갱신·모델 입력 범위, 연결 전 이력·평가·제안의 재사용·재평가·저장 가능 조건은 결정하지 않았습니다.
- **수용 반례:** 최초 연결을 위해 새 Chat을 반드시 시작하도록 강제하거나, 연결만으로 이전 제안을 검증 완료·저장 완료로 취급하면 안 됩니다. 첨부라는 표현을 연결 이후 저장 대상 변경 허용으로 해석하면 안 됩니다.
- **반영 위치:** 사용자 기능명세 핵심 개념, 공통 기준 10, 5.1, UF-AI-01·02, AC-16. 연결 전 제안 처리는 OPEN-UF-03·06, 조회·모델 입력 계약은 OPEN-UF-01·03, UX는 OPEN-UF-14와 연결합니다. D-UF-001에서 남겼던 최초 연결 허용 여부를 이번 결정으로 구체화했으며, 당시 결정 기록은 유지합니다.
- **후속 결정:** 재검토 시작 직전 Projection 재조회는 D-UF-006에서 정했습니다. 정확한 필드·API·버전과 그 밖의 갱신 방식은 미정으로 유지합니다.

### D-UF-006 재검토 시작 직전 Projection 재조회

- **결정일·근거:** 2026-10-30, 사용자가 ①안을 선택하고 재검토 시작 직전에 Projection을 다시 조회하도록 반영을 요청했습니다. 재검토 도중 프로젝트 정보가 바뀌는 경우는 다음 논의로 남겼습니다.
- **문제 상황:** 프로젝트 연결 시 상품 구성이 200ml였어도, 다른 화면에서 300ml로 바뀐 뒤 이전 가격안의 재검토를 요청할 수 있습니다. 연결 당시 정보만 사용하면 바뀐 프로젝트 조건을 놓칠 수 있습니다.
- **결정:** 명시적인 재검토 요청의 대상이 정해지면, 실제 재검토 시작 직전에 같은 프로젝트의 Projection을 다시 조회하여 그 조회 결과를 재검토 자료로 사용합니다. 대상 확인 질문에 답하는 동안에도 정보가 바뀔 수 있으므로 연결 시점이나 확인 질문 전 조회만으로 대신하지 않습니다.

- **현재 기준:** 사용자는 진행·종료·실패·취소 결과를 구분하고, 화면 이동·재접속만으로 새 유료 요청을 발생시키지 않습니다. 연결 전 제안의 재검토는 사용자의 명시적인 요청 시 실행합니다. 프로젝트 연결 시 Projection은 불러오되 재검토를 자동 실행하지 않으며, 기존 제안의 저장 시도만으로도 재검토를 자동 실행하지 않습니다.
- **대상 결정:** 요청·문맥상 명확한 대상은 추가 확인 없이 실행하며, 모호한 대상은 질문으로 확인한 뒤 실행합니다(D-UF-005).
- **조회 기준:** 재검토 시작 직전에 Projection을 다시 조회합니다(D-UF-006). 이 조회가 실행 도중·완료 후 변경과 저장 충돌의 처리를 대신하지 않습니다.
- **완료 기준:** 시작 자료로 재검토를 완료한 뒤 변경 여부를 확인하고, 변경이 확인된 해당 제안은 저장을 보류해 명시적인 재요청을 받습니다(D-UF-007). 정보 변경을 이유로 즉시 중단·자동 재실행하지 않습니다.
- **버전 기준:** 제안별 실제 입력·조회 자료 묶음의 버전으로 변경을 판정하고 저장 대상 항목 버전도 별도로 검증합니다(D-UF-008).
- **재선택 조회 실패 결정:** 재선택 평가를 위한 Projection 재조회가 실패하면 해당 평가를 보류하고 재시도를 안내하며 Chat·부분 제안은 계속할 수 있습니다. 이전 자료로 평가 완료를 대신하거나 실패·보류·부분 제안만으로 저장된 내용·상태를 변경하지 않습니다(D-UF-027).
- **보류 후 재시도 결정:** 보류 안내 후에는 사용자가 명시적으로 재시도를 요청할 때만 실패한 Projection 조회를 다시 시도합니다. 재시도 안내·연결 회복·시간 경과·다른 대화만으로 자동 재시도하지 않으며 요청·재조회만으로 저장·확정하지 않습니다. 성공 후 동일하고 명확한 대상의 재개는 D-UF-029를 따르며 요청의 세부 식별·UX와 대상 변경·동시 요청·기록·복구는 미정입니다(D-UF-028).
- **조회 성공 후 재개 결정:** 재시도 조회가 성공하고 보류했던 평가 대상이 그대로이며 명확하면 추가 확인 없이 같은 응답에서 새 자료로 전체 기준·남은 보류 사유를 다시 평가합니다. 재개·평가만으로 저장된 내용·상태를 바꾸지 않습니다. 진행 대상에서 빠진 가설의 보류 평가 취급은 D-UF-030을 따르며 그 밖의 대상 변경·불명확 시 처리는 미정입니다(D-UF-029).
- **진행 대상 제외 시 보류 종료:** 진행 대상에서 빠진 가설의 보류 평가는 종료하고 가설은 비교 후보로 유지합니다. 다시 선택하면 종료된 보류 평가를 재개하는 대신 현재 자료로 새로 평가하며 저장된 내용·상태는 자동으로 바꾸지 않습니다(D-UF-030).
- **미정:** 실행 상태와 종료 조건, 재검토 요청의 UX·의도 및 대상 식별의 세부 기준, 확인 질문의 응답·대기·취소, 재조회 실패 시 복구, 자료 묶음의 경계·버전 형식·참조 추적과 확인 실패 처리, 완료 후 저장까지의 근거 재검증·충돌, 추가 사용자 입력 대기, 동시 요청 범위, 취소 가능 시점과 완료 판단, 일반 실패의 자동 재시도 허용 조건, 도구 결과의 재사용, 재시작 복구.
- **합의 완료 조건:** 요청 접수 전 실패, 도구 실행 중 취소, 모델 응답 후 취소, 재접속과 재전송을 구분하는 사용자 결과가 있어야 합니다. 내부 반복·도구 호출의 제한값은 별도로 정해야 합니다.

### D-UF-004 연결 전 제안은 명시적인 요청 시 재검토 실행

- **결정일·근거:** 2026-10-30, 사용자가 ②안을 선택하고 프로젝트 연결 시 Projection은 불러오되 재검토는 자동 실행하지 않고 명시적으로 요청할 때 실행하도록 반영을 요청했습니다.
- **문제 상황:** 사용자가 프로젝트를 첨부한 목적이 이전 제안 저장이 아니라 새 질문을 위한 참조일 수도 있으므로, 연결 자체를 재검토 실행 의도로 취급하면 불필요한 AI 작업이 발생할 수 있습니다.
- **결정:** 프로젝트 연결 시 Projection을 불러옵니다. 연결 전 제안의 AI 재검토는 사용자가 명시적으로 요청할 때 실행합니다. 프로젝트 연결이나 기존 제안의 저장 시도만으로 재검토를 자동 실행하지 않습니다. 재검토 전 저장 시도에는 재검토의 필요성을 안내하고 명시적인 요청을 받습니다. 재검토 후 사용자 결과 확인·저장 선택은 D-UF-003을 따릅니다.
- **검토한 대안:** ① 연결 직후 자동 실행, ② 명시적인 재검토 요청 시 실행, ③ 기존 제안의 저장 시도 때 자동 실행을 비교했습니다. ②를 채택하고 ①·③은 채택하지 않았습니다.
- **선택 이유·트레이드오프:** 실행 의도를 명확히 하고 실제로 사용하지 않을 제안의 재검토에 드는 시간·비용을 줄입니다. 대신 사용자가 재검토를 요청하는 단계가 필요합니다.
- **결정 범위:** 연결 전 제안 재검토의 실행 조건을 정했습니다. 자연어 요청·별도 동작 등 실제 UX, 명시적 의도 식별 기준과 모호한 요청 처리, 대상 제안의 범위, 비용 안내·실패·취소·재시도는 미정입니다. 일반 대화의 응답·도구 호출을 전부 수동 실행으로 제한한 결정은 아닙니다.
- **수용 반례:** 프로젝트를 첨부하거나 기존 제안의 저장을 시도한 것만으로 재검토를 시작하면 안 됩니다. 일반 질문 전송을 이전 제안 재검토 요청으로 취급하면 안 됩니다. 명시적 재검토 요청을 결과 내용의 저장·확정 승인으로 간주하면 안 됩니다.
- **반영 위치:** 사용자 기능명세 공통 기준 12, 5.4, UF-AI-02·05·09, AC-16·18·19. 대상 범위·요청 식별은 OPEN-UF-06·10, UX는 OPEN-UF-14, 비용·실행 복구는 OPEN-UF-10·11과 연결합니다. D-UF-003의 당시 기록은 유지하고 후속 결정을 연결합니다.

- **결정일·근거:** 2026-10-30, 사용자가 A안을 채택하고 변경된 평가와 남은 보류 사유는 짧게 안내하며 상세 기준별 결과는 사용자가 요청할 때 제공하도록 반영을 요청했습니다.
- **문제 상황:** 선물용이라는 새 정보가 반영된 뒤 매번 전체 기준별 평가표를 보여주면 반복되는 내용과 응답 길이가 늘어납니다. 반대로 짧게 안내하면서 보류 사유를 감추면 전체 구체화나 저장이 완료됐다고 오해할 수 있습니다.
- **결정:** 평가가 갱신된 응답에서는 변경된 평가와 남은 보류 사유를 짧게 안내합니다. 상세 기준별 결과는 사용자가 요청할 때 제공하며 전체 기준별 평가표를 기본 응답마다 나열하지 않습니다. 짧은 안내에서도 전체 구체화 완료의 보류 여부와 남은 사유를 알 수 있어야 합니다.
- **검토한 대안:** A안인 변경점·남은 보류 사유 중심의 짧은 안내와 요청 시 상세 제공을 채택했습니다. B안인 평가 갱신 응답마다 해당 고객 가설의 전체 기준별 평가표를 기본 표시하는 방식은 채택하지 않았습니다.
- **선택 이유·트레이드오프:** Chat의 반복 내용과 읽기 부담을 줄일 수 있습니다. 대신 전체 기준별 현황을 확인하려면 사용자의 추가 요청이 필요하며, 요약에 보류 사실·사유가 드러나게 하는 표현 기준이 필요합니다.
- **결정 범위:** 평가 결과의 기본 표시량과 상세 제공 조건을 정했습니다. D-UF-020의 동일 응답 내 관련 평가 갱신은 유지하며 요약 표시를 이유로 평가 자체를 생략하지 않습니다. 요약·상세 제공만으로 저장된 내용·상태를 변경하거나 사용자 저장·확정 선택으로 간주하지 않습니다. 정확한 길이·문구·표 형식·표시 위치, 상세 요청의 UX·범위 식별과 상세 결과의 기준 시점·최신성 안내, 영속 기록·복구는 미정입니다. 접기·펼치기 버튼·별도 화면·API 필드를 정한 것은 아닙니다.
- **수용 반례:** 짧게 안내한다는 이유로 남은 보류 사유를 숨기거나 구체화·저장 완료처럼 표시하면 안 됩니다. 사용자가 상세 기준별 결과를 요청했는데 요약만 반복하거나, 요청이 없는데 기본 응답마다 전체 기준별 평가표를 나열하면 안 됩니다. 상세 제공을 저장·확정으로 취급하면 안 됩니다.
- **반영 위치:** 사용자 기능명세 공통 기준 29, UF-AI-06·08, AC-50·51 및 하위 문제·평가 기준 검토안 1·5.12절. 정확한 표시·요청 UX·최신성 안내는 OPEN-UF-14, 기록·복구는 OPEN-UF-12, 평가의 의미·완료 기준은 OPEN-UF-02, 저장·확정은 OPEN-UF-06·07·08에 연결합니다. D-UF-020의 당시 표시 미정 기록을 유지하고 표시 원칙을 구체화합니다.
