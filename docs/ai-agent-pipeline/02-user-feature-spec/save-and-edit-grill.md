# 저장·재편집 사용자 흐름과 합의

상태: **SAVE-01 A·SAVE-02 A 채택 / 사용자 기능의 대표 흐름 점검 / 실행 세부는 모듈 설계** · 최근 결정: 2026-11-03

연결: [정리·완료 계획](user-feature-closure-plan.md) · [사용자 기능명세](ai-pipeline-user-feature-spec-v0.1.md) · [기존 결정·미정 계약](open-contracts.md) · [웹 검색·Chip 합의](context-and-web-grill.md)

## 1. 검토 기준

웹 검색·Chip의 기본 동작은 D-UF-062~073에 기록했습니다. 구체적인 한도·권한·복구·표시 등은 잔여 OPEN으로 추적하며 U-07 전체 완료를 선언하지 않습니다. 정리 계획의 다음 순서인 P0-2 U-03~05에서 사용자에게 보일 동작·결과의 빈칸을 닫습니다.

기존 초안 저장 `UNSET / DECIDED → DRAFT`, 확정 `UNSET / DRAFT → DECIDED`, 직접 재확정과 현재 초안 재저장은 유지합니다. SAVE-01의 별도 ‘한 항목 전체 비우기’는 D-UF-074로 합의했고 기존 전이는 유지합니다. SAVE-02의 미확인 안내·자동 결과 확인·결과 안내도 D-UF-075로 합의했습니다. 이후는 사용자가 요청하고 결과를 이해·선택하는 흐름을 점검하며 실행 세부로 질문을 확장하지 않습니다. 이전 부분 가져오기 대안 두 개의 보류와 Q-LATEST-01 B·Q-LATEST-02 A도 그대로 보존합니다. 구체적인 화면 배치·API·DB·루프는 후속 설계입니다.

## 2. SAVE-01 — 한 체크리스트 항목 전체를 비운 뒤 어떤 상태로 둘 것인가 (A 채택 / D-UF-074)

**상황:** CK-04 상품 구성이 확정돼 있지만 사용자가 ‘새 구성은 나중에 정할 테니 이 구성 항목 전체를 비우고 싶다’고 선택합니다. 현재 명세 8절과 OPEN-UF-07·13은 항목 비우기·삭제·초기화의 결과를 미정으로 남겨뒀습니다. 다른 체크리스트나 프로젝트 전체를 삭제하는 요청, 일부 필드 수정, 일반 초안 저장과 구분합니다.

| 대안 | 명시적 비우기·검증 후 사용자 결과 | 트레이드오프 |
| --- | --- | --- |
| A — 해당 항목의 기획 내용을 비우고 UNSET으로 되돌림 (채택 / D-UF-074) | CK-04 전체 기획 내용이 없는 미설정 상태로 표시. 기존 확정 상태가 해제된다는 영향을 최종 선택 전에 알림. 다른 항목의 저장 내용/상태는 유지 | 내용 없음과 작성 중 초안을 구분해 진행 상황을 이해하기 쉬움. 대신 확정 내용을 비우면 그 항목이 미설정으로 돌아가므로 영향이 분명히 보여야 함 |
| B — 내용을 비우고 빈 DRAFT로 남김 (미채택) | CK-04 내용은 없지만 작성 중 초안으로 표시. 기존 확정 상태가 DRAFT로 바뀐다는 영향을 알리고 다른 항목은 유지 | 비우기도 재기획 작업의 일부로 표현할 수 있음. 대신 내용이 없는 항목을 미설정과 다르게 다뤄야 하는 이유와 표시가 필요함 |

**두 안에서 유지할 기존 경계:** 실제 내용/상태 변경은 사용자 명시적 최종 선택·공통 권한/대상/버전·서버 검증·저장 보류를 따릅니다. Chat 설명·AI 제안·편집만으로 비우지 않고 거부/보류/결과 미확인을 성공으로 표시하지 않습니다. 기존 D-UF-060·061의 최종 반영 흐름에 영향을 알리며 별도 중간 적용·종류 재선택·추가 확인 단계를 이번 질문으로 필수화하지 않습니다. 다른 항목에 실제 영향이 확인되면 변경 결과와 함께 짧게 안내하되 다른 항목을 자동 초기화하거나 후속 검토를 자동 시작하지 않습니다(D-UF-045·057).

**보존과 공동 책임:** 이번 대상은 한 항목의 현재 기획 내용·저장 상태입니다. Chat·프로젝트 원본 전체·관련 항목·과거 이력의 삭제나 이전 확정본의 영구 보존/복구를 함께 선택한 것으로 해석하지 않습니다. 비우기 권한·공통 관리 화면과의 담당·업무 검증은 C-01 공동 확인이며 결과의 인수 기준과 연결합니다. 실제 삭제/복구 구조·빈 내용의 저장 표현·상태 전이 구현은 사용자 결과 합의 후 M-02·04·07·08에서 설계합니다. 두 대안 검토 당시에는 상태 표를 바꾸지 않았으며, A 채택 후 D-UF-074의 전체 비우기 전이만 반영합니다. 나머지 삭제/초기화·공동 책임·복구 계약은 미정입니다.

**최종 선택·이유:** 사용자가 A를 채택했습니다(D-UF-074). 한 항목 전체를 명시적으로 비우고 서버 반영이 확인되면 내용 없음/UNSET으로 되돌립니다. 최종 선택 전에 비울 내용·상태 변화와 확정 해제 영향을 안내하고 다른 항목은 자동 변경하지 않으며 기존 검증·저장 보류를 유지합니다. 빈 초안과 아직 정하지 않은 항목을 구분하되 프로젝트/이력 삭제·영구 복구 보장으로 확대하지 않습니다. B안은 채택하지 않았으며 다음 SAVE-02는 별도 미정 질문입니다.

## 3. SAVE-02 — 저장 결과를 확인하지 못한 사용자의 결과 확인 흐름 (A 채택 / D-UF-075)

**상황:** 사용자가 CK-05 초안 저장이나 한 항목 전체 비우기를 최종 선택했지만 응답이 끊겨 서버에 반영됐는지 알 수 없습니다. 반영되지 않았을 수도 있고 반영 후 응답만 사라졌을 수도 있습니다. 현재 OPEN-UF-09는 성공/미반영으로 단정하지 않고 같은 변경을 조용히 두 번 적용하지 않도록 결과를 확인할 수 있어야 한다고 정했습니다. 이번에는 사용자가 보게 될 복구의 첫 단계, 즉 결과 확인의 시작 방식을 정합니다.

| 대안 | 기본 사용자 흐름 | 트레이드오프 |
| --- | --- | --- |
| A — 미확인을 알리고 읽기 목적의 결과 확인을 자동 시작 (채택 / D-UF-075) | 확인 중임을 알리고 현재 권한·확인 수단·서비스 범위 안에서 기존 요청의 반영 여부를 조회. 확인되면 그 결과를 보여주고 확인할 수 없으면 미확인을 유지하며 다음 행동 안내. 같은 저장/비우기를 자동 재전송하지 않음 | 사용자가 별도 결과 확인 조작을 반복할 부담을 줄이고 실제 상태를 찾기 쉬움. 대신 확인 작업의 진행·한계와 미확인 상태가 분명해야 하며 무한 확인 반복을 막아야 함 |
| B — 미확인을 알리고 사용자 결과 확인 요청 후 조회 (미채택) | 결과를 단정하지 않은 채 현재 편집안·선택을 유지하고 가능한 다음 행동을 안내. 사용자가 결과 확인을 선택·요청하면 기존 요청의 반영 여부를 조회 | 사용자가 추가 조회 시점을 제어하고 확인 요청을 알기 쉬움. 대신 실제로 반영돼 있어도 조작 전까지 결과 미확인이 남음 |

**두 안에서 유지할 기존 경계:** 응답 유실을 실패·미반영·성공으로 단정하거나 같은 변경을 자동 재전송하지 않습니다. 결과 확인은 기존 반영 여부를 알아보는 읽기이며 새 저장·비우기·재확정이 아닙니다. 확인할 수 있는 수단이 없거나 결과가 불충분하면 미확인을 유지합니다. 현재 내용이 우연히 같다는 이유만으로 해당 요청의 반영 성공을 확정하지 않습니다. 서버 검증·권한·대상/버전·저장 보류를 우회하지 않고 기존 저장 내용·현재 편집안을 임의로 덮어쓰지 않습니다.

**다른 재시도와의 구분:** 이 질문은 저장 결과를 읽어 확인하는 흐름이며 재선택 평가의 Projection 조회 실패·명시적 재시도(D-UF-027~030)를 자동으로 바꾸는 결정이 아닙니다. 일반 Chat과 가능한 편집은 이어갈 수 있지만 결과 확인을 실제 재저장 승인·실패한 변경의 자동 재실행으로 해석하지 않습니다. 새로운 편집 내용과 앞선 요청의 반영 결과도 구분합니다.

**후속 설계:** 결과 확인 수단은 공통 백엔드와 연결합니다. 요청 식별·중복 방지·확인 횟수/대기·재접속·동시성·API/조회 구현은 [모듈 이관 대장 3.2절](../03-module-feature-spec/deferred-design-contracts.md#32-저장-결과-확인의-후속-모듈-설계)로 옮기며 사용자 기능 Grill의 선행 질문으로 늘리지 않습니다.

**최종 선택:** 2026-11-03 사용자가 A를 채택했습니다(D-UF-075). 저장 결과를 확인하지 못하면 이를 알리고 반영 여부를 자동 확인합니다. 확인된 결과를 보여주되 확인할 수 없으면 미확인으로 안내하며 같은 변경을 자동 재전송하지 않습니다. 사용자는 추가 저장 조작을 반복하기보다 현재 반영 여부를 이해할 수 있어야 합니다. B안은 채택하지 않았습니다.

## 4. 이후 검토의 단위 — 2026-11-03

이 문서의 SAVE-01·02는 합의 기록입니다. 다음 검토는 사용자가 기획을 설명하고 → 제안을 비교·수정하고 → 저장/확정을 선택하고 → 결과·남은 한계를 이해하는 대표 흐름에 연결합니다.

새 질문은 사용자에게 필요한 기능·선택·산출 결과가 빠진 경우에 한정합니다. 확인을 몇 번·얼마나 기다릴지, 어떤 요청 키·API·복구 방식으로 구현할지는 사용자 Grill에서 정하지 않습니다. 사용자 기능의 빈칸과 공동·모듈 설계의 미정을 구분하며 이번에는 새 세부 질문을 추가하지 않습니다.
